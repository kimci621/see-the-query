<TlDr>`LATERAL` разрешает подзапросу справа видеть текущую строку слева. Postgres запускает его для каждой строки, поэтому так делают «самую дорогую книгу каждого автора».</TlDr>

## Что есть в данных

В <T id="public.author">author</T> 6 авторов. У Шолохова, Пушкина, Беляева и Верна по две книги, у Рамальо одна, у Пастернака ни одной.

У «Острова погибших кораблей» Беляева цена `NULL`. У Жюля Верна две книги по 610: «Путешествие к центру Земли» и «Дети капитана Гранта». Обе детали пригодятся, когда будем выбирать самую дорогую книгу.

## Подзапрос во FROM не видит соседа

Попробуем найти дорогую книгу каждого автора обычным подзапросом:

```sql run expectError=42P01
select a.name, t.title
from author a,
     (select title from book b
      where b.author_id = a.author_id
      order by price desc nulls last
      limit 1) t;
```

Ошибка `42P01`: `invalid reference to FROM-clause entry for table "a"`. Подзапрос в `FROM` независим: он не знает, что слева стоит `author a`, и не может взять оттуда `author_id`.

Это не придирка Postgres, а правило. Подзапрос во `FROM` строит свою таблицу до того, как внешний запрос начал с ней работать.

## LATERAL разрешает посмотреть налево

Добавим одно слово:

```sql run expect=rows:5
select a.name, t.title
from author a,
     lateral (
       select title from book b
       where b.author_id = a.author_id
       order by price desc nulls last, book_id
       limit 1
     ) t
order by a.name;
```

5 строк. Запомни число. Пастернака здесь нет: для него подзапрос не вернул ни одной строки, а запятая в `FROM` работает как внутреннее соединение.

`LATERAL` говорит: этот подзапрос имеет право ссылаться на источники слева. Postgres берёт строку автора, подставляет её `author_id` внутрь, выполняет подзапрос, получает одну книгу. И так для каждого автора.

Порядок внутри подзапроса: отфильтровать книги автора, отсортировать по цене по убыванию, взять первую. `nulls last` отправляет «Остров погибших кораблей» в конец, иначе книга без цены победила бы. Второй ключ `book_id` решает ничью у Жюля Верна: обе книги по 610, выбирается «Путешествие к центру Земли».

На доске слева 6 строк авторов. Дальше для каждого автора открывается мини-сцена: фильтр по `author_id`, сортировка, `LIMIT 1`. Подробно показаны первые три автора, остальные считаются так же. Подпись итога: «LATERAL: 3 из 6 строк подробно, всего 5 строк».

## Больше одной строки на автора

`LATERAL` не обязан возвращать ровно одну строку. Попросим две книги:

```sql run expect=rows:9
select a.name, t.title
from author a,
     lateral (
       select title from book b
       where b.author_id = a.author_id
       order by price desc nulls last, book_id
       limit 2
     ) t
order by a.name, t.title;
```

9 строк: 2 + 1 + 2 + 2 + 2. Рамальо дал одну книгу, у него больше нет. Пастернак снова отсутствует.

Это шаблон **топ N на группу**. Один и тот же подзапрос выполняется для каждой строки внешней таблицы, и его строки размножают автора, как обычное соединение.

## Когда подзапрос всегда возвращает строку

Возьмём не книгу, а счётчик:

```sql run expect=rows:6
select a.name, t.cnt
from author a,
     lateral (
       select count(*) as cnt from book b
       where b.author_id = a.author_id
     ) t
order by a.name;
```

6 строк. Пастернак вернулся, у него `cnt` равен 0.

`count(*)` без `GROUP BY` всегда возвращает одну строку, даже когда нечего считать. Поэтому подзапрос для Пастернака не пустой: в нём строка с нулём. Внутреннее соединение по запятой такую строку сохраняет.

Разница с поиском книги принципиальная: там подзапрос возвращал 0 строк, здесь одну. `LATERAL` честно передаёт наружу то, что получилось.

## LEFT JOIN LATERAL

Если нужны все авторы, включая тех, кому книга не нашлась, пишут `left join lateral`:

```sql noexec
select a.name, t.title
from author a
left join lateral (
  select title from book b
  where b.author_id = a.author_id
  order by price desc nulls last, book_id
  limit 1
) t on true;
```

`ON true` нужен потому, что у `LEFT JOIN` должно быть условие. Фильтр уже сделан внутри подзапроса, снаружи остаётся пропустить всё. Пастернак получит строку с `NULL` в `title`, всего будет 6 строк.

## Чего нет в выдаче и почему

- ❌ Пастернак в выдаче запросов через запятую: подзапрос не вернул ни одной строки, внутреннее соединение выбросило автора.
- ❌ «Остров погибших кораблей» как самая дорогая книга Беляева: цена `NULL`, а `nulls last` ставит её после чисел.
- ❌ «Дети капитана Гранта» в топ-1 Жюля Верна: обе книги по 610, второй ключ `book_id` выбрал «Путешествие к центру Земли».
- ❌ Вторые книги авторов в запросе с `limit 1`: осталась одна строка на автора.
- ❌ 6 строк в топ-1: Пастернак без книги выпал, осталось 5.

## Ловушки

<Callout kind="trap">
Забыл `nulls last`, и книга без цены стала самой дорогой:

```sql run expect=rows:5
select a.name, t.title
from author a,
     lateral (
       select title from book b
       where b.author_id = a.author_id
       order by price desc, book_id
       limit 1
     ) t
order by a.name;
```

5 строк, но у Беляева теперь «Остров погибших кораблей». В Postgres `DESC` по умолчанию ставит `NULL` первыми: `NULL` считается больше любого числа. `limit 1` берёт именно эту строку.

Сортировка `order by price desc` без `nulls last` опасна в любом топ-N. Пиши `nulls last`, если пустое значение не должно побеждать.
</Callout>

<Callout kind="tip">
Всегда добавляй второй ключ сортировки, например `book_id`. Без него две книги с одинаковой ценой могут меняться местами между запусками, и результат станет невоспроизводимым.

Для топ-N на большой таблице проверь план: `LATERAL` с `LIMIT` обычно использует индекс по `(author_id, price)`. Без индекса Postgres честно выполнит подзапрос для каждой строки, и на миллионах строк это долго.
</Callout>

## Проверь себя

1. Сколько строк вернёт запрос с `limit 2`, если убрать `limit` совсем? Сложи все книги пяти авторов.
2. Какую книгу получит Беляев, если убрать `nulls last`? Проверь на доске.
3. Сколько строк даст `left join lateral ... on true` вместо запятой? Кто появится шестым?

<Cheatsheet>
- `LATERAL` разрешает подзапросу справа ссылаться на строку слева.
- Подзапрос выполняется для каждой строки внешнего источника.
- `from a, lateral (...) t`: внутреннее соединение, авторы без строк подзапроса выпадают.
- `left join lateral (...) t on true`: все строки слева, у остальных `NULL`.
- Топ-N на группу: `where` по ключу группы, `order by`, `limit` внутри `LATERAL`.
- `desc` ставит `NULL` первыми, для цен нужен `nulls last`.
- Второй ключ сортировки делает выбор воспроизводимым.
- Для счётчика по группе `LATERAL` с `count(*)` вернёт строку даже для пустой группы.
</Cheatsheet>
