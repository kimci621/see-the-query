<TlDr>INNER JOIN склеивает строки двух таблиц в пары по условию ON. В выдачу попадают только строки, которым нашлась пара.</TlDr>

## Что есть в данных

На доске две таблицы. В <T id="public.book">book</T> 11 книг, в <T id="public.author">author</T> 6 авторов. Колонка <C id="public.book.author_id">book.author_id</C> хранит номер автора из <C id="public.author.author_id">author.author_id</C>, на доске их соединяет ребро.

Три строки особые. У «Простого Python» и «Изучаем Python» автора нет, в `author_id` стоит NULL. У Бориса Пастернака нет ни одной книги.

## Зачем соединять таблицы

В книге хранится не имя автора, а его номер. Имя лежит один раз, в таблице авторов. Исправил опечатку в имени, и она исправилась во всех его книгах сразу. Цена у этого одна: чтобы увидеть книгу рядом с именем, таблицы нужно соединить в запросе. Этим занимается `JOIN`.

Сначала посмотри на авторов и их номера:

```sql run expect=rows:6
select * from author;
```

6 строк. Шолохов это 1, Пушкин 3, Пастернак 6.

## Первое соединение

```sql run expect=rows:9
select b.title, a.name
from book b
join author a on a.author_id = b.author_id;
```

Вернулось 9 строк. Запомни это число.

`JOIN` перебирает пары: строка из <T id="public.book">book</T> плюс строка из <T id="public.author">author</T>. Для каждой пары он проверяет условие после `ON`. Дало TRUE: две строки склеиваются в одну широкую. Такое склеивание называют **соединением**, а `JOIN` без уточнений это **INNER JOIN**, внутреннее соединение. Слово `INNER` можно писать, можно опускать: на доске чип шага всё равно скажет «INNER JOIN».

На доске таблицы съезжаются, колонки `author_id` в обеих подсвечены. Между ними протягиваются 9 линий, по одной на каждую совпавшую пару. Потом половинки сливаются в одну таблицу «book b + author a»: слева колонки книги, справа колонки автора. Подпись шага: «INNER JOIN: 9 пар». Шаг `SELECT` оставляет из широкой строки только название и имя.

<Callout kind="analogy">
Курьер разносит посылки по дому. На каждой посылке номер квартиры, у курьера список жильцов с номерами. В ведомость он пишет строку на каждую врученную посылку: посылка и кто её получил. Посылка без номера в ведомость не попадёт. Жилец, которому ничего не пришло, тоже. А кому пришли две посылки, распишется дважды.
</Callout>

## Алиасы таблиц: b и a

В запросе у таблиц короткие имена: `book b`, `author a`. Это **алиасы таблиц**, как алиасы колонок из урока 4.1, только для таблиц. Через них колонку называют с указанием таблицы: `b.title`, `a.name`. Без алиасов пришлось бы писать `book.title` и `author.name`. А когда таблица соединяется сама с собой (урок 6.6), без алиасов вообще не обойтись.

Алиас заменяет имя таблицы во всём запросе. Старое имя после этого не работает:

```sql run expectError=42P01
select book.title from book b join author a on a.author_id = b.author_id;
```

Карточка ошибки так и пишет: «Таблица book здесь называется b», код `42P01`. В «Тексте Postgres» оригинал: `invalid reference to FROM-clause entry for table "book"`. Раз назвал таблицу `b`, дальше она только `b`.

## Кто не нашёл пару

Книг 11, а строк 9. Не хватает двух книг без автора. У них `author_id` NULL, а сравнение NULL с чем угодно даёт не TRUE, а «не знаю» (урок 4.5). Условие `ON` для них ни разу не дало TRUE, пары нет.

С другой стороны пропал Борис Пастернак: ни одна книга не ссылается на номер 6.

На доске это видно перед слиянием. Строки без пары краснеют и получают значок ✕, подпись говорит «INNER JOIN: строки без пары уходят». В склеенную таблицу они не переходят.

## Одна строка, две пары

Соединение может и размножить строку. У Михаила Шолохова две книги:

```sql run expect=rows:2
select a.name, b.title
from author a
join book b on b.author_id = a.author_id
where a.name = 'Михаил Шолохов';
```

2 строки: «Тихий Дон» и «Судьба человека». Автор один, а в выдаче он дважды: его строка вошла в две пары. На шаге `JOIN` у таких строк плашка «×2». Она стоит и у Пушкина, Беляева, Жюля Верна: у них тоже по две книги. Потом `WHERE` оставляет только Шолохова (урок 4.2: `WHERE` идёт после `JOIN`).

Сколько пар, столько строк. `JOIN` ничего не складывает и не схлопывает.

Заодно заметь: здесь `author` стоит первой, а `book` второй. Для INNER JOIN порядок таблиц не меняет набор строк, только порядок колонок при `select *`.

## USING: когда колонки называются одинаково

Ключ называется `author_id` в обеих таблицах. Тогда условие можно записать короче, через `USING`:

```sql run expect=rows:9
select b.title, a.name
from book b
join author a using (author_id);
```

Те же 9 строк. Условие то же, что `on b.author_id = a.author_id`. Подпись шага на доске: «INNER JOIN USING (author_id): 9 пар».

Разница видна со звёздочкой:

```sql run expect=rows:9
select * from book b join author a using (author_id);
```

Колонка `author_id` в выдаче одна, и она стоит первой. За ней остальные колонки книги, потом остальные колонки автора. Всего 12, подпись шага `SELECT` так и пишет: «12 колонок из 12». С `ON` колонок было бы 13, `author_id` встретился бы дважды. `USING` сливает одноимённые колонки соединения в одну.

## В ON можно писать любое условие

`ON` принимает любое условие, как `WHERE`. Оставим только российских авторов:

```sql run expect=rows:6
select b.title, a.name
from book b
join author a on b.author_id = a.author_id and a.country = 'Россия';
```

6 строк: по две книги у Шолохова, Пушкина и Беляева. «Python. К вершинам мастерства» (Бразилия) и две книги Жюля Верна (Франция) пары не нашли: ключ совпал, но вторая часть условия дала FALSE.

Для INNER JOIN неважно, писать такое условие в `ON` или в `WHERE`: результат один. Для LEFT JOIN это уже не так, разберём в уроке 6.3.

Пройди числа урока одной сценой. Первый шаг отправь «На доску», дальше листай «Дальше»:

## Чего нет в выдаче и почему

В соединении книг и авторов (9 строк):

- ❌ «Простой Python» и «Изучаем Python»: `author_id` NULL, условие `ON` не дало TRUE ни с одним автором.
- ❌ Борис Пастернак: ни одна книга не ссылается на него, пары нет.

В соединении с условием «Россия» (6 строк) ушли ещё:

- ❌ «Python. К вершинам мастерства»: автор из Бразилии.
- ❌ «Путешествие к центру Земли» и «Дети капитана Гранта»: автор из Франции.

## Ловушки

<Callout kind="trap">
Забыл условие соединения, и запрос не выполнится:

```sql run expectError=42601
select b.title, a.name from book b join author a;
```

Карточка «Синтаксическая ошибка», код `42601`: Postgres не понял запрос в месте «;». После `JOIN` он ждал `ON` или `USING`, а запрос кончился. Нужны все пары «каждый с каждым»: для этого есть CROSS JOIN, урок 6.5.
</Callout>

<Callout kind="trap">
Колонка `author_id` есть в обеих таблицах. Без алиаса Postgres не знает, какую из двух ты имеешь в виду:

```sql run expectError=42702
select author_id from book b join author a on b.author_id = a.author_id;
```

Карточка «Непонятно, какая author_id», код `42702`, и подсказка: укажи `a.author_id` или `b.author_id`. С `USING` такой ошибки нет: там колонка `author_id` одна.
</Callout>

<Callout kind="tip">
В запросах с `JOIN` пиши алиас у каждой колонки, даже если имя пока уникально. Завтра в другую таблицу добавят колонку с таким же именем, и запрос без алиасов упадёт с `42702`.
</Callout>

## Проверь себя

1. Замени в запросе с условием «Россия» `'Россия'` на `'Франция'`. Сколько строк вернётся?
2. Соедини книги с авторами и оставь через `WHERE` книги дороже 1000. Дорогих книг три, а сколько строк вернётся? Почему?
3. Сколько строк даст соединение с условием `a.born_year < 1900`? Борис Пастернак родился в 1890 году. Сначала ответь, потом проверь.

<Cheatsheet>
- `from t1 join t2 on условие`: пары строк, для которых условие TRUE. `JOIN` и `INNER JOIN` одно и то же.
- Строка без пары в выдачу не попадает. NULL в ключе пары не находит.
- Строка с N парами даёт N строк выдачи.
- `using (col)`: условие `t1.col = t2.col`, и колонка `col` в выдаче одна.
- Алиас таблицы: `book b`, дальше только `b.title`. Старое имя: `42P01`.
- Без `ON` и `USING`: `42601`. Колонка без алиаса есть в обеих таблицах: `42702`.
</Cheatsheet>
