<TlDr>`EXISTS` отвечает на вопрос «есть хоть одна строка», а не «сколько их». Автор остаётся одной строкой, сколько бы книг у него ни было. `IN` даёт тот же список, пока в подзапросе нет `NULL`.</TlDr>

## Что есть в данных

В <T id="public.author">author</T> 6 авторов, книги есть у пяти. У Бориса Пастернака книг нет.

У Михаила Шолохова, Александра Пушкина, Александра Беляева и Жюля Верна по две книги, у Лусиану Рамальо одна. Ещё две книги в <T id="public.book">book</T> не привязаны ни к какому автору: «Простой Python» и «Изучаем Python».

## JOIN размножает

Вопрос: какие авторы вообще выпускали книги. Начнём с обычного соединения:

```sql run expect=rows:9
select a.name, b.title
from author a
join book b on b.author_id = a.author_id
order by a.name, b.title;
```

9 строк. Авторов пять, а строк девять: у четырёх авторов по две книги, и каждый из них повторился дважды. Запомни 9.

На доске видно, как строка автора расходится на две. Для вопроса «есть ли книги» вторая строка не нужна.

## DISTINCT чинит, но после умножения

```sql run expect=rows:5
select distinct a.name
from author a
join book b on b.author_id = a.author_id
order by a.name;
```

5 строк. Результат правильный. Но `DISTINCT` убирает дубли уже после того, как соединение сделало 9 строк. Добавь в `SELECT` название книги, и `DISTINCT` перестанет помогать: пары снова разные.

Для проверки «есть или нет» колонки правой таблицы не нужны вовсе. Нужен только факт совпадения.

## EXISTS проверяет существование

```sql run expect=rows:5
select a.name
from author a
where exists (select 1 from book b where b.author_id = a.author_id)
order by a.name;
```

5 строк: все авторы, кроме Пастернака.

Это **коррелированный подзапрос**: внутри есть ссылка на `a.author_id` из внешнего запроса. Для каждой строки автора Postgres выполняет внутренний `SELECT` с её значением. Как только находится первая книга, дальше искать нечего: ответ на вопрос «есть?» уже получен.

`select 1` пишут по привычке. Значение из подзапроса никуда не попадает, важен только факт строки. Можно написать `select *`, результат тот же.

На доске для каждого автора запускается маленькая проверка по `book`. Нашлась книга: строка зелёная и остаётся. Не нашлась: Пастернак краснеет и уходит. Счётчик: 5 из 6.

Такой приём называют **SEMI JOIN**, полусоединение. В синтаксисе Postgres такого ключевого слова нет, это название шаблона.

## IN проверяет принадлежность

```sql run expect=rows:5
select a.name
from author a
where a.author_id in (select author_id from book)
order by a.name;
```

Те же 5 строк. `IN` собирает список значений из подзапроса и проверяет, есть ли в нём `author_id` текущего автора.

Разница с `EXISTS` в форме, а не в результате. `IN` не коррелирован: подзапрос не зависит от внешней строки и выполняется один раз. `EXISTS` с корреляцией проверяет каждую строку отдельно, но Postgres умеет превращать оба варианта в одно соединение.

В списке из `book` есть два `NULL`: это книги без автора. Для авторов с книгами `IN` всё равно даёт `TRUE`, потому что совпадение уже найдено. Для Пастернака совпадения нет, а сравнение с `NULL` даёт `UNKNOWN`. `WHERE` такой результат не пропускает, поэтому Пастернак и здесь отсутствует. Для положительной проверки это то, что нужно. Проблема начнётся с `NOT IN` в уроке 6.11.

## Условие внутри EXISTS

Фильтр можно поставить внутрь подзапроса. Авторы, у которых есть книга дороже 1000:

```sql run expect=rows:1
select a.name
from author a
where exists (
  select 1 from book b
  where b.author_id = a.author_id and b.price > 1000
)
order by a.name;
```

1 строка: Рамальо. Условие про цену стоит внутри `EXISTS`, поэтому проверяется вместе с авторством. Если вынести `b.price > 1000` наружу, понадобится соединение и появится риск размножения.

## Чего нет в выдаче и почему

- ❌ Пастернак в `EXISTS` и `IN`: у него нет ни одной книги.
- ❌ Дубли авторов в `EXISTS`: подзапрос возвращает да или нет, а не строки книг.
- ❌ Названия книг в выдаче: `EXISTS` не тянет колонки из подзапроса.
- ❌ «Простой Python» и «Изучаем Python» в списке авторов: у этих книг `author_id` равен `NULL`, автора у них нет.
- ❌ Вторая книга автора в `EXISTS`: для ответа хватает первой найденной.

## Ловушки

<Callout kind="trap">
Забыл корреляцию, и `EXISTS` перестал зависеть от автора:

```sql run expect=rows:6
select a.name
from author a
where exists (select 1 from book b)
order by a.name;
```

6 строк, все авторы, включая Пастернака. Подзапрос не упоминает `a`, поэтому для каждой строки он возвращает одно и то же: в `book` есть хотя бы одна строка. Формально условие истинно всегда.

На доске одна и та же проверка повторяется для всех шести авторов. Сравни с коррелированным вариантом: там у Пастернака проверка пустая.

Проверяй, что внутри подзапроса есть ссылка на внешний алиас. Без неё `EXISTS` отвечает про всю таблицу, а не про текущую строку.
</Callout>

<Callout kind="tip">
Для «есть ли связанные строки» выбирай `EXISTS`, когда условие сложное или колонок несколько. `IN` удобнее для одного столбца. По скорости современный Postgres обычно строит одинаковый план, так что решай по читаемости.

Не добавляй `DISTINCT` к соединению, если правая таблица нужна только для проверки. Это лишний шаг: `EXISTS` не создаёт дублей с самого начала.
</Callout>

## Проверь себя

1. У скольких авторов есть книга дешевле 400? Напиши запрос с `EXISTS` и условием `b.price < 400`.
2. Сколько авторов имеют книгу без цены? Проверь `b.price is null` внутри `EXISTS`.
3. Замени `EXISTS` на `NOT EXISTS`. Сколько строк останется и кто в них? Ответ пригодится в следующем уроке.

<Cheatsheet>
- `exists (select 1 ...)`: истина, если подзапрос вернул хотя бы одну строку.
- Коррелированный подзапрос ссылается на алиас внешнего запроса.
- `EXISTS` не размножает строки и не требует `DISTINCT`.
- `select 1` внутри: значение не используется, важен факт строки.
- `in (select col ...)`: проверка принадлежности, тот же результат для положительного условия.
- `NULL` в списке `IN` не мешает найти совпадение, но исключает строки без совпадения.
- `EXISTS` без ссылки на внешний алиас проверяет всю таблицу, а не текущую строку.
- Фильтр по правой таблице ставь внутрь `EXISTS`, рядом с корреляцией.
</Cheatsheet>
