<TlDr>VIEW сохраняет запрос под именем. При обращении к представлению PostgreSQL использует этот запрос и текущие данные исходных таблиц.</TlDr>

## Что есть в данных

В <T id="public.book">book</T> одиннадцать книг, три из них дороже 1000 рублей. Создадим представление с этими книгами. Примеры ниже рассчитаны на выполнение по порядку.

```sql apply expect=rows:0
create view expensive_book as select book_id, title, price from book where price > 1000;
```

Кнопка «Применить» сохраняет представление в учебной базе. На доске появляется `expensive_book`: внутри виден его запрос, пунктирная линия связывает его с `book`. Сброс базы удалит созданное представление.

<Callout kind="analogy">
Представь закладку с заранее записанным поиском в каталоге. Она хранит условие поиска, а не отдельную копию найденных книг. Открыв закладку позже, увидишь данные каталога на этот момент.
</Callout>

## Читать представление

{/* final-only: у представления нет ctid для пошаговой трассы */}
```sql run expect=rows:3 trace=final-only
select * from expensive_book order by book_id;
```

Получаем книги 2, 10 и 11. Представление можно использовать в `FROM` как источник строк. Доска показывает его определение и связь с таблицей; пошаговая трасса чтения VIEW пока недоступна, поэтому итог виден в панели результата.

{/* final-only: у представления нет ctid для пошаговой трассы */}
```sql run expect=rows:2 trace=final-only
select book_id, title from expensive_book where price > 2000 order by book_id;
```

Дополнительный фильтр оставляет две книги: 2 и 11. PostgreSQL может преобразовать запрос при планировании, поэтому число обращений к базовой таблице определяют по плану, а не по числу упоминаний VIEW.

## Где хранится определение

{/* final-only: pg_views это системное представление */}
```sql run expect=rows:1 trace=final-only
select schemaname, viewname from pg_views where viewname = 'expensive_book';
```

В каталоге `pg_views` есть строка с именем и схемой представления. Его определение можно увидеть в колонке `definition` или получить функцией `pg_get_viewdef`.

## Изменить исходные данные

```sql apply expect=rows:1
update book set price = 1500 where book_id = 6 returning title, price;
```

Применение меняет цену «Головы профессора Доуэля» в таблице. Теперь книга тоже проходит условие представления:

{/* final-only: у представления нет ctid для пошаговой трассы */}
```sql run expect=rows:1 trace=final-only
select count(*) as n from expensive_book;
```

Счётчик вернул 4. Представление не хранит отдельный снимок этих строк: при следующем чтении оно использует данные исходной таблицы, видимые запросу.

## Когда это полезно

VIEW даёт имя часто используемой выборке и может сохранить привычный интерфейс, когда внутреннее устройство таблиц меняется. Также представления позволяют выдавать доступ к выбранным данным при правильно настроенных правах. Сложный запрос внутри представления не становится автоматически дешёвым: для проверки используй `EXPLAIN`.

## Чего нет в выдаче и почему

- ❌ Книг дешевле или ровно 1000 рублей: условие использует строгое `> 1000`.
- ❌ Четвёртой книги до применения `UPDATE`: её прежняя цена равна 560.
- ❌ Отдельной копии строк внутри обычного VIEW: сохранено определение запроса.

## Ловушки

<Callout kind="trap">
`SELECT *` в определении VIEW разворачивается при создании. Позже добавленная колонка исходной таблицы сама в представлении не появится. Проверим на отдельном представлении:

```sql apply expect=rows:0
create view all_books as select * from book;
```

```sql apply expect=rows:0
alter table book add column extra_note text;
```

{/* final-only: information_schema.columns это системное представление */}
```sql run expect=rows:1 trace=final-only
select count(*) as n from information_schema.columns
where table_schema = 'public' and table_name = 'all_books' and column_name = 'extra_note';
```

Счётчик вернул 0: колонка добавлена в `book`, но не в `all_books`. Для возврата к исходным данным нажми «Сброс».
</Callout>

<Callout kind="tip">
Перечисляй нужные колонки явно. Так легче увидеть договорённость между представлением и запросами, которые его используют. Удаляют представление командой `DROP VIEW`; исходная таблица при этом остаётся.
</Callout>

## Проверь себя

1. Сколько строк вернёт `expensive_book` до изменения цены и после него?
2. Почему колонка, добавленная в `book`, не появилась в созданном ранее `all_books`?
3. Где найти определение представления?

<Cheatsheet>
- `CREATE VIEW имя AS SELECT ...` сохраняет запрос под именем.
- Обычное представление не хранит отдельный снимок результата.
- `SELECT` из представления можно дополнить собственными условиями.
- `pg_views` и `pg_get_viewdef` показывают определение.
- `SELECT *` в определении фиксирует список колонок на момент создания.
</Cheatsheet>
