<TlDr>Транзакция объединяет изменения: COMMIT фиксирует их, а ROLLBACK отменяет. Другие сессии не видят незавершённые изменения.</TlDr>

## Что есть в данных

В <T id="public.book">book</T> у книги 2 «Python. К вершинам мастерства» цена 2400,00. Изменим её и посмотрим, что сохраняется. Выполняй примеры по порядку: кнопка «Применить» оставляет изменения в учебной базе до сброса.

```sql run expect=rows:1
select title, price from book where book_id = 2;
```

На доске остаётся одна книга. Запомни цену 2400,00: с ней сравним результат первого изменения.

## Зафиксировать изменение

**Транзакция** связывает несколько команд в одну работу с базой. Начало отмечает `BEGIN`, успешное завершение - `COMMIT`. После фиксации другие транзакции могут увидеть изменения в зависимости от своего снимка данных.

```sql apply expect=rows:1
begin;
update book set price = 7 where book_id = 2;
commit;
select title, price from book where book_id = 2;
```

Нажми «Применить». Последний `SELECT` возвращает одну строку с ценой 7,00. Это изменение осталось в таблице: последующие примеры увидят его тоже.

<Callout kind="analogy">
Представь заказ на складе: пока сотрудник собирает несколько позиций, заказ ещё не передан на отправку. Когда сборка завершена, сотрудник подтверждает заказ целиком. Без подтверждения промежуточный набор не становится отправленным заказом.
</Callout>

В сцене ниже A меняет цену книги 1. Пока A не зафиксировала изменение, B читает прежнюю цену. После `COMMIT` следующий запрос B видит новую. Это заранее подготовленная сцена, она не меняет учебную базу.

<TwoSessions id="tx-basic" />

Без явного `BEGIN` PostgreSQL обычно выполняет каждый отдельный оператор в собственной транзакции. Клиентская программа может сама управлять транзакциями, поэтому в своём приложении проверяй её настройки.

## Отменить изменение

`ROLLBACK` завершает текущую транзакцию и отменяет её изменения. Попробуем поставить другую цену, но не сохранять её.

```sql apply expect=rows:1
begin;
update book set price = 9 where book_id = 2;
rollback;
select title, price from book where book_id = 2;
```

Последний запрос возвращает цену 7,00: изменение на 9 отменено, а ранее зафиксированное изменение осталось. Посмотри на доску после выполнения.

<TwoSessions id="tx-rollback" />

Теперь изменим две книги и отменим оба изменения одной командой:

```sql apply expect=rows:2
begin;
update book set price = 15 where book_id = 1;
update book set price = 20 where book_id = 2;
rollback;
select book_id, price from book where book_id in (1, 2) order by book_id;
```

Возвращаются две строки с ценами 890,00 и 7,00. Ни одно из двух временных изменений не осталось. Отмена относится к текущей транзакции, а не ко всей истории базы.

## Четыре свойства ACID

- **Атомарность**: изменения транзакции фиксируются как одно целое или отменяются. В последнем примере обе цены вернулись к прежним значениям.
- **Согласованность**: база проверяет заданные ограничения. Например, ограничение на бонус не пропускает отрицательное значение. Правила, которых нет в базе, приложение должно обеспечить само.
- **Изолированность**: параллельные транзакции работают с данными по правилам выбранного уровня изоляции. В сценах B не читает незавершённую запись A, но разные уровни по-разному определяют видимость последующих изменений.
- **Долговечность**: при обычных настройках PostgreSQL подтверждённая фиксация рассчитана на восстановление после сбоя с помощью журнала WAL. Учебная песочница работает в памяти и не заменяет резервное копирование.

Проверим ограничение бонуса. У покупателя 2 бонус равен нулю:

```sql run expect=rows:1
select customer_id, bonus from customer where customer_id = 2;
```

На доске остаётся одна строка с бонусом 0. Попытка уменьшить его нарушает `CHECK`:

```sql apply expectError=23514
begin;
update customer set bonus = bonus - 500 where customer_id = 2;
commit;
```

PostgreSQL возвращает ошибку `23514`. Песочница прерывает выполнение блока на ошибке и откатывает открытую транзакцию. Следующий запрос снова показывает бонус 0:

```sql run expect=rows:1
select customer_id, bonus from customer where customer_id = 2;
```

## Чего нет в выдаче и почему

- ❌ Цены 9 после `ROLLBACK`: изменение отменено до чтения.
- ❌ Отрицательного бонуса: ограничение `CHECK` отклонило запись.
- ❌ Незавершённой цены A в первом чтении B: другая сессия ещё не зафиксировала изменение.

## Ловушки

<Callout kind="trap">
В обычном примере «На доску» приложение само открывает транзакцию и откатывает предпросмотр. Поэтому блоки с собственными `BEGIN`, `COMMIT` и `ROLLBACK` в этом уроке запускаются кнопкой «Применить». Если отправить `BEGIN` внутри уже открытой транзакции, PostgreSQL выдаст предупреждение, но не создаст вложенную транзакцию.
</Callout>

<Callout kind="tip">
Держи транзакции короткими: открытая транзакция может удерживать блокировки и мешать другим запросам. После ошибки откатывай транзакцию; частичный откат через `SAVEPOINT` разберём в следующем уроке.
</Callout>

## Проверь себя

1. Какую цену книги 2 покажет запрос после отмены изменения на 9? Почему?
2. Что увидит B до `COMMIT` и после него в первой сцене?
3. Что произойдёт с бонусом после ошибки ограничения?

<Cheatsheet>
- `BEGIN` начинает блок транзакции.
- `COMMIT` фиксирует изменения, `ROLLBACK` отменяет изменения текущей транзакции.
- Ошибка ограничения отклоняет команду. Открытую неуспешную транзакцию нужно откатить.
- ACID: атомарность, согласованность, изолированность, долговечность.
</Cheatsheet>
