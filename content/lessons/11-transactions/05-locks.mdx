<TlDr>Блокировки защищают строки при параллельной работе. Взаимное ожидание PostgreSQL обнаруживает и прерывает ошибкой 40P01.</TlDr>

## Что есть в данных

В <T id="public.book">book</T> книга 1 «Тихий Дон» стоит 890,00. Возьмём её строку в блокировку и посмотрим, что произойдёт с запросом другой сессии.

```sql run expect=rows:1
select book_id, title, price from book where book_id = 1;
```

На доске одна книга. Обычный `SELECT` читает подходящую версию строки из снимка; ниже добавим явную блокировку к чтению.

## Заблокировать строку

**Блокировка** ограничивает одновременные действия над одним объектом. PostgreSQL получает нужные блокировки и автоматически, например при `UPDATE`. С помощью `SELECT FOR UPDATE` можно заранее заблокировать выбранные строки перед изменением.

```sql apply expect=rows:1
begin;
select book_id, title from book where book_id = 1 for update;
```

Запрос вернул одну строку. Кнопка «Применить» выполняет блок целиком и после него завершает открытую транзакцию, поэтому блокировка в песочнице уже отпущена. В обычном клиенте удерживай её в рамках транзакции и заверши работу через `COMMIT` или `ROLLBACK`.

В сцене A удерживает строку книги 1, а B пытается взять несовместимую блокировку той же строки. B ждёт до завершения A, затем получает строку. Сцена подготовлена заранее и не меняет учебную базу.

<TwoSessions id="lock-for-update" />

Обычное чтение без `FOR UPDATE` не конфликтует с блокировкой строки и использует MVCC. Но некоторые блокировки таблицы могут задержать даже обычный `SELECT`, поэтому не считай любое чтение независимым от всех блокировок.

<Callout kind="analogy">
Сотрудник берёт карточку на исправление и ставит отметку «редактируется». Другой редактор ждёт, пока карточку вернут. Посетитель при этом может читать опубликованную версию каталога.
</Callout>

## Другие варианты ожидания

`NOWAIT` сообщает об ошибке сразу, если нужную блокировку строки нельзя получить. В учебной базе другая сессия эту строку сейчас не удерживает, поэтому запрос возвращает книгу:

```sql apply expect=rows:1
begin;
select book_id, title from book where book_id = 1 for update nowait;
```

Получилась одна строка. Отсутствие ожидания здесь связано с тем, что конфликта нет; сама настройка `NOWAIT` не отменяет блокировки других типов.

`FOR SHARE` берёт более мягкую блокировку строки: она совместима с некоторыми другими блокировками чтения, но мешает конфликтующему изменению строки.

```sql apply expect=rows:1
begin;
select book_id, title from book where book_id = 1 for share;
```

Снова вернулась одна строка, и песочница завершила транзакцию. Точный список конфликтов зависит от режима блокировки: его удобно сверять по документации.

`SKIP LOCKED` пропускает строки, заблокированные другой транзакцией. Это бывает полезно нескольким обработчикам очереди, но такая выборка может быть неполной и не подходит для общего согласованного отчёта:

```sql apply expect=rows:2
begin;
select book_id, title from book where book_id in (1, 2) order by book_id for update skip locked;
```

В этой песочнице обе строки свободны, поэтому результат содержит две книги. При конфликте подходящая строка может быть пропущена.

## Взаимная блокировка

**Deadlock** возникает, когда транзакции образуют цикл ожидания: A ждёт ресурс B, а B ждёт ресурс A. В сцене каждая сессия сначала меняет свою книгу, затем пытается изменить книгу другой сессии.

<TwoSessions id="deadlock" />

PostgreSQL обнаруживает цикл и прерывает одну транзакцию с кодом `40P01`, чтобы другая могла продолжить. В этой подготовленной сцене выбрана B, но в общем случае нельзя рассчитывать на выбор конкретной стороны. Интервалы проверки в сцене настроены для воспроизводимости.

Для предупреждения взаимных блокировок старайся получать необходимые блокировки в одинаковом порядке во всех путях приложения. Это снижает риск, но не заменяет обработку ошибки и повтор всей транзакции, если он уместен.

## Чего нет в выдаче и почему

- ❌ Других книг в первом запросе: условие выбрало только `book_id = 1`.
- ❌ Ожидающих строк в примере `SKIP LOCKED`: другая сессия не удерживает выбранные книги.
- ❌ Гарантии, что в каждой взаимной блокировке прервётся B: PostgreSQL может выбрать другую транзакцию.

## Ловушки

<Callout kind="trap">
Блокировка строки действует в транзакции. Если клиент фиксирует транзакцию сразу после `SELECT FOR UPDATE`, блокировка освобождается до следующей отдельной команды. В песочнице это происходит после каждого блока «Применить».
</Callout>

<Callout kind="tip">
Выбирай только нужные строки и заверши транзакцию после работы с ними. Не держи блокировку во время ожидания пользователя или внешнего сервиса. В настройках сервера и транзакции можно ограничить ожидание через `lock_timeout`.
</Callout>

## Проверь себя

1. Почему B ждёт в первой сцене и когда ожидание заканчивается?
2. Что возвращает `SKIP LOCKED`, если другая транзакция держит одну из подходящих строк?
3. Что означает `40P01` и почему порядок доступа к строкам важен?

<Cheatsheet>
- `FOR UPDATE` блокирует выбранные строки от конфликтующих изменений и блокировок.
- `NOWAIT` сообщает о конфликте сразу; `SKIP LOCKED` пропускает занятые строки.
- Блокировки обычно освобождаются при завершении транзакции; откат к точке сохранения может освободить полученные после неё блокировки раньше.
- Deadlock даёт `40P01`; избегай разных порядков захвата одних и тех же ресурсов.
</Cheatsheet>
