<TlDr>Уровень изоляции определяет видимость параллельных изменений и допустимые результаты. При ошибке сериализации транзакцию повторяют целиком.</TlDr>

## Что есть в данных

В <T id="public.book">book</T> книга 1 «Тихий Дон» стоит 890,00. Две подготовленные сцены покажут, как меняется видимость этой цены, когда другая сессия её обновляет. Сами сцены не изменяют учебную базу.

```sql run expect=rows:1
select title, price from book where book_id = 1;
```

На доске остаётся одна книга с ценой 890,00. Это исходная цена и в каждой из сцен.

## Read Committed

**Уровень изоляции** задаёт правила, по которым транзакция видит параллельные изменения. В PostgreSQL по умолчанию используется `Read Committed`. Обычный `SELECT` получает снимок на начало своего выполнения, а следующий `SELECT` в той же транзакции может получить более свежие данные.

{/* final-only: SHOW возвращает настройку без пошаговой трассы */}
```sql run expect=rows:1 trace=final-only
show transaction_isolation;
```

В результате одна строка: `read committed`. Это текущая настройка транзакции в учебной базе. Для `SHOW` доска показывает итог без пошаговой трассы.

В первой сцене B читает книгу дважды в одной транзакции. Между чтениями A фиксирует новую цену. Второй запрос B видит 1,00 вместо 890,00. Такое изменение результата называется **неповторяющимся чтением**.

<TwoSessions id="non-repeatable-read" />

При этом обычный `SELECT` видит и собственные предыдущие изменения транзакции, хотя они ещё не зафиксированы. Другая сессия незавершённую запись не увидит.

## Repeatable Read

В `Repeatable Read` снимок для транзакции создаётся при первом операторе, которому нужен снимок, а не в момент `BEGIN`. Последующие обычные чтения используют тот же снимок и не видят новые фиксации других транзакций. Собственные изменения транзакции остаются видимыми ей самой.

```sql apply expect=rows:1
begin isolation level repeatable read;
select current_setting('transaction_isolation') as isolation;
```

Последний запрос возвращает `repeatable read`. В этом упражнении песочница автоматически завершает открытую транзакцию после блока «Применить», поэтому настройка не переносится на следующие примеры. В приложении завершай транзакцию явно через `COMMIT` или `ROLLBACK`.

Во второй сцене B сначала читает 890,00. A фиксирует цену 1,00, но повторное чтение B показывает 890,00 из прежнего снимка. Затем B пытается изменить эту же строку и получает ошибку сериализации `40001`: запись изменилась после её снимка.

<TwoSessions id="repeatable-read" />

В PostgreSQL `Repeatable Read` также не допускает фантомного чтения, но возможны другие аномалии сериализации при параллельной работе с разными строками. Одинаковые результаты повторного чтения ещё не доказывают, что все транзакции эквивалентны последовательному выполнению.

## Serializable

`Serializable` проверяет параллельные транзакции так, чтобы результат успешно зафиксированных транзакций был совместим с некоторым последовательным порядком их выполнения. При конфликте PostgreSQL может прервать одну из них ошибкой `40001`.

```sql apply expect=rows:1
begin isolation level serializable;
select current_setting('transaction_isolation') as isolation;
```

Результат последнего запроса - `serializable`. Как и в прошлом блоке, песочница закрывает транзакцию после выполнения.

<Callout kind="analogy">
Представь две заявки на изменение общего расписания. Каждая опирается на свою копию. Перед утверждением проверка должна убедиться, что совместный результат не противоречит порядку утверждения заявок. Если согласовать не удалось, одну заявку нужно подготовить заново по текущему расписанию.
</Callout>

После `40001` откати неудачную транзакцию и повтори её целиком, включая чтение и выбор значений. Повтор одной последней команды может использовать устаревшее решение. При высокой конкуренции повторов может понадобиться несколько.

## Указать уровень

Уровень можно задать при начале транзакции. Посмотрим `Read Committed` явно:

```sql apply expect=rows:1
begin isolation level read committed;
select current_setting('transaction_isolation') as isolation;
```

Последний запрос вернул `read committed`. Песочница завершает этот блок автоматически. В обычном клиенте открытая транзакция остаётся открытой до завершения.

После выполнения блоков проверим настройку следующей транзакции:

{/* final-only: SHOW возвращает настройку без пошаговой трассы */}
```sql run expect=rows:1 trace=final-only
show transaction_isolation;
```

Снова видим `read committed`: настройки предыдущих транзакций не изменили уровень по умолчанию.

`Read Uncommitted` тоже можно запросить, но PostgreSQL выполняет его как `Read Committed`. Выбирай уровень исходя из того, какие параллельные результаты допустимы для задачи, и учитывай стоимость повторов.

## Чего нет в выдаче и почему

- ❌ Незавершённой цены A в обычном чтении B: PostgreSQL не допускает грязного чтения.
- ❌ Новой цены во втором чтении `Repeatable Read`: B продолжает использовать прежний снимок.
- ❌ Гарантии последовательного результата только от `Repeatable Read`: некоторые аномалии возможны.

## Ловушки

<Callout kind="trap">
Снимок `Repeatable Read` не фиксируется самой командой `BEGIN`. Если другая транзакция успела зафиксировать изменение до первого оператора, который получает снимок, это изменение может попасть в снимок.
</Callout>

<Callout kind="tip">
Обрабатывай `40001` на границе всей транзакции. Повтори и запросы, и логику выбора значений. Для коротких операций `Read Committed` может быть достаточен; более строгий уровень выбирают под требуемое правило данных.
</Callout>

## Проверь себя

1. Почему два чтения B в сцене `Read Committed` возвращают разные цены?
2. Когда создаётся снимок в `Repeatable Read` и что происходит при конфликтующем обновлении?
3. Что нужно повторить после ошибки `40001`?

<Cheatsheet>
- `Read Committed`: новый снимок для каждого обычного `SELECT`.
- `Repeatable Read`: общий снимок с первого оператора, которому он нужен; возможна ошибка `40001`.
- `Serializable`: успешные транзакции совместимы с последовательным порядком; конфликты требуют повтора.
- В PostgreSQL `Read Uncommitted` работает как `Read Committed`.
</Cheatsheet>
