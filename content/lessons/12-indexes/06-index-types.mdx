<TlDr>У PostgreSQL есть несколько типов индексов. Выбор зависит от данных, операторов запроса и доступного класса операторов.</TlDr>

## GIN и поиск по части строки

В <T id="public.book">book</T> 100 000 книг. Посчитаем названия, содержащие «о Python»:

```sql run expect=rows:1
select count(*) as total from book where title ilike '%о Python%';
```

Одна строка результата содержит 16 667. `ILIKE` ищет без учёта регистра; знак `%` допускает произвольные символы. Для поиска внутри строки установим расширение `pg_trgm`:

```sql apply expect=rows:0
create extension pg_trgm;
```

Нажми «Применить», затем создай GIN-индекс с классом операторов для триграмм:

```sql apply expect=rows:0
create index book_title_trgm_idx on book using gin (title gin_trgm_ops);
```

**GIN** связывает составные значения с их элементами. Вместе с подходящими классами операторов его применяют для массивов, JSONB, полнотекстового поиска и триграмм. Расширение `pg_trgm` помогает искать и по фрагменту строки, не только по её началу.

Найдём конкретное название:

```sql run expect=rows:1
select count(*) as total from book where title ilike '%Книга 8 о Python%';
```

Счётчик равен 1. Посмотрим план поиска самой книги:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
select book_id from book where title ilike '%Книга 8 о Python%';
```

Открой полное значение JSON. В исходном наборе план обычно содержит `Bitmap Index Scan` по `book_title_trgm_idx`, затем проверку найденных строк. Для другого шаблона или распределения данных план может отличаться.

<Callout kind="analogy">
Алфавитный каталог удобно искать по началу названия. Для поиска фрагмента внутри названия можно завести указатель коротких сочетаний символов и по нему находить кандидатов для проверки.
</Callout>

## BRIN и порядок данных

Заказы в <T id="public.orders">orders</T> добавлены по возрастанию времени. Создадим BRIN по времени:

```sql apply expect=rows:0
create index orders_created_brin_idx on orders using brin (created_at);
```

BRIN хранит сводку по диапазонам соседних страниц. Для этого типа времени стандартный класс может хранить минимум и максимум. Если диапазон страниц не может содержать нужную дату, его можно пропустить.

Посчитаем заказы за 1 июня 2023 года:

```sql run expect=rows:1
select count(*) as total from orders
where created_at >= '2023-06-01 00:00+03' and created_at < '2023-06-02 00:00+03';
```

В одной строке счётчика 288 заказов. Проверь план:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
select order_id from orders
where created_at >= '2023-06-01 00:00+03' and created_at < '2023-06-02 00:00+03';
```

В этом наборе обычно выбран `Bitmap Index Scan` по BRIN с последующей проверкой страниц таблицы. BRIN возвращает кандидатов на уровне диапазонов страниц, поэтому в `Rows Removed by Index Recheck` могут быть строки за другие даты. Порядок данных и размер диапазона влияют на эффективность; индекс компактный, но его поддержка тоже имеет стоимость.

## Hash и другие типы

Создадим Hash-индекс по адресу покупателя:

```sql apply expect=rows:0
create index customer_email_hash_idx on customer using hash (email);
```

Проверим равенство:

```sql run expect=rows:1
select customer_id from customer where email = 'User42@Example.com';
```

Вернулась одна строка с номером 42. Hash поддерживает индексный поиск по равенству, но не поиск диапазона или выдачу в порядке ключа. В этом наборе для `email` уже существует уникальный B-tree, поэтому дополнительный Hash-индекс здесь нужен только для опыта и может не выбираться планировщиком.

B-tree по умолчанию подходит для равенства, диапазонов и сортировки. GiST поддерживает разные структуры и операторы, например поиск по геометрии и диапазонам; некоторые классы поддерживают поиск ближайших соседей. SP-GiST полезен для некоторых разбиений пространства, в том числе для поддерживаемых операций с IP-адресами. Возможности определяет не только название типа, но и класс операторов.

«Сброс» вернёт учебную базу к исходному состоянию и удалит созданные индексы и расширение.

## Чего нет в выдаче и почему

- ❌ 16 667 строк результата `count(*)`: это значение в одной строке.
- ❌ Заказов за другие даты в результате: повторная проверка BRIN отбрасывает неподходящие строки.
- ❌ Гарантии применения каждого созданного индекса: планировщик сравнивает доступные варианты.

## Ловушки

<Callout kind="trap">
BRIN хранит сводку по страницам, а не точный список всех подходящих строк. Чем слабее связь значения с расположением строк, тем больше лишних страниц может потребоваться проверить.
</Callout>

<Callout kind="tip">
Подбирай тип и класс операторов под конкретные условия запроса. Сравни планы на своих данных и учти место и стоимость поддержки индекса при записи.
</Callout>

2. Почему BRIN может вернуть кандидатов, которые не проходят повторную проверку?
3. Почему учебный Hash-индекс по email может оказаться лишним?

<Cheatsheet>
- B-tree поддерживает равенство, диапазоны и упорядоченную выдачу.
- GIN подходит для поиска элементов составных значений с соответствующим классом операторов.
- BRIN хранит сводки по диапазонам страниц; Hash поддерживает равенство.
- GiST и SP-GiST решают специализированные задачи, доступные операции зависят от класса операторов.
</Cheatsheet>
