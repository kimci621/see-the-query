<TlDr>EXPLAIN показывает план и оценки PostgreSQL. EXPLAIN ANALYZE выполняет запрос и добавляет фактические счётчики.</TlDr>

## Что есть в данных

В <T id="public.orders">orders</T> 100 000 заказов. У покупателя 42 есть пять заказов; отдельного индекса по `customer_id` в исходном наборе нет. Начнём с обычного поиска:

```sql run expect=rows:5
select order_id from orders where customer_id = 42 order by order_id;
```

В результате пять строк. Во вкладке «План» PostgreSQL показывает дерево выполнения этого `SELECT`. Узел `Seq Scan` на исходном наборе проверяет 100 000 строк, пять проходят фильтр. Наведи указатель на связанный узел или переведи на него фокус: соответствующий шаг подсветится на ленте.

## План до выполнения

**План запроса** - дерево операций, выбранных оптимизатором. Нижние узлы обычно читают исходные данные, вышестоящие используют их результат, например сортируют строки. Вкладка «План» строится для поддерживаемых `SELECT` на большом наборе; запросы с произвольными функциями или блокировкой строк она автоматически не повторяет.

`EXPLAIN` без `ANALYZE` показывает оценки, не выполняя сам оператор. Запросим машинный формат JSON:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (format json) select order_id from orders where customer_id = 42 order by order_id;
```

Вернулась одна строка с JSON-планом. Нажми на подчёркнутую ячейку, чтобы открыть полное значение; окно можно прокручивать и закрыть клавишей Esc. В исходном плане узел чтения содержит `Plan Rows` - оценку числа строк, которые он передаст дальше за один проход. `Total Cost` - оценка стоимости в условных единицах, а не время в миллисекундах. Над `EXPLAIN` доска показывает итог без пошаговой трассы.

<Callout kind="analogy">
Перед поездкой навигатор оценивает маршрут по карте и доступным сведениям. После поездки можно сравнить оценку с фактическим временем и пройденным расстоянием. Карта нужна для выбора пути, но не является записью уже состоявшейся поездки.
</Callout>

## Измерить выполнение

`EXPLAIN ANALYZE` выполняет оператор и сообщает фактические значения. Добавим `BUFFERS`, чтобы увидеть обращения к буферам:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, buffers, format json)
select order_id from orders where customer_id = 42 order by order_id;
```

Снова одна строка с JSON. Ищи в узле чтения `Actual Rows`: на один проход приходится пять строк. `Rows Removed by Filter` показывает 99 995 отброшенных строк. Вместе это 100 000 проверенных строк, если узел выполнился один раз.

Сравни `Plan Rows` и `Actual Rows`. Большая разница может подсказать проблему с оценкой или статистикой, но сама по себе не доказывает её причину. Время зависит от машины, нагрузки и состояния кэша, поэтому точное число из одного запуска не переносится на другой.

## Повторные проходы и буферы

Если узел выполнился несколько раз, `Actual Loops` показывает количество проходов, а фактические строки и время указываются в среднем за проход. Для общего числа приблизительно умножь среднее на `Actual Loops`. При усреднении и округлении точность может потеряться.

`Shared Hit Blocks` показывает обращения к общим буферам, где нужный блок уже был в кэше, а `Shared Read Blocks` - блоки, прочитанные в буферы. Повторные обращения учитываются. Счётчики родителя включают работу дочерних узлов, поэтому складывать все уровни дерева между собой нельзя.

Сравним поиск диапазона по первичному ключу:

```sql run expect=rows:10
select order_id from orders where order_id between 5000 and 5009 order by order_id;
```

Вернулось десять строк. Открой вкладку «План» и сравни узел чтения с предыдущим `Seq Scan`. Запросим тот же план в JSON:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, buffers, format json)
select order_id from orders where order_id between 5000 and 5009 order by order_id;
```

JSON занимает одну строку результата. Планировщик может использовать индекс первичного ключа; фактические счётчики буферов и время зависят от запуска. Не сравнивай их как число уникальных страниц или как фиксированное время с диска.

## ANALYZE действительно выполняет команду

Посмотрим статус заказа 1:

```sql run expect=rows:1
select order_id, status from orders where order_id = 1;
```

В результате статус `new`. Следующая команда измеряет `UPDATE`, который временно меняет его на `cancelled`:

{/* final-only: EXPLAIN UPDATE не имеет пошаговой трассы */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
update orders set status = 'cancelled' where order_id = 1;
```

`ANALYZE` выполнил `UPDATE`, но кнопка «На доску» запускает предпросмотр в транзакции с откатом. Поэтому после окончания примера статус остаётся прежним:

```sql run expect=rows:1
select order_id, status from orders where order_id = 1;
```

Снова видим `new`. Не нажимай «Применить» для этого примера, если не хочешь сохранить изменение. На обычном сервере `EXPLAIN ANALYZE` тоже выполняет команду; откат транзакции не отменяет все возможные побочные эффекты, например выдачу значений последовательности или внешние действия функции.

## Чего нет в выдаче и почему

- ❌ Фактического времени в обычном `EXPLAIN`: без `ANALYZE` это только оценки.
- ❌ Изменённого статуса после предпросмотра: транзакция с `UPDATE` откатилась.
- ❌ Суммы буферов всех уровней как числа разных страниц: обращения могут повторяться и включаются в счётчики родителей.

## Ловушки

<Callout kind="trap">
`EXPLAIN ANALYZE` не является безопасным чтением только потому, что начинается со слова `EXPLAIN`. Он выполняет вложенный оператор. Перед измерением изменения данных продумай откат и побочные эффекты.
</Callout>

<Callout kind="tip">
Начни с самого дорогого по факту участка и сравни оценки с результатами. Повтори измерение при сопоставимых условиях и учти кэш, количество проходов и стоимость поддержания индекса.
</Callout>

2. Сколько строк проверил исходный `Seq Scan` для покупателя 42 и сколько вернул?
3. Почему после `EXPLAIN ANALYZE UPDATE` в предпросмотре статус заказа не изменился?

<Cheatsheet>
- `EXPLAIN` показывает выбранный план и оценки.
- `EXPLAIN ANALYZE` выполняет оператор и добавляет фактические данные.
- `Actual Loops` нужен для понимания средних показателей узла.
- `BUFFERS` показывает обращения к буферам; счётчики узлов нельзя бездумно суммировать.
</Cheatsheet>
