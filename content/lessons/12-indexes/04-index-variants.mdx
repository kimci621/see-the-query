<TlDr>Индекс может проверять уникальность, хранить только часть строк, индексировать выражение или содержать дополнительные колонки для запроса.</TlDr>

## Уникальный индекс и часть таблицы

В учебном наборе у покупателя 1 пять новых заказов:

```sql run expect=rows:1
select count(*) as total from orders where customer_id = 1 and status = 'new';
```

Одна строка результата содержит число 5. Попробуем потребовать не более одного нового заказа на покупателя:

```sql run expectError=23505
create unique index orders_new_unique_idx on orders (customer_id) where status = 'new';
```

Ошибка `23505`: данные уже нарушают это правило, поэтому индекс не создан. Если бы в таблице не было повторных покупателей среди новых заказов, такой **частичный уникальный индекс** проверял бы уникальность только строк, подходящих под `WHERE`. Заказы других статусов в него не попали бы.

Уникальный индекс также может помогать поиску. Обычный уникальный индекс по умолчанию допускает несколько `NULL`; `NULLS NOT DISTINCT` меняет это правило. Первичный ключ и ограничение `UNIQUE` создают необходимые уникальные индексы автоматически.

Создадим частичный индекс без требования уникальности:

```sql apply expect=rows:0
create index orders_new_customer_idx on orders (customer_id) where status = 'new';
```

«Применить» сохраняет индекс в учебной базе. Теперь найдём те же заказы:

```sql run expect=rows:5
select order_id from orders where customer_id = 1 and status = 'new' order by order_id;
```

В результате пять строк. Частичный индекс содержит только строки с `new`; планировщик может выбрать его, когда способен доказать, что условие запроса подразумевает условие индекса. Сам результат от создания индекса не меняется.

<Callout kind="analogy">
На складе можно завести отдельный указатель только для посылок, ожидающих отправки. Если в указателе запрещены повторные номера получателей, сначала придётся проверить, что среди ожидающих посылок таких повторов нет.
</Callout>

## Индекс по выражению

В <T id="public.customer">customer</T> адрес покупателя 42 записан как `User42@Example.com`. Найдём его без учёта регистра с помощью `lower`:

```sql run expect=rows:1
select customer_id, email from customer where lower(email) = 'user42@example.com';
```

Вернулась одна строка с исходным адресом. Создадим индекс по результату выражения:

```sql apply expect=rows:0
create index customer_lower_email_idx on customer (lower(email));
```

План того же поиска можно посмотреть целиком в JSON:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
select customer_id from customer where lower(email) = 'user42@example.com';
```

Открой полное значение ячейки. Для исходного набора план обычно содержит `Bitmap Index Scan` по `customer_lower_email_idx`. Индекс хранит результат `lower(email)`, а не исходный текст адреса. Наличие подходящего индекса не гарантирует его выбор: решение зависит от оценок и данных.

## Дополнительные колонки в индексе

Создадим индекс по покупателю и добавим в него статус:

```sql apply expect=rows:0
create index orders_customer_cover_idx on orders (customer_id) include (status);
```

`customer_id` - ключ поиска, а `status` после `INCLUDE` хранится как дополнительное значение. Этот статус не становится ключом поиска или сортировки в индексе. Запросим план для одного найденного заказа:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
select status from orders where customer_id = 42 limit 1;
```

Результат содержит одну строку с JSON-планом. В этом наборе план обычно показывает `Index Only Scan` по новому индексу. Найди `Heap Fetches`: если счётчик больше нуля, PostgreSQL всё же проверил видимость некоторых строк в таблице. Название `Index Only Scan` не обещает ноль обращений к таблице. Это зависит от карты видимости и состояния данных.

«Сброс» удалит созданные учебные индексы и восстановит исходный набор. Дополнительные индексы занимают место и требуют работы при изменении данных.

## Чего нет в выдаче и почему

- ❌ Уникального индекса по новым заказам: пять заказов одного покупателя нарушают его условие.
- ❌ Заказов других статусов в частичном индексе: они не подходят под его `WHERE`.
- ❌ Гарантии отсутствия обращений к таблице при `Index Only Scan`: видимость строки иногда нужно проверить в таблице.

## Ловушки

<Callout kind="trap">
Частичный индекс полезен запросу, только когда планировщик может связать его условие с предикатом индекса. Проверяй конкретный план, особенно для запросов с параметрами.
</Callout>

<Callout kind="tip">
Выбирай индекс под конкретные запросы и ограничения данных. Сверяй план и `Heap Fetches`, а также учитывай размер индекса и стоимость записи.
</Callout>

## Проверь себя

1. Почему уникальный индекс по покупателю среди новых заказов не создался?
2. Чем индекс `lower(email)` отличается от индекса по исходному адресу?
3. Почему в `Index Only Scan` может быть ненулевой `Heap Fetches`?

<Cheatsheet>
- `UNIQUE` запрещает повторение ключей с учётом правил обработки `NULL`.
- Частичный индекс содержит строки, удовлетворяющие его `WHERE`.
- Индекс по выражению хранит результат этого выражения.
- `INCLUDE` добавляет данные в индекс, но не в ключ поиска; видимость может потребовать обращения к таблице.
</Cheatsheet>
