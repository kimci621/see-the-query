<TlDr>Seq Scan просматривает таблицу последовательно. B-tree помогает найти подходящие ключи в упорядоченном индексе и перейти к строкам таблицы.</TlDr>

## Что есть в данных

В большом учебном наборе <T id="public.orders">orders</T> содержит 100 000 заказов. Первичный ключ <C id="public.orders.order_id">order_id</C> уже обеспечен уникальным B-tree индексом `orders_pkey`. Сначала найдём заказ 5000:

```sql run expect=rows:1
select order_id, customer_id from orders where order_id = 5000;
```

Результат содержит одну строку. Большая таблица на доске показана сжато: она не загружает все 100 000 строк в узел. Открой вкладку «План» под редактором: PostgreSQL показывает выбранный способ доступа и фактические счётчики.

## Последовательный просмотр

**Seq Scan** проходит по строкам таблицы и проверяет условие. Для полного поиска по неиндексированной колонке ему может понадобиться просмотреть всю таблицу. Найдём заказы покупателя 42, для которого отдельного индекса пока нет:

```sql run expect=rows:5
select order_id from orders where customer_id = 42 order by order_id;
```

Получилось пять заказов. Во вкладке «План» найди узел `Seq Scan`: на исходном наборе он показывает 100 000 просмотренных строк и пять возвращённых. Подсветка связанного шага включается при наведении на название узла или переводе фокуса с клавиатуры.

Число возвращённых строк само по себе не говорит, сколько работы выполнил запрос: здесь результат мал, но условие проверялось по всей таблице. Счётчики и выбранный план зависят от данных, индексов и статистики.

## Как помогает B-tree

**B-tree** хранит упорядоченные ключи на страницах дерева. По разделителям внутренних страниц PostgreSQL выбирает путь к листу, а запись листа указывает на версию строки в таблице. Для некоторых запросов нужные данные можно получить из самого индекса; это отдельный способ `Index Only Scan`.

Сцена читает реальные страницы `orders_pkey` из учебной базы. На первом шаге видны страницы таблицы, на втором - принудительный `Seq Scan` по ключу 5000. Затем раскрой корень и листы и проследи путь этого же ключа. Последний шаг показывает план, который оптимизатор выбрал для того же запроса без принуждения.

<BTreeScene table="orders" index="orders_pkey" column="order_id" value="5000" />

Адрес `ctid` в сцене относится к версии строки, а не к постоянному идентификатору заказа. Количество страниц и обращения к буферам получены в текущем запуске: повторные обращения учитываются, поэтому счётчик буферов не равен числу разных страниц.

<Callout kind="analogy">
Представь упорядоченный каталог деталей на складе. Сначала находишь нужный диапазон номеров в указателе, затем нужную карточку и место детали. Если нужно осмотреть почти всё содержимое склада, обход всех полок может оказаться удобнее переходов по указателю.
</Callout>

## Равенство и диапазон

B-tree подходит не только для одного значения. По нему можно искать диапазон и получать строки в порядке ключа:

```sql run expect=rows:10
select order_id from orders where order_id between 5000 and 5009 order by order_id;
```

Вернулось десять заказов. Посмотри план: оптимизатор может использовать индекс первичного ключа для диапазона. Наличие индекса не заставляет его выбирать индекс при любом условии или размере результата.

## Добавить индекс для покупателя

Создадим отдельный индекс по <C id="public.orders.customer_id">customer_id</C>:

```sql apply expect=rows:0
create index orders_customer_idx on orders (customer_id);
```

«Применить» сохраняет индекс в учебной базе. Он занимает место и должен поддерживаться при изменении данных. Нажми «Сброс», чтобы удалить учебные изменения и вернуться к исходному набору.

Теперь повторим тот же поиск пяти заказов:

```sql run expect=rows:5
select order_id from orders where customer_id = 42 order by order_id;
```

Результат по-прежнему содержит пять строк. Во вкладке «План» сравни выбранный способ доступа с прежним `Seq Scan`. В этом наборе PostgreSQL обычно выбирает поиск через новый индекс, но конкретный план может измениться вместе со статистикой и условиями выполнения.

```sql run expect=rows:10
select order_id, customer_id from orders where customer_id in (42, 43) order by order_id;
```

Для двух покупателей получаем десять заказов. Посмотри, какие узлы появились в плане и сколько строк они вернули. Само количество заказов от создания индекса не изменилось.

```sql run expect=rows:1
select count(*) as total_orders from orders;
```

Счётчик вернул одну строку со значением 100 000. Для операции над всей таблицей последовательное чтение может быть дешевле, чем множество переходов через индекс.

## Чего нет в выдаче и почему

- ❌ Заказов других покупателей в запросе для 42: их отбрасывает условие `WHERE`.
- ❌ Новых заказов после создания индекса: индекс меняет способ поиска, а не содержимое таблицы.
- ❌ Обещания, что индекс всегда быстрее: решение зависит от доли строк, статистики и стоимости доступа.

## Ловушки

<Callout kind="trap">
`ctid` описывает положение конкретной версии строки и может измениться после обновления. Для постоянной ссылки на заказ используй `order_id`.
</Callout>

<Callout kind="tip">
Создавай индекс под реальные условия запросов и проверяй план на подходящих данных. Каждый дополнительный индекс требует места и работы при записи, поэтому полезность оценивают вместе со стоимостью поддержки.
</Callout>

## Проверь себя

1. Сколько строк возвращает поиск покупателя 42 и сколько просматривает исходный `Seq Scan`?
2. Какой путь проходит поиск ключа 5000 в сцене?
3. Почему после создания индекса результат остался прежним, хотя план мог измениться?

<Cheatsheet>
- `Seq Scan` последовательно читает строки таблицы.
- B-tree хранит упорядоченные ключи и подходит для равенства и диапазонов.
- `CREATE INDEX` добавляет структуру поиска, но не гарантирует её выбор планировщиком.
- Вкладка «План» показывает фактические счётчики для поддерживаемого `SELECT`.
</Cheatsheet>
