<TlDr>Планировщик оценивает долю подходящих строк и стоимость вариантов по статистике. ANALYZE обновляет статистику, а EXPLAIN показывает выбранный план.</TlDr>

## Сколько строк подходит

В <T id="public.orders">orders</T> 100 000 заказов. Посчитаем оплаченные:

```sql run expect=rows:1
select count(*) as total from orders where status = 'paid';
```

Одна строка результата содержит 67 000. Теперь посчитаем новые заказы:

```sql run expect=rows:1
select count(*) as total from orders where status = 'new';
```

Здесь значение счётчика 3000. В документации PostgreSQL **селективность условия** - доля строк, которые ему соответствуют: в исходном наборе это 0,67 и 0,03. В других источниках словами «высокая селективность» иногда называют обратное свойство: насколько узкой получается выборка. Чтобы не путаться, сравниваем сами доли.

## Один индекс, разные планы

Создадим индекс по статусу:

```sql apply expect=rows:0
create index orders_status_idx on orders (status);
```

Нажми «Применить». Посмотрим фактический план поиска оплаченных заказов:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json) select order_id from orders where status = 'paid';
```

Открой полное значение JSON. В исходном наборе обычно выбран `Seq Scan`: условию соответствуют 67 000 строк. Сравним поиск новых заказов:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json) select order_id from orders where status = 'new';
```

Здесь обычно видны `Bitmap Index Scan` и `Bitmap Heap Scan`, возвращающие 3000 строк. Индекс один и тот же, но доля найденных заказов разная. Точный план зависит от статистики, стоимости операций и состояния базы; одна доля не гарантирует конкретный способ чтения.

<Callout kind="analogy">
В бумажном справочнике указатель удобен, когда нужно найти несколько записей. Если нужен почти весь справочник, последовательное чтение может оказаться дешевле постоянных переходов по указателю.
</Callout>

## Что знает планировщик

Планировщик использует приблизительные сведения о размере таблицы и распределении значений. Их можно посмотреть через представление `pg_stats`. Узнаем оценку числа разных покупателей и связь порядка значений с физическим порядком строк:

{/* final-only: системное представление не показано на учебной доске */}
```sql run expect=rows:1 trace=final-only
select n_distinct, correlation from pg_stats
where schemaname = 'public' and tablename = 'orders' and attname = 'customer_id';
```

Вернулась одна строка. `n_distinct` около −0,2 означает оценку числа разных значений примерно в 20% от размера таблицы; это не отрицательное число покупателей. `correlation` около нуля говорит, что порядок значений слабо связан с физическим порядком строк. Оценки зависят от выборки статистики.

Сравним время создания заказа:

{/* final-only: системное представление не показано на учебной доске */}
```sql run expect=rows:1 trace=final-only
select correlation from pg_stats
where schemaname = 'public' and tablename = 'orders' and attname = 'created_at';
```

Для исходного набора корреляция близка к 1: заказы вставлены в порядке времени. Это может быть полезно при выборе BRIN-индекса, но не гарантирует его выгоду для любого запроса.

Статистика также хранит частые значения и оценку их долей:

{/* final-only: системное представление не показано на учебной доске */}
```sql run expect=rows:1 trace=final-only
select most_common_vals, most_common_freqs from pg_stats
where schemaname = 'public' and tablename = 'orders' and attname = 'status';
```

В одной строке перечислены статусы и приблизительные частоты в соответствующем порядке. Для `paid` оценка около 0,67, для `new` около 0,03. Они могут немного отличаться от точных долей, полученных через `count(*)`.

## Обновить статистику

Статистика может устареть после массовых изменений. Обновим её для заказов:

```sql apply expect=rows:0
analyze orders;
```

«Применить» сохраняет обновлённую статистику в учебной базе. После повторного сбора оценки могут немного измениться: для большой таблицы `ANALYZE` обычно использует выборку. В обычной установке PostgreSQL автовакуум также запускает анализ по мере изменений; после крупной загрузки иногда полезно запустить его вручную.

Не путай эту команду с `EXPLAIN ANALYZE`: первая собирает статистику таблицы, вторая выполняет запрос и добавляет фактические показатели в план. «Сброс» вернёт исходный учебный набор и удалит созданный индекс.

## Чего нет в выдаче и почему

- ❌ 67 000 строк результата у `count(*)`: счётчик находится в одной строке.
- ❌ Гарантированного плана только по размеру выборки: планировщик учитывает и другие оценки стоимости.
- ❌ Точной переписи данных в `pg_stats`: статистика приблизительна и может устареть.

## Ловушки

<Callout kind="trap">
Большое расхождение `Plan Rows` и `Actual Rows` - повод исследовать оценки и статистику, но не доказательство одной конкретной причины. При нескольких проходах учитывай `Actual Loops`.
</Callout>

<Callout kind="tip">
Сравни планы и фактические счётчики на подходящих данных. После массового изменения проверь актуальность статистики и при необходимости запусти `ANALYZE`.
</Callout>

<Cheatsheet>
- Селективность условия в документации PostgreSQL - оценка доли подходящих строк.
- `pg_stats` показывает приблизительную статистику распределения.
- `ANALYZE` обновляет статистику; `EXPLAIN ANALYZE` выполняет запрос и измеряет план.
- Один индекс может давать разные планы для разных условий.
</Cheatsheet>
