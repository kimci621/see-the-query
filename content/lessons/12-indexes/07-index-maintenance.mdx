<TlDr>Индексы требуют места и работы при записи. Перед удалением проверь их назначение и статистику; CONCURRENTLY уменьшает блокировку записи при создании.</TlDr>

## Зачем проверять индексы

Дополнительный индекс может ускорять запросы, но занимает место и требует поддержки при изменениях данных. В учебном наборе <T id="public.customer">customer</T> содержит 20 000 покупателей. Найдём тех, у кого 42 бонуса:

```sql run expect=rows:1
select count(*) as total from customer where bonus = 42;
```

В одной строке счётчика 40 покупателей. Индекс по бонусам мог бы помочь некоторым запросам, но его полезность нужно проверять на реальной нагрузке и с учётом цены записи.

## Что показывает статистика

Системное представление `pg_stat_user_indexes` содержит сведения об использовании индексов. Посмотрим индекс первичного ключа <T id="public.orders">orders</T>:

{/* final-only: системное представление не показано на учебной доске */}
```sql run expect=rows:1 trace=final-only
select indexrelname, idx_scan from pg_stat_user_indexes
where schemaname = 'public' and relname = 'orders';
```

В результате одна строка `orders_pkey` и счётчик 0. В этой учебной базе PGlite статистика активности не накапливается, поэтому ноль здесь не показывает реальное использование. На сервере `idx_scan` помогает искать кандидатов для исследования, но сам по себе не доказывает, что индекс лишний.

Первичный ключ и уникальные ограничения защищают данные даже тогда, когда индекс не выбирают для обычных запросов. Учитывай время с последнего сброса статистики, редкие периодические запросы, реплики и назначение индекса, прежде чем решать вопрос об удалении.

<Callout kind="analogy">
Журнал обращений к запасному выходу может долго оставаться пустым. Это не говорит, что выход не нужен: сначала нужно понять, какую задачу он решает.
</Callout>

## Создание без блокировки обычной записи

Обычный `CREATE INDEX` блокирует изменения таблицы до окончания построения. `CREATE INDEX CONCURRENTLY` позволяет обычным `INSERT`, `UPDATE` и `DELETE` продолжаться, но выполняет больше работы и может ждать другие транзакции. Эта команда не запускается внутри блока транзакции.

Кнопка «На доску» выполняет предпросмотр внутри транзакции с откатом. Поэтому такой пример завершится ошибкой:

```sql run expectError=25001
create index concurrently customer_bonus_idx on customer (bonus);
```

Ошибка `25001` сообщает, что конкурентное создание нельзя выполнить внутри транзакции. Создадим индекс отдельной командой вне предпросмотра:

```sql apply expect=rows:0
create index concurrently customer_bonus_idx on customer (bonus);
```

Нажми «Применить». Учебная база работает в браузере и не моделирует параллельную нагрузку сервера; здесь мы проверяем синтаксис и ограничение транзакции, а не измеряем блокировки.

Проверим созданные индексы покупателя:

{/* final-only: системное представление не показано на учебной доске */}
```sql run expect=rows:3 trace=final-only
select indexname from pg_indexes
where schemaname = 'public' and tablename = 'customer' order by indexname;
```

Три строки: новый `customer_bonus_idx`, индекс уникального email и индекс первичного ключа. После неудачного конкурентного построения на сервере может остаться индекс со статусом `INVALID`: он не используется для запросов, но может требовать ресурсов на обновление. Перед повторной попыткой проверь его состояние и причину ошибки.

## Удалить учебный индекс

Удалим только созданный в уроке индекс:

```sql apply expect=rows:0
drop index customer_bonus_idx;
```

Нажми «Применить» и снова посмотри список:

{/* final-only: системное представление не показано на учебной доске */}
```sql run expect=rows:2 trace=final-only
select indexname from pg_indexes
where schemaname = 'public' and tablename = 'customer' order by indexname;
```

Остались два индекса ограничений. Обычный `DROP INDEX` блокирует доступ к таблице на время удаления; `DROP INDEX CONCURRENTLY` уменьшает это влияние, но имеет ограничения и тоже не выполняется в блоке транзакции. На рабочем сервере сначала изучи зависимости и условия удаления, а не удаляй индексы только по нулевому счётчику.

## Чего нет в выдаче и почему

- ❌ Гарантии бесполезности `orders_pkey` при нулевом `idx_scan`: он обеспечивает первичный ключ, а учебный счётчик не накапливается.
- ❌ `customer_bonus_idx` после удаления: команда удалила именно этот учебный индекс.
- ❌ Демонстрации параллельной записи: браузерный пример проверяет команды в одной учебной базе.

## Ловушки

<Callout kind="trap">
`CREATE INDEX CONCURRENTLY` нельзя выполнять внутри блока транзакции. После неудачи проверь, не остался ли `INVALID`-индекс, и выясни причину ошибки.
</Callout>

<Callout kind="tip">
Для оценки индекса изучи запросы за представительный период, ограничения и зависимости. Только затем сравни пользу индекса с затратами на его хранение и обновление.
</Callout>

## Проверь себя

1. Почему нулевого `idx_scan` недостаточно для удаления индекса?
2. Почему конкурентное создание не выполнилось через «На доску», но выполнилось через «Применить»?
3. Что нужно проверить после неудачного `CREATE INDEX CONCURRENTLY`?

<Cheatsheet>
- Индекс расходует место и ресурсы на поддержку при изменении данных.
- `idx_scan` помогает исследовать использование, но не описывает назначение индекса целиком.
- `CREATE INDEX CONCURRENTLY` не блокирует обычную запись на всё время построения и не работает внутри блока транзакции.
- Неудачное конкурентное построение может оставить `INVALID`-индекс.
</Cheatsheet>
