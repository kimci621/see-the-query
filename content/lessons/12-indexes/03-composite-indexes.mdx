<TlDr>В составном B-tree порядок колонок влияет на поиск и сортировку. Условия по первым колонкам обычно лучше ограничивают область поиска.</TlDr>

## Что есть в данных

В <T id="public.orders">orders</T> 100 000 заказов. Посчитаем новые заказы начиная с 1 июня 2023 года:

```sql run expect=rows:1
select count(*) as total from orders
where status = 'new' and created_at >= '2023-06-01 00:00+03';
```

Результат содержит одну строку со значением 1696. `count(*)` возвращает счётчик в одной строке, а не 1696 строк результата. Если убрать условие по статусу:

```sql run expect=rows:1
select count(*) as total from orders
where created_at >= '2023-06-01 00:00+03';
```

В одной строке результата теперь 56 513: в это число входят заказы всех статусов. Числа относятся к исходному учебному набору.

## Порядок ключей

Создадим B-tree по статусу и времени:

```sql apply expect=rows:0
create index orders_status_created_idx on orders (status, created_at);
```

Нажми «Применить»: индекс сохранится в учебной базе. Он не меняет число заказов и занимает дополнительное место. «Сброс» вернёт исходный набор.

В индексе записи упорядочены сначала по <C id="public.orders.status">status</C>, а внутри каждого статуса по <C id="public.orders.created_at">created_at</C>. Условие равенства по статусу и диапазон по времени позволяют ограничить область поиска. Посмотрим фактический план:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
select order_id from orders
where status = 'new' and created_at >= '2023-06-01 00:00+03';
```

Открой полное значение JSON в результате. В учебном наборе план обычно содержит `Bitmap Index Scan` с обоими условиями в `Index Cond`, затем чтение таблицы. Вернулось 1696 заказов; выбранный план зависит от статистики и может отличаться.

<Callout kind="analogy">
В каталоге посылки отсортированы по городу, затем по дате отправки. Для одного города можно сразу перейти к нужному диапазону дат. Чтобы найти дату во всех городах, приходится учитывать несколько отдельных групп.
</Callout>

## Если первой колонки нет в условии

Проверим план поиска только по времени:

{/* final-only: EXPLAIN возвращает план, но не анимируется как SELECT */}
```sql run expect=rows:1 trace=final-only
explain (analyze, format json)
select order_id from orders where created_at >= '2023-06-01 00:00+03';
```

Обычно здесь выбирается `Seq Scan`: условию соответствует больше половины таблицы. Это решение планировщика для данного набора, а не запрет использовать индекс без первой колонки.

В PostgreSQL 18 B-tree может использовать **skip scan**: выполнить несколько поисков по значениям пропущенной ведущей колонки. Это бывает выгодно, когда разных значений немного и можно пропустить значительную часть индекса. Проверяй план для своих данных, а не считай, что отсутствие первого условия всегда исключает индекс.

## Индекс и сортировка

Порядок ключей может помочь и с `ORDER BY`:

```sql run expect=rows:10
select status, created_at from orders order by status, created_at limit 10;
```

Вернулось десять строк. Открой вкладку «План»: индекс в подходящем порядке может избавить запрос от отдельного узла `Sort`. План зависит от условий, направления сортировки и оценок планировщика; сам `ORDER BY` по-прежнему нужен, чтобы запрос требовал нужный порядок.

## Один составной или два отдельных

Составной индекс подходит для повторяющихся сочетаний условий и нужного порядка. Отдельные индексы могут быть полезны, если часто ищут по каждой колонке независимо. PostgreSQL иногда объединяет их через bitmap, но при этом порядок индексов теряется и для `ORDER BY` может понадобиться сортировка. Сравни планы и стоимость поддержки индексов на реальной нагрузке.

## Чего нет в выдаче и почему

- ❌ 1696 строк в результате `count(*)`: это значение счётчика в одной строке.
- ❌ Заказов до указанной даты в обоих подсчётах: их исключает условие по времени.
- ❌ Гарантии выбранного плана: индекс даёт планировщику вариант, но не заставляет его использовать.

## Ловушки

<Callout kind="trap">
Для B-tree равенство по ведущим колонкам и диапазон по следующей обычно ограничивают область чтения. Условия правее диапазона могут проверяться в индексе, но не обязательно сокращают его сканируемую часть.
</Callout>

<Callout kind="tip">
Выбирай порядок колонок под частые запросы и сортировки. Проверяй `EXPLAIN ANALYZE` после изменений и учитывай место и дополнительную работу при записи.
</Callout>

## Проверь себя

1. Почему первый `count(*)` показывает одну строку со значением 1696?
2. Как порядок `(status, created_at)` помогает поиску по статусу и диапазону времени?
3. Почему поиск только по времени не доказывает, что составной индекс никогда не используется?

<Cheatsheet>
- B-tree упорядочивает составной ключ слева направо.
- Равенство по ведущим колонкам и диапазон по следующей ограничивают область поиска.
- Skip scan может помочь без условия по первой колонке, если планировщик сочтёт его выгодным.
- Индекс может помочь сортировке; `ORDER BY` задаёт требуемый порядок результата.
</Cheatsheet>
