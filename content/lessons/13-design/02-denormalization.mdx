<TlDr>Денормализация хранит вычислимые данные отдельно ради определённой выгоды. Вместе с копией появляется задача поддерживать её согласованность с источником.</TlDr>

## Что есть в данных

В <T id="public.book">book</T> 11 книг, а <T id="public.order_item">order_item</T> хранит позиции заказов. Посчитаем для каждой книги число позиций и оставим книги, встречающиеся хотя бы в двух:

```sql run expect=rows:5
select b.title, count(oi.book_id) as order_lines
from book b left join order_item oi on oi.book_id = b.book_id
group by b.book_id, b.title
having count(oi.book_id) >= 2
order by b.book_id;
```

В результате пять книг. `count(oi.book_id)` считает строки позиций, а не число экземпляров: количество экземпляров записано в `qty` и может быть больше одного. Книга без позиций получает счётчик 0 благодаря `LEFT JOIN`.

## Сохраняем копию счётчика

Добавим в книгу обычную колонку для сохранённого числа позиций:

```sql apply expect=rows:0
alter table book add column order_line_count int not null default 0;
```

Нажми «Применить». Теперь заполним колонку подсчётом из `order_item`:

```sql apply expect=rows:11
update book set order_line_count =
  (select count(*) from order_item oi where oi.book_id = book.book_id);
```

Обновились 11 строк. Повторим выборку через сохранённую колонку:

```sql run expect=rows:5
select title, order_line_count from book where order_line_count >= 2 order by book_id;
```

Снова получили те же пять книг. Значение в `book` дублирует вычислимый факт из `order_item`. Сохранённый счётчик может удешевить частое чтение, но реальную пользу нужно измерять вместе с затратами на запись и поддержание данных.

<Callout kind="analogy">
У библиотеки может быть список выдач и отдельный счётчик выдач каждой книги. Счётчик удобен для быстрого просмотра, но при новой выдаче его нужно обновить вместе со списком.
</Callout>

## Как появляется рассинхрон

Сравним сохранённый и актуальный подсчёт для книги 7, «Остров погибших кораблей»:

```sql run expect=rows:1
select b.title, b.order_line_count, count(oi.book_id) as actual_lines
from book b left join order_item oi on oi.book_id = b.book_id
where b.book_id = 7
group by b.book_id, b.title, b.order_line_count;
```

Оба числа равны 0: этой книги ещё нет в позициях заказов. Добавим её в заказ 1 с учебной ценой позиции 100:

```sql apply expect=rows:1
insert into order_item (order_id, book_id, qty, price) values (1, 7, 1, 100) returning book_id;
```

Применение добавляет одну позицию. Цена позиции здесь задана для опыта; цена в карточке книги может отсутствовать и сама по себе не подставляется в заказ. Сравним счётчики ещё раз:

```sql run expect=rows:1
select b.title, b.order_line_count, count(oi.book_id) as actual_lines
from book b left join order_item oi on oi.book_id = b.book_id
where b.book_id = 7
group by b.book_id, b.title, b.order_line_count;
```

Теперь `actual_lines` равен 1, а сохранённый `order_line_count` остался 0. Обычная колонка не узнаёт об изменении другой таблицы сама. Вернём согласованность для этой книги:

```sql apply expect=rows:1
update book set order_line_count =
  (select count(*) from order_item oi where oi.book_id = book.book_id)
where book_id = 7;
```

Проверим:

```sql run expect=rows:1
select b.title, b.order_line_count, count(oi.book_id) as actual_lines
from book b left join order_item oi on oi.book_id = b.book_id
where b.book_id = 7
group by b.book_id, b.title, b.order_line_count;
```

Оба значения снова равны 1. Ручной пересчёт устранил рассогласование в примере, но не решает автоматически обновления, удаления и одновременные изменения в рабочей системе. «Сброс» вернёт исходный учебный набор.

## Как поддерживать результат

Генерируемая колонка подходит для выражения из данных той же строки, но не может считать строки другой таблицы через подзапрос. Материализованное представление сохраняет результат запроса и обновляется через `REFRESH`; между обновлениями данные могут устареть. Триггер может обновлять счётчик при изменении позиций, но его нужно спроектировать для всех нужных операций и конкурентной работы.

Денормализация бывает полезна для часто читаемых отчётов или рассчитанных заранее итогов, если допустимая задержка обновления и стоимость поддержки понятны. Начинай с измерений и явно определяй источник данных и способ восстановления счётчика.

## Чего нет в выдаче и почему

- ❌ Числа проданных экземпляров в `order_line_count`: это число строк позиций, независимо от `qty`.
- ❌ Автоматического изменения обычного счётчика при вставке позиции: мы не задали механизм синхронизации.
- ❌ Гарантии, что хранение копии ускорит систему: это зависит от нагрузки и стоимости поддержки.

## Ловушки

<Callout kind="trap">
Сохранённый итог может устареть после `INSERT`, `UPDATE` или `DELETE` в исходной таблице. Механизм обновления должен учитывать все способы изменения данных и одновременную работу транзакций.
</Callout>

<Callout kind="tip">
Сначала измерь запросы и согласуй допустимое устаревание. Для копии определи источник истины, способ пересчёта и проверку расхождений.
</Callout>

## Проверь себя

1. Почему число позиций заказа не всегда равно числу экземпляров книги?
2. Почему после вставки новой позиции два счётчика показали разные значения?
3. Чем ручной пересчёт отличается от обновления материализованного представления или триггера?

<Cheatsheet>
- Избыточность может ускорить чтение, но создаёт дополнительную стоимость и риск рассогласования.
- Обычная колонка не обновляется автоматически при изменении другой таблицы.
- Материализованное представление обновляется отдельно; триггер требует корректной логики для всех изменений.
- Сверяй сохранённые итоги с источником и проверяй поведение при конкурентной записи.
</Cheatsheet>
