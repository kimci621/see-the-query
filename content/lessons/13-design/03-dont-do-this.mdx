<TlDr>Проверяй смысл `NULL`, границы временных интервалов, типы и зависимости объектов. Многие опасные конструкции допустимы, но требуют понимания их поведения.</TlDr>

## Что есть в данных

В <T id="public.author">author</T> есть автор без книг. В <T id="public.book">book</T> две книги с неизвестным `author_id`. В <T id="public.orders">orders</T> время заказа хранится с учётом часового пояса. На этих данных проверим несколько типичных ошибок.

## NOT IN и NULL справа

Попробуем найти авторов без книг:

```sql run expect=rows:0
select name from author where author_id not in (select author_id from book);
```

Получилось 0 строк, хотя автор без книг есть. Подзапрос содержит `NULL`: для автора без совпадения сравнение с неизвестным значением не даёт `true`, поэтому `WHERE` исключает строку. Исключим `NULL` из подзапроса:

```sql run expect=rows:1
select name from author
where author_id not in (select author_id from book where author_id is not null);
```

Теперь видим Бориса Пастернака. Здесь `author.author_id` - первичный ключ и не бывает `NULL`. Другой способ проверить отсутствие связанной строки:

```sql run expect=rows:1
select a.name from author a
where not exists (select 1 from book b where b.author_id = a.author_id);
```

Снова одна строка с Борисом Пастернаком. `NOT EXISTS` проверяет отсутствие совпавших строк, а не отсутствие значения в списке с неизвестными элементами.

<DontDoThis href="https://wiki.postgresql.org/wiki/Don't_Do_This#Don't_use_NOT_IN">
Не заменяй `NOT IN` на `NOT EXISTS` механически: сначала определи, что делать с `NULL` с обеих сторон сравнения. У этих конструкций разные результаты для неизвестного значения.
</DontDoThis>

## NULL слева тоже важен

Проверим книги без совпадающего автора, используя список авторов без `NULL`:

```sql run expect=rows:0
select title from book where author_id not in (select author_id from author);
```

Результат снова пуст. У двух книг собственный `author_id` равен `NULL`, а сравнение неизвестного значения не становится `true` даже при отсутствии `NULL` в подзапросе. Проверим отсутствие связанной строки:

```sql run expect=rows:2
select b.title from book b
where not exists (select 1 from author a where a.author_id = b.author_id)
order by b.book_id;
```

Получились «Простой Python» и «Изучаем Python». У них не указан автор; это не доказывает, что у книги нет автора в реальном мире. Если неизвестные значения не должны попадать в результат, добавь явное условие `b.author_id is not null`.

<Callout kind="analogy">
Если номер на карточке неизвестен, нельзя уверенно сказать, что он не совпадает ни с одним номером в списке. Проверка наличия связанной карточки отвечает на другой вопрос: удалось ли найти совпадающую запись по указанному номеру.
</Callout>

## Границы времени

`BETWEEN` включает обе границы. Сравним два условия на ровно полночь 1 апреля:

```sql run expect=rows:1
select timestamp '2024-04-01 00:00' between timestamp '2024-03-01 00:00' and timestamp '2024-04-01 00:00' as included_between,
       timestamp '2024-04-01 00:00' >= timestamp '2024-03-01 00:00'
       and timestamp '2024-04-01 00:00' < timestamp '2024-04-01 00:00' as included_half_open;
```

В одной строке первое значение `true`, второе `false`. Для соседних месяцев удобен полуоткрытый интервал: начало включено, начало следующего месяца исключено. Посчитаем мартовские заказы по московскому смещению:

```sql run expect=rows:1
select count(*) as total from orders
where created_at >= '2024-03-01 00:00+03' and created_at < '2024-04-01 00:00+03';
```

В одной строке счётчика 3. Для моментов времени используй подходящий тип, обычно `timestamptz`: он представляет момент и отображается в часовом поясе сеанса. Исходное имя часового пояса он не хранит. `timestamp without time zone` подходит для локального времени без привязки к моменту, если такая модель действительно нужна.

## Текст и имена

`char(n)` дополняет короткие значения пробелами. Посмотрим длину строки и число байт для ASCII-символа:

```sql run expect=rows:1
select length('a'::char(4)) as characters, octet_length('a'::char(4)) as bytes;
```

Одна строка показывает 1 и 4: пробелы дополнения по-разному учитываются этими функциями. Для обычного текста часто достаточно `text`; если длина или формат являются правилом данных, задай подходящее ограничение.

Имена без двойных кавычек PostgreSQL приводит к нижнему регистру. Имя, созданное как `"OrderLine"`, придётся писать в точности с кавычками и регистром. Имена в нижнем регистре с подчёркиваниями обычно проще использовать в SQL и инструментах.

## Лишние данные и зависимости

`SELECT *` полезен для исследования, но в стабильном запросе часто лучше перечислить нужные колонки: так понятен контракт результата и не передаются лишние значения. Это не обещает пропорционального сокращения чтения страниц. Аналогично не создавай индекс на каждое поле автоматически: проверь планы и стоимость поддержки индексов при записи.

`DROP TABLE ... CASCADE` может удалить зависящие объекты или ограничения. Перед удалением изучи зависимости и последствия; `RESTRICT` по умолчанию помогает увидеть препятствие, а не убирает его автоматически.

## Чего нет в выдаче и почему

- ❌ Автора без книг в первом `NOT IN`: справа есть `NULL`, и условие для него неизвестно.
- ❌ Книг с неизвестным автором в `NOT IN` даже после исключения `NULL` справа: `NULL` остаётся слева.
- ❌ Момента 1 апреля в полуоткрытом мартовском интервале: верхняя граница исключена.

## Ловушки

<Callout kind="trap">
`NOT EXISTS` и `NOT IN` могут давать разные ответы при `NULL`. Выбирай конструкцию по нужной семантике, а не только по внешнему виду запроса.
</Callout>

<Callout kind="tip">
Проверяй условия на граничных значениях и `NULL`, а перед изменением схемы изучай зависимости. Документация описывает и причины рекомендаций, и случаи, когда исключение оправдано.
</Callout>

## Проверь себя

1. Почему первый запрос с `NOT IN` не вернул автора без книг?
2. Что изменится в примере с книгами, если исключить `NULL` только справа?
3. Почему полуоткрытый интервал удобен для соседних месяцев?

<Cheatsheet>
- `NOT IN` с `NULL` требует внимания к обеим сторонам сравнения.
- Для временных периодов часто удобно `>= начало AND < следующее_начало`.
- `timestamptz` хранит момент, а не исходное имя часового пояса.
- Перед `CASCADE` проверяй зависимости; индексы и выбираемые колонки подбирай под задачу.
</Cheatsheet>
