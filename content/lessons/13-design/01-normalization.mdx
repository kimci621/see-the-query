<TlDr>Нормализация помогает хранить независимые факты отдельно и уменьшать противоречия при изменении данных. Связи между таблицами сохраняются через ключи.</TlDr>

## Что есть в данных

В начале урока пользовательских таблиц нет. Создадим студентов с текстовым списком увлечений. Выполняй блоки по порядку и нажимай «Применить» для изменения базы; «Сброс» вернёт её в начало.

```sql apply expect=rows:0
create table student (id int primary key, name text, city text, hobbies text);
```

Добавим три строки:

```sql apply expect=rows:3
insert into student values
  (1, 'Анна', 'Москва', 'шахматы, рисование'),
  (2, 'Борис', 'Казань', 'плавание'),
  (3, 'Вера', null, 'шахматы, музыка, кино');
```

В таблице три студента. У Анны два увлечения, у Бориса одно, у Веры три. Найдём строку, где в списке встречается слово «музыка»:

```sql run expect=rows:1
select name from student where hobbies like '%музыка%';
```

Вернулась Вера. Поиск подстроки удобен для опыта, но не проверяет границы отдельных увлечений: похожий фрагмент внутри другого слова тоже подойдёт. Список в одной строке сложно проверять ограничениями и связывать с отдельными записями.

## Разделяем значения

Если увлечения нужно искать и изменять по отдельности, представим каждую связь студента и увлечения отдельной строкой. Сцена читает текущую таблицу и показывает проект разделения; сама она базу не меняет. Переключи все три шага и проследи связи по `id`:

<SplitScene source="student" keyColumn="id" extract="hobbies" target="student_hobby" parentColumn="student_id" valueColumn="hobby" />

Тот же разбор выполняет PostgreSQL: `string_to_array` делит текст по запятой, `unnest` разворачивает массив в строки, а `trim` убирает пробелы по краям:

{/* final-only: разворачивание массива не имеет пошаговой трассы */}
```sql run expect=rows:6 trace=final-only
select id, trim(unnest(string_to_array(hobbies, ','))) as hobby from student order by id;
```

Получилось шесть строк. Это демонстрация для наших данных: если значение само содержит запятую, простое разделение уже не восстановит его надёжно.

<Callout kind="analogy">
Вместо одной карточки с перечислением всех секций можно хранить отдельную карточку каждой записи на секцию. Номер студента на карточке связывает её с человеком; добавление одной записи не требует переписывать весь список.
</Callout>

## Создаём связанные таблицы

Создадим таблицу связей. Внешний ключ требует существующего студента, а составной первичный ключ не допускает повтор одной пары:

```sql apply expect=rows:0
create table student_hobby (
  student_id int references student(id),
  hobby text,
  primary key (student_id, hobby)
);
```

Перенесём шесть значений:

```sql apply expect=rows:6
insert into student_hobby (student_id, hobby)
select id, trim(unnest(string_to_array(hobbies, ','))) from student;
```

После успешного переноса в учебном примере удалим старую колонку со списком:

```sql apply expect=rows:0
alter table student drop column hobbies;
```

У `student` остались идентификатор, имя и город; в `student_hobby` шесть пар. После удаления старой колонки сцене больше неоткуда читать исходный список, поэтому она покажет подсказку. Чтобы снова пройти сцену, нажми «Сброс» и создай исходные данные заново.

Соединим таблицы по ключу:

```sql run expect=rows:6
select s.name, sh.hobby from student s
join student_hobby sh on sh.student_id = s.id
order by s.id, sh.hobby;
```

Вернулось шесть строк: по одной на каждую пару. Исходные увлечения сохранились как отдельные значения. Здесь `JOIN` показывает только студентов с увлечениями; для сохранения строк без пары нужен подходящий внешний `JOIN`.

Для показа человеку список можно собрать в запросе:

```sql run expect=rows:3
select s.name, string_agg(sh.hobby, ', ' order by sh.hobby) as hobbies
from student s join student_hobby sh on sh.student_id = s.id
group by s.id, s.name order by s.id;
```

Получились три строки. Здесь увлечения отсортированы по имени, поэтому порядок и пробелы исходного текста не обязательно сохраняются. Для наших данных сохранился набор значений, а не точная копия прежней строки.

## Нормальные формы

**Первая нормальная форма** требует рассматривать значения атрибутов как отдельные значения в выбранной модели. В нашем примере хобби нужны как самостоятельные факты, поэтому храним каждое отдельно. Атомарность зависит от того, что именно считает значением предметная область: наличие `array` или `jsonb` само по себе не решает вопрос проектирования.

**Вторая нормальная форма** добавляет требование: неключевой атрибут не должен зависеть только от части составного потенциального ключа. Например, в таблице пар `(student_id, hobby)` имя студента зависит от одного `student_id`, поэтому его место в `student`.

**Третья нормальная форма** устраняет определённые транзитивные зависимости. В простом случае с одним ключом неключевой факт не должен определяться другой неключевой колонкой: название отдела, определяемое номером отдела, разумно хранить вместе с отделом, а не повторять в каждой строке сотрудника. Проверяй зависимости по правилам своей предметной области, а не только по названиям колонок.

## Чего нет в выдаче и почему

- ❌ Отдельной строки студента без увлечений в примере с обычным `JOIN`: ему нужна совпавшая строка связи.
- ❌ Исходного порядка хобби в `string_agg`: запрос явно сортирует значения по имени.
- ❌ Старой колонки `hobbies` после `ALTER TABLE`: значения перенесены в учебную таблицу связей.

## Ловушки

<Callout kind="trap">
Разделение текста по запятой не подходит для произвольных списков с запятыми внутри значений, повторами или значимым порядком. Перед переносом данных определи формат и проверь, какие сведения должны сохраниться.
</Callout>

<Callout kind="tip">
Используй ключи и ограничения для фактов, которые должны быть согласованы. Если порядок, повтор или история изменения важны, явно представь их в модели и проверь перенос данных.
</Callout>

<Cheatsheet>
- Нормализация разделяет факты и уменьшает противоречия при изменении данных.
- Отдельные значения можно хранить строками связующей таблицы с внешним ключом.
- 2НФ рассматривает частичные зависимости от составных потенциальных ключей; 3НФ - транзитивные зависимости.
- Для переноса важно сохранить нужные значения, повторы, порядок и смысл данных.
</Cheatsheet>
