<TlDr>У каждой колонки свой тип. Несовместимые типы Postgres не сравнивает: приводи явно через `::`.</TlDr>

## Что есть в данных

<T id="public.book">book</T> уже знакома: 11 книг, 9 колонок. Особые строки те же, что в главе 4: у «Острова погибших кораблей» нет цены, у «Простого Python» нет автора. Теперь смотри не на строки, а на колонки: <C id="public.book.price">price</C> это numeric, <C id="public.book.pages">pages</C> это int, <C id="public.book.published_at">published_at</C> это date, <C id="public.book.tags">tags</C> это text[], массив строк. Тип подписан у каждой колонки на доске.

## Тип это договор

Тип колонки отвечает на два вопроса: какие значения там живут и что с ними можно делать. Цену можно сложить с числом, а название нельзя:

```sql run expect=rows:1
select title, price, pages, published_at, tags from book where book_id = 1;
```

На доске `WHERE` оставит одну строку, а `SELECT` пять колонок. У «Тихого Дона» цена 890.00 имеет тип numeric, число страниц имеет тип int, дата имеет тип date, а теги хранятся в массиве из двух строк.

А теперь попробуем сравнить текст с числом:

```sql run expectError=42883
select title from book where title = 5;
```

Postgres отвечает: `operator does not exist: text = integer`. Так он говорит: «операции сравнения текста с числом не существует». Запрос остановился до сравнения строк: у оператора нет подходящей пары типов.

<Callout kind="analogy">
Представь два ключа: один открывает дверь, другой почтовый ящик. Они могут быть похожи, но заменить один другим нельзя. Приведение меняет значение в форму, которую принимает операция.
</Callout>

## Приведение через `::`

Явное приведение записывается двойным двоеточием: `значение::тип`. То же самое длинно: `cast(значение as тип)`.

Превратим цену в текст и добавим знак рубля:

```sql run expect=rows:1
select price::text || ' ₽' as label from book where book_id = 1;
```

На шаге `SELECT` появится новая колонка `label` со значением «890.00 ₽». Сама цена в таблице останется числом: мы изменили только результат выражения.

Текст в число, чтобы считать:

```sql run expect=rows:1
select '42'::int + 1 as answer;
```

Результат `43`. Здесь таблица не нужна: Postgres считает выражение и показывает одну строку с одной колонкой.

Та же операция через стандартную запись `CAST`:

```sql run expect=rows:1
select cast('42' as integer) + 1 as answer;
```

Ответ опять `43`. Форма `CAST` работает и в других СУБД, а `::` это сокращённая запись PostgreSQL. Выбирай одну форму для запроса, чтобы её было проще читать.

Приведение не исправляет некорректные данные. Если текст не похож на число, запрос завершится ошибкой:

```sql run expectError=22P02
select 'abc'::int;
```

Ошибка `22P02 invalid_text_representation` с текстом `invalid input syntax for type integer: "abc"`. Такой текст нельзя прочитать как целое число.

## Когда Postgres приводит сам

В некоторых местах приведение происходит неявно. Например, строковый литерал с числом сравнивается с колонкой numeric без твоего участия:

```sql run expect=rows:7
select book_id, title, price from book where price > '500' order by book_id;
```

На шаге `WHERE` останутся 7 строк: литерал `'500'` Postgres сам привёл к numeric. Удобно, но полагаться на это не стоит: неявные приведения есть не для каждой пары типов, и запрос с ними читается хуже. Если тип неясен, укажи его явно: так читателю не придётся угадывать, какое сравнение выберет Postgres.

У литерала без указанного типа и у выражения типа `text` разные роли. Попробуй явно назначить строке тип `text`:

```sql run expectError=42883
select title from book where price > '500'::text;
```

Теперь у оператора слева numeric, а справа text. Подходящего сравнения нет, поэтому Postgres возвращает ошибку. Чтобы сравнивать числа, используй `500` или приведи строку к numeric.

## Приведение и диапазон

Знакомый фильтр из главы 4: обе границы заданы числами, а цена хранится как numeric:

```sql run expect=rows:4
select title, price from book where price > 500 and price < 1000 order by book_id;
```

На доске останутся 4 строки. В главе про даты увидишь тот же приём с границами типа date.

## Чего нет в выдаче и почему

- ❌ «Остров погибших кораблей» в обоих сравнениях по цене: `price` это NULL, а NULL не больше и не меньше числа. Урок 4.5 помнит.
- ❌ Книги с ценой ровно 500 или 1000: их в данных и нет, границы строгие.
- ❌ «Судьба человека», «Капитанская дочка» и «Сказка о рыбаке и рыбке»: их цены ниже 500.

## Ловушки

<Callout kind="trap">
Пустая строка это текст, а не ноль. Её тоже нельзя привести к числу:

```sql run expectError=22P02
select ''::int;
```

Если в текстовой колонке пустая строка означает отсутствие значения, сначала преврати её в `NULL`: `nullif(col, '')::int`. Другой текст, который нельзя прочитать как число, всё равно вызовет ошибку.
</Callout>

<Callout kind="tip">
Перед сравнением проверь типы обеих сторон. В этом приложении тип каждой колонки подписан на доске; в другой базе посмотри описание таблицы или `information_schema.columns`.
</Callout>

3. Приведи `pages` книги 1 к text и склей со словом «страниц»: сколько операторов приведения понадобилось?

<Cheatsheet>
- Тип колонки: какие значения и операции возможны. Несовместимое не сравнивается: `42883`.
- Явное приведение: `x::тип` или `cast(x as тип)`. Кривой текст → `22P02`.
- Числа к text приводят сами при `||`, литералы в сравнении с numeric тоже.
- Правило: сомневаешься в типе, приводи явно.
</Cheatsheet>
