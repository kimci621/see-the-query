<TlDr>Первичный ключ однозначно определяет строку. `bigint` и `uuid` решают эту задачу по-разному: выбирай по способу генерации и нуждам системы.</TlDr>

## Что есть в данных

У книг первичный ключ <C id="public.book.book_id">book_id</C> создаётся как `bigint generated always as identity`. Значения выдаёт последовательность, а ограничение `PRIMARY KEY` обеспечивает уникальность и запрещает NULL.

```sql run expect=rows:1
select book_id, pg_typeof(book_id)::text as type from book where book_id = 1;
```

У первой книги идентификатор 1 и тип `bigint`.

```sql run expect=rows:1
select count(*) as n from book;
```

В таблице 11 книг. Не считай число строк по последнему идентификатору: удаления и неудачные вставки могут оставить пропуски в последовательности.

<Callout kind="analogy">
Номер книги похож на инвентарную бирку: название или цена могут измениться, а бирка продолжит указывать на ту же запись. Сам номер не обязан описывать книгу.
</Callout>

## Что такое UUID

UUID хранит 128 бит, то есть 16 байт. В привычной записи это 32 шестнадцатеричные цифры и дефисы. Значение можно создать в базе или приложении ещё до вставки строки.

```sql run expect=rows:1
select gen_random_uuid() as u, gen_random_uuid() = gen_random_uuid() as same;
```

`gen_random_uuid()` создаёт случайный UUID версии 4. Обычно два вызова дают разные значения, поэтому `same` здесь будет false с подавляющей вероятностью. Функция случайная: при повторном запуске значения меняются, а значения на доске и в результате могут различаться.

```sql run expect=rows:1
select 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid as u,
       pg_typeof('a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid)::text as type;
```

Это конкретный UUID типа `uuid`. PostgreSQL проверяет формат и выводит значение в стандартной записи.

## Размер значения

```sql run expect=rows:1
select pg_column_size(1::bigint) as bigint_bytes,
       pg_column_size('a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid) as uuid_bytes;
```

Отдельное значение `bigint` занимает 8 байт, UUID 16. Размер таблицы и индекса зависит не только от размера значения. Индексы PostgreSQL хранятся отдельно от таблицы: первичный ключ не добавляется автоматически в каждый другой индекс.

## Как выбрать

`bigint` с последовательностью удобен, когда идентификаторы выдаёт одна база. Независимые базы могут выдать одинаковые числа, поэтому при слиянии понадобится стратегия согласования.

UUID можно создавать независимо на разных узлах. Это упрощает объединение данных, но вероятность совпадения не равна нулю: ограничение `PRIMARY KEY` всё равно нужно. UUID v4 случаен; UUID v7 включает время и обычно лучше сохраняет близость новых значений в сортировке. Точный порядок создания он не гарантирует. В PostgreSQL 18 есть встроенная функция `uuidv7()`:

```sql noexec
create table event (
  event_id uuid default uuidv7() primary key,
  payload jsonb
);
```

UUID не заменяет проверку доступа. Даже трудно угадываемый идентификатор не даёт права читать чужую запись.

## Хэш и идентификатор

```sql run expect=rows:1
select md5('a') as hash;
```

Получаем `0cc175b9c0f1b6a831c399e269772661`. Хэш вычисляется из содержимого: одинаковый ввод даст одинаковый результат, но совпадение хэшей не доказывает равенство данных. MD5 не подходит для криптографической защиты; для проверки совпадений важно учитывать риск коллизий и при необходимости сравнивать исходные данные.

## Чего нет в выдаче и почему

- ❌ Второй книги с `book_id = 1`: первичный ключ запрещает повторение.
- ❌ Количества книг в самом `book_id`: последовательность выдаёт значения, а не считает текущие строки.
- ❌ Гарантии уникальности от одной только генерации UUID: в таблице её обеспечивает ограничение.

## Ловушки

<Callout kind="trap">
`identity` сам по себе не гарантирует уникальность: последовательность можно сбросить или изменить значения. Для уникальности добавь `PRIMARY KEY` или `UNIQUE`.
</Callout>

```sql run expectError=22P02
select 'не-uuid'::uuid;
```

Неверная запись UUID вызывает ошибку `22P02`.

<Callout kind="tip">
Ключ выбирают по требованиям к неизменности, генерации и размеру данных. Естественный ключ тоже подходит, если он стабилен, уникален и всегда заполнен; суррогатный помогает отделить идентификатор от меняющихся свойств.
</Callout>

## Проверь себя

1. Почему максимальный `book_id` не обязан совпадать с количеством книг?
2. Что даёт `PRIMARY KEY` сверх генерации значения?
3. Почему два независимых источника могут выбрать UUID, а не собственные последовательности?

<Cheatsheet>
- `PRIMARY KEY` требует уникальное значение без NULL.
- `bigint` занимает 8 байт, `uuid` хранит 128 бит, или 16 байт.
- `gen_random_uuid()` генерирует UUID v4; в PostgreSQL 18 доступен `uuidv7()`.
- Последовательность может иметь пропуски, а генерация UUID не отменяет ограничение уникальности.
- Хэш содержимого и идентификатор строки решают разные задачи.
</Cheatsheet>
