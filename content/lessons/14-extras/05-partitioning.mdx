<TlDr>Секционированная таблица объединяет физические секции. PostgreSQL направляет строку в секцию по ключу.</TlDr>

## Что есть в данных

Начнём с пустой базы. Создадим таблицу измерений и две секции по месяцам. Затем вставим строки в родительскую таблицу и проверим, где они оказались.

## Родитель и секции

**Секционирование** делит одну логическую таблицу на секции, в которых хранятся строки. Создадим родителя с ключом `logdate` и правилом `RANGE`:

```sql apply expect=rows:0
create table measurement (
  city_id integer not null,
  logdate date not null,
  peaktemp integer
) partition by range (logdate);
```

Сам родитель здесь не хранит строки. Добавим секции за май и июнь:

```sql apply expect=rows:0
create table measurement_2024_05 partition of measurement
for values from ('2024-05-01') to ('2024-06-01');
```

```sql apply expect=rows:0
create table measurement_2024_06 partition of measurement
for values from ('2024-06-01') to ('2024-07-01');
```

Нижняя граница диапазона включена, верхняя исключена. Дата 1 июня относится к июньской секции, не к майской. Диапазоны секций одного родителя не могут пересекаться.

<Callout kind="analogy">
Месячные папки архива складываются в общий раздел: запись отправляется в нужную папку по дате, а запрос к разделу может читать сразу все папки.
</Callout>

## Маршрут вставки

Посмотрим предпросмотр двух строк:

```sql run expect=rows:2
insert into measurement values
  (1, '2024-05-10', 20), (1, '2024-06-15', 25);
```

Доска показывает, как PostgreSQL направил строки в разные секции. Предпросмотр откатывается. Сохраним те же строки:

```sql apply expect=rows:2
insert into measurement values
  (1, '2024-05-10', 20), (1, '2024-06-15', 25);
```

Проверим секции через системную колонку `tableoid`:

{/* final-only: чтение секционированного родителя показывает результат без пошагового разбора */}
```sql run expect=rows:2 trace=final-only
select tableoid::regclass as section, city_id, logdate, peaktemp
from measurement order by logdate;
```

В одной строке секция `measurement_2024_05`, в другой - `measurement_2024_06`. `tableoid` указывает физическую таблицу строки; приведение к `regclass` показывает её имя.

## Нет подходящей секции

Апрель пока никуда не входит:

```sql run expectError=23514
insert into measurement values (1, '2024-04-01', 18);
```

PostgreSQL вернул ошибку `23514`: подходящей секции нет, строка не вставлена. Создадим секцию по умолчанию:

```sql apply expect=rows:0
create table measurement_default partition of measurement default;
```

Теперь вставка пройдёт:

```sql apply expect=rows:1
insert into measurement values (1, '2024-04-01', 18);
```

{/* final-only: чтение секционированного родителя показывает результат без пошагового разбора */}
```sql run expect=rows:3 trace=final-only
select tableoid::regclass as section, city_id, logdate, peaktemp
from measurement order by logdate;
```

Строк теперь три. Апрель попал в `measurement_default`, а остальные остались в своих секциях. «Сброс» удалит учебные таблицы.

## Когда это помогает

Если условие запроса позволяет исключить секции, PostgreSQL может не читать их. Это называется **отсечением секций**. Удаление или отсоединение целой старой секции также может быть удобнее массового `DELETE`, но требует планирования блокировок и хранения данных.

Кроме `RANGE`, PostgreSQL поддерживает `LIST` по заданным значениям и `HASH` по остатку хеша. Секционирование не ускоряет любой запрос автоматически: проверь планы и измерь нагрузку. Слишком большое число секций тоже создаёт накладные расходы.

## Чего нет в выдаче и почему

- ❌ Апреля до создания `DEFAULT`: дата не входила ни в один диапазон.
- ❌ Данных после одного предпросмотра: вставка в песочнице откатилась до нажатия «Применить».

## Ловушки

<Callout kind="trap">
Верхняя граница `RANGE` не входит в секцию. Если первичный или уникальный ключ задан на секционированном родителе, он должен включать все колонки ключа секционирования; выражения в ключе секционирования накладывают дополнительные ограничения.
</Callout>

<Callout kind="tip">
Выбирай ключ по реальным запросам и жизненному циклу данных. Планируй создание будущих секций и следи за `DEFAULT`: перед добавлением нового диапазона может понадобиться перенести из неё подходящие строки.
</Callout>

## Проверь себя

1. В какую секцию попадёт дата 1 июня? Проверь вставкой и запросом с `tableoid`.
2. Что случилось с апрельской строкой до создания `DEFAULT`?
3. Почему отсечение секций не гарантирует ускорения любого запроса?

<Cheatsheet>
- `PARTITION BY RANGE` задаёт ключ и способ разделения родителя.
- `FROM` включает нижнюю границу, `TO` исключает верхнюю.
- `DEFAULT` принимает значения, не подходящие другим секциям.
- `tableoid::regclass` показывает физическую таблицу строки.
</Cheatsheet>
