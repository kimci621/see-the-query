<TlDr>`WITH` даёт имя промежуточному результату. Сначала описываешь его, потом используешь в основном запросе как обычную таблицу.</TlDr>

## Что есть в данных

В <T id="public.orders">orders</T> 8 заказов. Если смотреть по <C id="public.orders.created_at">created_at</C>, с 1 мая 2024 года сделано два: заказ 7 со статусом paid и заказ 8 со статусом new. Заказ 7 создан в 00:10 по Москве, поэтому граница `>= '2024-05-01'` его берёт. В песочнице часовой пояс UTC+3.

## Имя для промежуточного результата

```sql run expect=rows:2
with recent as (
  select * from orders where created_at >= '2024-05-01'
)
select order_id, status from recent order by order_id;
```

2 строки: 7 и 8. Без `WITH` пришлось бы повторить условие в каждом месте или завернуть его в подзапрос `FROM`. С `WITH` условие живёт в одном месте и у него есть имя `recent`.

На доске над <T id="public.orders">orders</T> появляется пунктирная таблица `recent` с двумя строками. Это не настоящая таблица в базе, а результат, который существует только на время запроса. Дальше основной `SELECT` читает его как обычную таблицу.

## Второй CTE видит первый

CTE можно перечислить несколько, через запятую. Каждый следующий видит предыдущие по имени:

```sql run expect=rows:1
with recent as (
  select * from orders where created_at >= '2024-05-01'
),
paid_recent as (
  select * from recent where status = 'paid'
)
select order_id, status from paid_recent order by order_id;
```

1 строка: заказ 7. `paid_recent` читает не `orders`, а `recent`. На доске две пунктирные таблицы выстраиваются цепочкой: `orders` → `recent` (2 строки) → `paid_recent` (1 строка). Вторая таблица меньше, потому что фильтр по статусу сработал уже после первой.

Порядок важен: `recent` не может сослаться на `paid_recent`, который объявлен ниже. Имя видно только вперёд.

## CTE и группировка

С CTE удобно разбить запрос на шаги. Сначала оставить нужные заказы, потом посчитать статусы:

```sql run expect=rows:2
with recent as (
  select * from orders where created_at >= '2024-05-01'
),
by_status as (
  select status, count(*) as cnt from recent group by status
)
select status, cnt from by_status order by status;
```

2 строки: new с 1 заказом и paid с 1. На доске `recent` сворачивается в две строки, `by_status` в две строки со счётчиками, основной `SELECT` только переставляет колонки. Если бы заказов с мая была тысяча, этот же запрос читался бы так же: сначала сузить, потом считать.

## Один раз описан

С точки зрения запроса `recent` описан один раз. Исправишь условие в одном месте, и его увидят все ссылки. В трассировщике CTE материализуется один раз: на доске появляется отдельная таблица с результатом.

В PostgreSQL 12+ нерекурсивный CTE без побочных эффектов планировщик может встроить в основной запрос, если ссылка на него одна. Тогда отдельной таблицы в плане нет, а условие как будто оказалось внутри основного `SELECT`. Если ссылок несколько, по умолчанию CTE считается один раз. Как этим управлять явно, разберём в 8.8.

## Ловушки

<Callout kind="trap">
`WITH` живёт только внутри одного оператора. Следующий блок начинается с чистого листа:

```sql run expectError=42P01
select * from recent;
```

Код `42P01`, `relation "recent" does not exist`. Это не ошибка в имени, а граница жизни CTE: он объявлен в предыдущем запросе и вместе с ним закончился. На верхнем уровне оператора `WITH` один, но CTE внутри него можно перечислять через запятую.
</Callout>

<Callout kind="note">
Если назвать CTE так же, как таблицу, внутри основного запроса это имя будет означать CTE, а не таблицу. Внутри тела CTE имя ещё означает настоящую таблицу. Старайся не повторять имена таблиц без нужды.
</Callout>

## Чего нет в выдаче и почему

- ❌ Заказы 1-6 в `recent`: они созданы до 1 мая.
- ❌ Заказ 8 в `paid_recent`: его статус new, а не paid.
- ❌ Остальные шесть заказов в `by_status`: они не попали в `recent`.
- ❌ `recent` в следующем операторе: CTE существует только внутри своего запроса.
- ❌ Отдельная строка для заказа 7 в `by_status`: он свернулся в группу paid.

<Cheatsheet>
- `with имя as (select ...) select ...`
- CTE объявляется до основного запроса и живёт один оператор.
- Несколько CTE разделяются запятой; следующий видит предыдущие.
- CTE можно использовать в `FROM` и `JOIN`, а его колонки в `WHERE`, `GROUP BY` и `ORDER BY`.
- Один раз описан: условие правится в одном месте.
- В PostgreSQL 12+ простой CTE может встроиться в основной запрос; `MATERIALIZED` в 8.8 фиксирует отдельный расчёт.
</Cheatsheet>
