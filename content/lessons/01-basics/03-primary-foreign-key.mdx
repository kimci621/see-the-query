<TlDr>Первичный ключ отличает одну строку таблицы от другой. Внешний ключ проверяет ссылку между строками.</TlDr>

## Что есть в данных

На доске <T id="public.author">author</T> с 6 авторами и <T id="public.book">book</T> с 11 книгами. У Шолохова две книги. У «Изучаем Python» и «Простого Python» автор не указан. У Бориса Пастернака книг в этом наборе нет.

В начальном запросе уже стоят обе таблицы. Чуть позже разберём, как они соединяются; сейчас посмотри на значки ключей и линию между таблицами.

## Как отличить одну строку от другой

У автора есть имя, но два человека могут носить одинаковые имена. Поэтому в <T id="public.author">author</T> есть отдельный номер <C id="public.author.author_id">author.author_id</C>:

```sql run expect=rows:6
select author_id, name from author order by author_id;
```

Получилось 6 строк. У Михаила Шолохова номер 1, у Лусиану Рамальо номер 2, у Бориса Пастернака номер 6. На доске у `author_id` нарисован ключ.

Это **первичный ключ** (`PRIMARY KEY`). Postgres требует, чтобы его значение отличалось у каждой строки и не было `NULL`. Значения ключа помогают указать на конкретную строку, даже если имена авторов совпадают.

Первичный ключ может состоять из нескольких колонок. Тогда уникальным должно быть их сочетание. В <T id="public.author">author</T> ключ состоит из одной: `author_id`. У <T id="public.book">book</T> свой первичный ключ <C id="public.book.book_id">book.book_id</C>; он отличает книги друг от друга.

## Как книга находит автора

В таблице книг есть ещё одна колонка, тоже с именем `author_id`. Выберем две книги:

```sql run expect=rows:2
select book_id, title, author_id
from book
where book_id in (1, 3)
order by book_id;
```

В результате «Тихий Дон» и «Судьба человека». У книг разные `book_id`, но в обеих строках `author_id = 1`. Номер 1 здесь указывает на автора, а не на книгу.

<C id="public.book.author_id">book.author_id</C> это **внешний ключ** (`FOREIGN KEY`), который ссылается на <C id="public.author.author_id">author.author_id</C>. Чтобы увидеть обе колонки, нажми на доску, затем Esc и кнопку «Вписать доску». Наведи на подчёркнутый `book.author_id` в начале абзаца: обе колонки подсветятся. Между таблицами проведена линия связи.

Проверим, чья это единица:

```sql run expect=rows:1
select author_id, name from author where author_id = 1;
```

Одна строка: Михаил Шолохов. Сначала значение 1 нашли в двух строках книг, теперь нашли строку автора с тем же номером.

<Callout kind="analogy">
У каждого гардеробного жетона свой номер. На нескольких вещах одного посетителя может стоять номер его жетона: по нему вещи относят к одному владельцу. В базе номер автора работает похоже, но за совпадением следит ограничение внешнего ключа.
</Callout>

## Покажем имя рядом с книгой

Имя лежит в `author`, название в `book`. `JOIN` соединяет строки по совпавшему `author_id`:

```sql run expect=rows:3
select a.name, b.title
from author a join book b using (author_id)
order by b.book_id
limit 3;
```

В первых трёх строках Шолохов встречается дважды: рядом с «Тихим Доном» и «Судьбой человека». Между ними книга Лусиану Рамальо. На доске линии соединяют пары строк, а строка автора с номером 1 получает две пары. Подробно про `JOIN` поговорим в главе 6.

## Можно ли оставить ссылку пустой

Внешний ключ не обязательно заполнен. Если колонка допускает `NULL`, значение можно не указывать. В <T id="public.book">book</T> так устроен `author_id`:

```sql run expect=rows:2
select title from book where author_id is null order by title;
```

Две строки: «Изучаем Python» и «Простой Python». На шаге `WHERE` остальные 9 книг уходят из призрака. `NULL` здесь означает, что номер автора не указан; его не ищут среди номеров в `author`.

## Чего нет в выдаче и почему

- «Изучаем Python» и «Простой Python» не попали в результат `JOIN`: у них нет номера для пары с автором.
- Борис Пастернак не появился в результате `JOIN`: в этом наборе нет книги с `author_id = 6`.
- «Тихий Дон» не попал в список книг без автора: в его `author_id` стоит 1, а не `NULL`.

## Ловушки

<Callout kind="trap">
Пустая ссылка и ссылка на несуществующий номер дают разные результаты. Попробуем указать автора 99, которого нет в <T id="public.author">author</T>:

```sql run expectError=23503
insert into book (title, author_id) values ('Новая книга', 99);
```

Postgres возвращает `23503`: внешний ключ `book_author_id_fkey` не нашёл автора с номером 99. На сцене видна попытка вставки и красная стрелка к таблице авторов. Строка в базовую таблицу не добавилась: запрос закончился ошибкой, а превью в любом случае откатывает изменения.

Внешний ключ может быть пустым, если колонка допускает `NULL`. Но указанное значение должно найтись в связанном ключе. Здесь это первичный ключ автора; в других таблицах ссылка может вести и на подходящий уникальный ключ.
</Callout>

А если повторить первичный ключ автора? Для этого примера передадим номер вручную: `OVERRIDING SYSTEM VALUE` разрешает указать значение для нашей identity-колонки.

```sql run expectError=23505
insert into author (author_id, name)
overriding system value
values (1, 'Другой автор');
```

Ошибка `23505`: номер 1 уже занят. Даже если имя другое, второй автор с тем же первичным ключом не появится. Доска показывает попытку вставки и существующую строку, с которой возник конфликт.

<Cheatsheet>
- `PRIMARY KEY` отличает строки таблицы: значения ключа уникальны и не равны `NULL`.
- `book.book_id` идентифицирует книгу; `book.author_id` связывает её с автором.
- Внешний ключ проверяет указанную ссылку. Если колонка допускает `NULL`, ссылку можно оставить пустой.
- `JOIN` соединяет строки по условию; `INNER JOIN` оставляет только найденные пары.
- Нет автора с таким номером: ошибка `23503`. Повтор первичного ключа: `23505`.
</Cheatsheet>
