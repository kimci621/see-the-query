# Visual SQL: визуальный тьютор по PostgreSQL

Дизайн-спека. Дата: 2026-10-08. Статус: черновик на ревью.

---

## 0. Суть одной фразой

Веб-приложение, где слева темы, по центру теория, справа miro-подобная доска с таблицами. Доской управляет SQL: пишешь запрос, и в реальном времени видишь, как Postgres его выполняет. Таблицы съезжаются при JOIN, строки отваливаются на WHERE, колонки исчезают на SELECT, строки сбиваются в кучки на GROUP BY.

## 1. Понимание задачи

### Что сказал заказчик

- Цель: «грокнуть» PostgreSQL через визуал, а не через текст и голую таблицу результата.
- Покрыть ~99% рутины junior/middle/senior: схемы, таблицы, ограничения, DML, выборки, фильтрация, сортировка, соединения нескольких таблиц, агрегация, подзапросы, CTE, окна, транзакции, индексы.
- Формат: теория + живой визуализатор. Это не «теория + задачи». Задачи-головоломки появятся позже, после всех глав.
- Визуализатор меняется на каждое изменение SQL в реальном времени.
- Видно таблицы, ячейки, строки, колонки, схему и слияния.
- JOIN показываем буквально: две таблицы сближаются и сливаются в одну.
- `select * from table_x` фокусирует камеру на таблице и подсвечивает все её поля.
- Оптимизация: общую доску анимации не трогают никогда. Анимация идёт на отдельном слое поверх доски («доска на доске»).
- MVP: на доске только перемещение и зум. Клики по доске будут позже.
- Интерфейс: слева темы, по центру теория, справа доска.
- UI на shadcn/ui.
- Контент: официальная документация PostgreSQL, PG wiki «Don't Do This», полезные ссылки, курс «Диджитализируй!» (темы 11 и 12) как эталон стиля объяснения.

### Решения из уточнений

- Аудитория: сначала для себя, потом публично. Поэтому теорию пишем своими словами в стиле курса. Курс платный, тексты из него не копируем, он служит референсом по структуре, глубине и тону. Аккаунтов нет, прогресс хранится в localStorage.
- Движок SQL: PGlite (настоящий PostgreSQL, скомпилированный в WASM) в браузере, в Web Worker. Бэкенд не нужен.
- MVP: вертикальный срез. Весь движок плюс 13 ключевых уроков, дальше наращиваем уроки по готовым рельсам.

### Допущения (поправь, если не так)

- Язык интерфейса и теории: русский. Ключевые слова SQL и идентификаторы на английском.
- Десктоп-first (ширина от 1280px). На планшете можно смотреть, мобильная версия не цель.
- Одна вкладка браузера = одна песочница БД. Всё живёт локально, сервер только раздаёт статику.
- Таблицы в учебных датасетах маленькие (5-15 строк), чтобы каждую строку было видно глазами. Большие объёмы нужны только в главе про индексы, там доска показывает сжатый вид.

### Критерии успеха

1. Пишешь `select * from book` → через <300 мс после паузы в наборе камера фокусируется на `book`, колонки подсвечены, внизу результат.
2. Пишешь `... join author a on ...` → на оверлее две таблицы съезжаются, совпавшие строки соединяются линиями и сливаются, несовпавшие отваливаются (INNER) или остаются с NULL-ячейками (LEFT).
3. Анимация каждого шага совпадает с реальным результатом Postgres. Если визуализатор не уверен в шаге, он честно показывает только итог (см. принцип «Честность»).
4. Доска с 30 таблицами панорамируется и зумится на 60 fps, пока на оверлее идёт анимация.
5. Новичок проходит урок по JOIN и может объяснить, почему «Простой Python» пропал из INNER JOIN, но остался в LEFT JOIN.

## 2. Продуктовые принципы

1. **Визуал первичен.** Теория объясняет, доска показывает. Каждое понятие урока должно иметь видимое проявление на доске.
2. **Настоящий Postgres.** Все результаты, ошибки и тексты ошибок берутся от реального PostgreSQL (PGlite). Свой интерпретатор SQL не пишем.
3. **Честность.** Анимация никогда не врёт. Финальная стадия трассировки сверяется с реальным результатом запроса. При расхождении или при неподдерживаемой конструкции включается режим «только итог»: подсвечиваем задействованные таблицы и показываем результат без пошаговой анимации, а пользователь видит пометку «пошаговый разбор для этой конструкции пока не умею».
4. **Живость.** Реакция на ввод без кнопки «Run». Пока пишешь, работает превью. Изменить данные можно только явным действием «Применить».
5. **Доска неприкосновенна.** Базовая доска не анимируется и не перерисовывается во время сцен. Все движения идут на оверлее.
6. **Логический порядок, а не порядок записи.** Шаги показываются в порядке выполнения: FROM → JOIN → WHERE → GROUP BY → HAVING → окна → SELECT → DISTINCT → ORDER BY → LIMIT. Это главная ментальная модель, которую должен унести ученик.
7. **Числа как якоря.** Как в курсе («Вернулось 9 строк. Запомни это число»): каждый шаг подписан счётчиком «было 10 → осталось 6».

- Правая колонка делится по вертикали (тоже Resizable): доска / таймлайн / редактор / результат.

### 3.2 Левая колонка: темы

- shadcn `Sidebar` (collapsible="icon") + `Collapsible` для глав.
- Статус урока: ○ не открыт, ● открыт, ✓ пройден (дочитал до конца и выполнил хотя бы один пример на доске).
- Внизу прогресс-бар по всей программе.
- Поиск по урокам: `⌘K` открывает shadcn `Command` с поиском по названиям, ключевым словам SQL и тегам («NULL», «ON CONFLICT»).

### 3.3 Центр: теория

- MDX-урок в `ScrollArea`, типографика prose (Tailwind Typography).
- Структура урока по шаблону (см. 6.1): tl;dr → подготовка данных → основная часть → ловушки → «Don't Do This» → шпаргалка → ссылки на доку.
- Каждый SQL-блок в теории: подсветка + кнопки `▶ На доску` (подставить в редактор и проиграть сцену) и `⧉ Копировать`.
- Блок `<Scene>`: заранее срежиссированная последовательность запросов («сначала смотри на таблицы, теперь добавим JOIN, теперь WHERE») с кнопками «Дальше/Назад». Нужен для пошаговых объяснений.
- Ссылки на объекты в тексте (`<T>book</T>`, `<C>book.author_id</C>`) при наведении подсвечивают таблицу или колонку на доске. Мост «текст ↔ доска».
- Навигация ⟨ ⟩ между уроками, «следующий урок» внизу.

### 3.4 Правая колонка: базовая доска

- Бесконечное полотно с точечной сеткой, как в Miro. Pan (drag, трекпад, пробел+drag) и zoom (колесо, pinch, кнопки, `⌘0` fit).
- Таблица на доске (`TableNode`):
  - шапка: `схема.таблица`, бейдж числа строк;
  - список колонок: имя, тип, иконки 🔑 PK, 🔗 FK, `NN` (NOT NULL), `U` (UNIQUE), `✓` (CHECK), DEFAULT в тултипе;
  - строки данных: до 15 видны, дальше «+ ещё 37». NULL рисуется серой плашкой `NULL` (курсивом и пунктиром), чтобы его не путали с пустой строкой `''`.
- Связи FK рисуются рёбрами с «вороньей лапкой» (1:N), подпись `ON DELETE ...` в тултипе.
- Схемы (`public`, `shop`, `archive`) показываются как рамки-группы с названием. Таблицы внутри.
- Миникарта (React Flow MiniMap) по кнопке.
- Раскладка: из урока (если задана) или авто через dagre (слева направо по FK).
- MVP: перетаскивать таблицы нельзя, клики только для будущих фич. Есть только pan и zoom.
- Состояния таблицы на доске без оверлея (дёшево, только CSS-класс):
  - `focused`: камера плавно подлетает (`fitBounds`), рамка акцентного цвета;
  - `columns-highlighted`: подсветка выбранных колонок (для `select title, price from book` светятся только эти две);
  - `dimmed`: всё остальное приглушено, пока идёт сцена.

### 3.5 Оверлей-сцена («доска на доске»)

- Отдельный слой поверх полотна с той же камерой: оверлей подписан на viewport React Flow и применяет тот же `transform: translate() scale()`. При pan/zoom он двигается синхронно, но базовые ноды при этом не перерисовываются.
- Сцена начинается с «призраков»: копии задействованных таблиц появляются точно поверх оригиналов, оригиналы под ними приглушаются. Дальше двигаются только призраки.
- Рабочая зона сцены: свободная область рядом с задействованными таблицами. Камера мягко подстраивается, чтобы вся сцена была в кадре (тумблер «Камера следит» в панели).
- Сцена закрывается (`Esc` или изменение запроса на пустой): призраки растворяются, доска возвращается в обычный вид.
- Каталог анимаций по операциям описан в разделе 4.

### 3.6 Редактор SQL

- CodeMirror 6, диалект PostgreSQL, автодополнение по таблицам и колонкам текущей БД (схема берётся из каталога PGlite).
- Несколько операторов через `;`: визуализируется оператор под курсором (как в DataGrip), остальные выполняются по кнопке «Применить всё».
- Связь «редактор ↔ доска»:
  - курсор в `FROM book` → фокус на `book`;
  - курсор внутри `WHERE ...` → таймлайн прыгает на шаг WHERE;
  - наведение на идентификатор колонки → подсветка колонки на доске и в призраке.
- Ошибка парсинга во время набора: волнистое подчёркивание. Последняя валидная сцена остаётся на экране, но слегка гаснет. Никакого мигания.
- Ошибка Postgres: подчёркивание по `position` из ошибки + человеческое объяснение (см. 5.14).

### 3.7 Таймлайн-плеер

- Чипы шагов в логическом порядке: `FROM ▸ JOIN ▸ WHERE ▸ GROUP BY ▸ SELECT ▸ ORDER BY ▸ LIMIT`. Активный шаг подсвечен, клик по чипу прыгает к нему.
- Кнопки ⏮ ⏯ ⏭, скорость 0.5x / 1x / 2x, скраббер (shadcn Slider).
- Подпись шага, сгенерированная из данных: «WHERE price > 500: осталось 6 из 10 строк», «LEFT JOIN: 9 пар, 1 строка без пары получила NULL».
- Автоплей при изменении запроса: включён по умолчанию. При включённом автоплее после правки сцена проигрывается заново быстрым темпом (2x) до последнего шага.
- Клавиши (когда фокус на доске): `Space` play/pause, `←/→` шаг.

### 3.8 Панель результата

Вкладки shadcn `Tabs`:
- **Результат**: таблица (виртуализированная, моно-шрифт), счётчик строк, время выполнения.
- **Сообщения**: NOTICE, ошибки, объяснения.
- **План** (с главы про индексы): `EXPLAIN (ANALYZE, FORMAT JSON)` в виде дерева.

### 3.9 Превью и «Применить»

- **Превью** (по умолчанию, во время набора): любой оператор, включая INSERT/UPDATE/DELETE/DDL, выполняется внутри `BEGIN ... ROLLBACK`. Оверлей показывает, что *произошло бы*. База не меняется.
- **Применить** (`⌘⏎`): выполнение с COMMIT. Базовая доска обновляется: новая таблица появляется, строки меняются. Это единственный момент, когда базовая доска перерисовывается, и делается это одним коммитом состояния после окончания анимации.
- **Отменить** (`⌘Z` вне редактора): откат последнего применённого оператора (реализация в 5.4).
- **Сброс урока**: вернуть датасет урока в исходное состояние.

### 3.10 Горячие клавиши

`⌘K` поиск, `⌘⏎` применить, `⌘\` режим фокуса, `⌘0` вписать доску, `Esc` закрыть сцену, `Space` и `←/→` плеер, `⌘Z` отмена применённого. Шпаргалка по `?`.

### 3.11 Визуальный стиль

- База: shadcn (стиль new-york, цвет neutral/zinc), светлая и тёмная темы.
- Шрифты: Geist Sans для UI и теории, Geist Mono (или JetBrains Mono) для SQL и ячеек.

## 4. Визуальный язык: каталог анимаций

Каждая операция имеет одну фиксированную метафору. Ученик учит метафору один раз, дальше она везде одинаковая.

### Выборка из одной таблицы

- **FROM t**: призрак таблицы отделяется от оригинала, камера фокусируется. Это и есть ответ на «`select *` фокусирует таблицу».
- **WHERE**: по строкам пробегает «сканер» (горизонтальная линия). Строка, где условие TRUE, мигает зелёным. FALSE: строка краснеет и уезжает вниз с fade. NULL (unknown): строка становится серой с бейджем `UNKNOWN` и тоже уходит. Это визуально учит трёхзначной логике. На ячейках, участвующих в условии, на мгновение появляется вычисленное значение (`price 450 > 500 → false`).
- **SELECT (проекция)**: лишние колонки схлопываются по ширине и исчезают. Вычисляемые колонки (`price * 0.9 as sale`) «выращиваются» справа: заголовок появляется, значения в каждой строке выезжают из исходных ячеек. Алиас показывается переименованием заголовка.
- **DISTINCT**: одинаковые строки съезжаются в стопку и схлопываются в одну, на стопке счётчик `×3`.
- **DISTINCT ON**: то же, но в каждой стопке видно, какая строка победила по ORDER BY.
- **ORDER BY**: строки плавно переезжают на новые места (FLIP-анимация). Ключ сортировки подсвечен в каждой строке, NULL-ы явно уезжают в конец (или в начало при `NULLS FIRST`).
- **LIMIT / OFFSET**: появляется линия-«ножницы». Строки за линией (и до OFFSET) гаснут и уходят.
- **CASE WHEN**: в новой колонке для каждой строки на мгновение показывается, какая ветка сработала (`WHEN price > 1000 → 'дорого'`).

### Соединения

- **INNER JOIN**: два призрака съезжаются навстречу друг другу. Между ячейками ключей (`book.author_id` ↔ `author.author_id`) протягиваются линии для каждой совпавшей пары. Потом пары сливаются в одну широкую строку (левая часть + правая часть). Строки без пары краснеют и уходят. Если строка слева совпала с несколькими справа, она «клонируется», и это учит размножению строк при JOIN.
- **LEFT JOIN**: как INNER, но строка слева без пары не уходит. Она едет в итог, а правая половина заполняется NULL-плашками. Правые строки без пары уходят.
- **RIGHT JOIN**: зеркально LEFT.
- **FULL JOIN**: обе стороны без пар остаются, недостающие половины заполнены NULL.
- **CROSS JOIN**: каждая левая строка веером раскладывается на все правые, получается сетка N×M со счётчиком `4 × 3 = 12`.
- **SELF JOIN**: таблица «раздваивается» на две копии с разными алиасами (`e` и `m`), дальше обычный JOIN.
- **3+ таблиц**: слияния идут цепочкой: сначала первые две в одну, затем результат с третьей. Промежуточный результат каждый раз виден как отдельная таблица.
- **USING / NATURAL**: колонки-ключи двух таблиц сливаются в одну колонку (а не две одинаковые). У NATURAL дополнительно подсвечиваются все совпавшие по имени колонки как предупреждение.
- **ON vs WHERE для LEFT JOIN**: две сцены рядом. Условие в ON отсеивает пары до сохранения левых строк, условие в WHERE отсеивает строки уже после. Это классическая ловушка, и она лучше всего объясняется визуально.
- **SEMI JOIN (EXISTS / IN)**: для каждой левой строки справа вспыхивает найденное совпадение (первое), строка остаётся, но правые колонки в итог не попадают.
- **ANTI JOIN (NOT EXISTS / LEFT JOIN ... IS NULL)**: остаются только строки, у которых линия совпадения так и не протянулась. Отдельно `NOT IN` с NULL в подзапросе: всё становится UNKNOWN и итог пустой. Сцена-ловушка.
- **LATERAL**: для каждой левой строки справа выполняется мини-запрос (маленькая сцена в рамке), его результат приклеивается к строке.

### Агрегация

- **Агрегат без GROUP BY**: все строки сжимаются в одну, значение «набегает» счётчиком (`count`: 1, 2, 3...; `sum`: накапливается). `count(*)` и `count(col)` отличаются видимо: NULL-ячейки при `count(col)` не засчитываются и мигают серым.
- **GROUP BY**: строки окрашиваются в цвет своей группы и съезжаются в стопки. Каждая стопка схлопывается в одну строку с агрегатами. Колонки не из GROUP BY и не в агрегате перечёркиваются (это объясняет ошибку `must appear in the GROUP BY clause`).
- **HAVING**: как WHERE, но фильтр идёт по уже схлопнутым стопкам.
- **FILTER (WHERE ...)**: внутри стопки часть строк гаснет только для конкретного агрегата.
- **ROLLUP / CUBE / GROUPING SETS**: стопки собираются в несколько уровней, итоговые строки помечены `(всего)`.

### Подзапросы, множества, CTE

- **Скалярный подзапрос**: маленькая сцена в рамке схлопывается в одно значение, которое улетает в ячейку внешнего запроса.
- **Подзапрос в FROM / CTE**: материализуется временная таблица с пунктирной рамкой и именем CTE, дальше участвует как обычная.
- **Коррелированный подзапрос**: для каждой внешней строки по очереди запускается мини-сцена (первые 3 строки подробно, остальные быстро).
- **Рекурсивный CTE**: итерации показаны слоями. Якорь, потом шаг 1, шаг 2... пока шаг не вернёт 0 строк. Видно дерево (сотрудники → менеджеры, категории → подкатегории).
- **UNION ALL**: таблицы встают друг под другом. **UNION**: плюс схлопывание дублей как в DISTINCT. **INTERSECT**: остаются только строки, у которых нашлась пара-близнец. **EXCEPT**: из верхней вычёркиваются строки, найденные в нижней.

### Оконные функции

- **PARTITION BY**: строки окрашиваются по партициям, но не схлопываются (ключевое отличие от GROUP BY, показано явно).
- **ORDER BY в окне + frame**: по партиции едет рамка окна (`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`), значение в новой колонке считается для текущей строки.
- **row_number / rank / dense_rank**: номера проставляются по очереди, на «ничьих» видна разница между функциями.
- **lag / lead**: стрелка от соседней строки к текущей.

### Изменение данных (DML)

- **INSERT**: новая строка влетает в таблицу снизу с зелёной подсветкой. Значения DEFAULT и identity появляются с бейджем `default`. Нарушение ограничения: строка «отскакивает» с красной вспышкой. При нарушении FK к целевой таблице тянется пульсирующая красная стрелка.
- **INSERT ... SELECT**: строки результата SELECT перелетают в целевую таблицу.
- **UPDATE**: сначала WHERE (как в выборке), потом в затронутых ячейках старое значение переворачивается в новое (flip-анимация) с жёлтой подсветкой.
- **DELETE**: WHERE, потом строки перечёркиваются и уходят. При `ON DELETE CASCADE` удаление волной идёт по FK-рёбрам в зависимые таблицы.
- **RETURNING**: затронутые строки «отпечатываются» в панель результата.
- **ON CONFLICT**: строка подлетает, сталкивается с существующей по уникальному ключу, дальше либо отскакивает (`DO NOTHING`), либо обновляет существующую (`DO UPDATE`).
- **MERGE**: каждая исходная строка помечается веткой `MATCHED / NOT MATCHED` и идёт по своему пути.
- **TRUNCATE**: таблица мгновенно пустеет, без построчного сканирования (визуальный контраст с DELETE).

### Структура (DDL)

- **CREATE TABLE**: в превью таблица-черновик с пунктирной рамкой «рисуется» колонка за колонкой. После «Применить» она становится сплошной на базовой доске.
- **ALTER TABLE ADD COLUMN**: колонка выезжает справа, существующие строки получают NULL или DEFAULT.
- **DROP COLUMN**: колонка растворяется. **RENAME**: заголовок перепечатывается.
- **ADD CONSTRAINT**: иконка ограничения прилетает на колонку. Если существующие данные нарушают ограничение, конфликтные строки мигают красным, и в сообщении ошибка.
- **DROP TABLE ... CASCADE**: таблица и зависимые объекты (FK, view) гаснут волной.
- **CREATE SCHEMA**: появляется новая рамка-группа.
- **CREATE INDEX**: рядом с таблицей появляется значок индекса, в главе про индексы раскрывается в дерево.
- **CREATE VIEW**: таблица-«окно» со стеклянной рамкой, внутри запрос; при SELECT из вью видно, что под ним живые таблицы.

### Транзакции, MVCC, индексы (продвинутые сцены)

- **MVCC**: у строк показываются системные колонки `xmin`/`xmax` (они реальные, PGlite их отдаёт). UPDATE визуально создаёт новую версию строки, старая становится «мёртвой» серой, пока не придёт VACUUM.
- **Уровни изоляции и блокировки**: срежиссированные сцены «две сессии». Две колонки-таймлайна (сессия A и сессия B), шаги по времени, видно, кто что видит и кто кого ждёт. PGlite однопоточный, поэтому это сценарий с заранее заданным ходом, а не две живые сессии. Сценарий валидируется на настоящем Postgres в CI (см. 8).
- **Индексы**: B-дерево рисуется деревом. При Seq Scan сканер проходит всю таблицу, при Index Scan путь спускается по дереву и прыгает прямо к строкам. Счётчик «прочитано строк» рядом.
- **EXPLAIN**: дерево узлов плана (Seq Scan, Hash Join, Sort...), толщина рёбер пропорциональна числу строк, при наведении на узел подсвечивается соответствующий шаг на доске.

### 5.4 Слой БД

- **Worker**: PGlite живёт в Web Worker, поэтому тяжёлый запрос не морозит UI.
- **Загрузка урока**: свежая БД → выполнить датасет урока (`content/datasets/*.sql`) → сделать снапшот (`dumpDataDir`) → кэшировать снапшот в памяти по имени датасета. Повторное открытие урока = `loadDataDir` из кэша (быстро).
- **Превью**: `BEGIN; SET LOCAL statement_timeout = '2s'; ...пробы...; ROLLBACK;`.
- **Применить**: оператор выполняется с COMMIT. Он записывается в журнал применённых операторов урока, затем обновляется `BoardModel` (схема из `information_schema`/`pg_catalog` + данные таблиц).
- **Отмена**: восстановить снапшот датасета и заново применить журнал без последнего оператора. Для маленьких учебных БД это миллисекунды и проще, чем хранить снапшот на каждый шаг.
- **Сторож (watchdog)**: если запрос не вернулся за 3 с (например, `generate_series(1, 1e9)` или огромный CROSS JOIN), worker убивается, поднимается новый, БД восстанавливается из снапшота + журнала. Пользователь видит: «Запрос оказался слишком тяжёлым для песочницы».
- **Лимиты**: пробы стадий получают `LIMIT` 2000 строк. Если стадия больше, сцена идёт в сжатом режиме (см. 9).
- **Персистентность**: журнал применённых операторов по уроку хранится в localStorage, так что после перезагрузки страницы песочница восстанавливается. IndexedDB для PGlite не используем: проще воспроизвести журнал.

### 5.5 Парсер

- `parse(sql)` → список операторов с AST и диапазонами в тексте.
- `statementAt(cursor)` → оператор под курсором.
- `relationsOf(stmt)` → какие таблицы и колонки упомянуты (для фокуса и подсветки на доске даже в режиме «только итог»).
- `clauseRanges(stmt)` → диапазоны текста для FROM/WHERE/GROUP BY/... (для связи курсор ↔ стадия). AST даёт позицию начала узла, конец считаем по началу следующего клауза.

### 5.6 Трассировщик (ядро)

Задача: превратить один оператор в последовательность стадий, где у каждой строки есть **lineage**, т.е. происхождение (из каких исходных строк она получилась). Lineage нужен, чтобы анимация знала, какая строка куда едет.

**Идея**: Postgres сам считает каждую стадию. Мы не вычисляем SQL сами, мы задаём Postgres'у «подсмотренные» запросы-пробы.

**Идентичность строк**: для базовых таблиц используем системную колонку `ctid` (физический адрес строки, стабилен в рамках транзакции). Для производных отношений (подзапрос в FROM, CTE, VALUES, функции вроде `generate_series`, view) внутри той же транзакции делаем `CREATE TEMP TABLE __vs_<n> AS <подзапрос>`, переписываем ссылку на временную таблицу, и у её строк тоже появляется `ctid`. Lineage строки на стадии = кортеж ctid по каждому алиасу FROM, например `{b: '(0,3)', a: '(0,1)'}`. При LEFT JOIN ctid правой стороны равен NULL, и это прямо говорит «пары не нашлось».

**Пробы для SELECT** (логический порядок):

1. **scan(alias)**: `SELECT ctid, * FROM t` для каждого отношения в FROM.
2. **join(k)**: для левоглубокого дерева соединений проба с FROM до k-го JOIN включительно: `SELECT b.ctid, a.ctid, b.*, a.* FROM book b JOIN author a ON ...`. Отсюда берём пары, клонированные строки (одна левая с несколькими правыми) и строки без пары (сравнением со scan).
3. **where**: та же проба + исходный WHERE. Отброшенные строки = разница lineage до и после. Для подсветки «TRUE / FALSE / UNKNOWN» добавляем в пробу без WHERE колонку `(<условие>) AS __vs_pred`, она отдаёт true/false/null по каждой строке.
4. **group**: `SELECT <ключи>, array_agg(<lineage>), <агрегаты из SELECT и HAVING> FROM ... WHERE ... GROUP BY ...`. Даёт состав стопок и значения агрегатов.
5. **having**: та же проба + HAVING, плюс колонка-предикат для подсветки.
6. **window**: проба с lineage и вычисленными оконными выражениями из SELECT, плюс `PARTITION BY`-ключи для раскраски.
7. **project**: исходный target list + lineage (для группового запроса lineage = ключ группы). Отсюда видно, какие колонки остались, какие вычислились и как названы.
8. **distinct**: группировка проекции по всем выходным колонкам с `array_agg(lineage)` → стопки дублей.
9. **sort**: проекция + `row_number() OVER (ORDER BY <исходный ORDER BY>)` → новые позиции строк.
10. **limit**: применяем исходные LIMIT/OFFSET к упорядоченному списку.

Пробы, которые не нужны запросу, пропускаем (нет WHERE → нет стадии where).

**Множества (UNION/INTERSECT/EXCEPT)**: каждая ветка трассируется отдельно как свой пайплайн, затем стадия `setop` с пробой, которая добавляет к строкам метку ветки.

**CTE**: каждый CTE материализуется во временную таблицу (стадия `materialize` с собственным вложенным Trace), дальше основной запрос трассируется как обычно. **Рекурсивный CTE**: итерации считаем самостоятельно в транзакции: выполняем якорь, затем рекурсивную часть с подстановкой рабочей таблицы, пока шаг не вернёт 0 строк (с ограничением 50 итераций). Каждая итерация = слой в стадии `recursion`. Финал сверяем с настоящим `WITH RECURSIVE`.

**Подзапросы**: некоррелированный скалярный или IN-подзапрос трассируется как вложенный Trace, его результат показывается как значение или множество. Коррелированный и LATERAL: прогоняем подзапрос отдельно для первых N внешних строк с подстановкой значений (N=3 подробно), остальные строки берём из итоговой пробы.

**DML**:
- INSERT: `INSERT ... RETURNING ctid, *` в транзакции. Ошибка ограничения → стадия `error` с указанием ограничения (`constraint_name` из ошибки Postgres) и колонки.
- UPDATE/DELETE: сначала проба `SELECT ctid, <PK>, * FROM t WHERE <условие>` (какие строки затронуты, это та же визуализация WHERE), потом сам оператор с `RETURNING *`. Сопоставление «до/после» по первичному ключу. Если PK нет, показываем как удаление старой версии + вставку новой, и это честно отражает MVCC.
- Каскады: снимок всех таблиц до и после (они маленькие), diff по PK → какие строки в зависимых таблицах удалены или изменены.
- ON CONFLICT и MERGE: diff до/после плюс пробы на совпадение ключей.

**DDL**: снимок схемы из каталога до и после выполнения в транзакции → diff (таблицы, колонки, ограничения, индексы, схемы, view). Стадия `ddl` содержит этот diff.

**Сверка (принцип честности)**: в той же транзакции выполняем исходный оператор как есть и сравниваем его результат с финальной стадией трассы как мультимножества строк (а при наличии ORDER BY с учётом порядка, но только по ключам сортировки, потому что при равных ключах порядок не определён). Не совпало → `mode: 'final-only'`, в dev-сборке пишем предупреждение в консоль с запросом.

**Фолбэк «только итог»**: если в AST есть неподдерживаемый узел (список поддерживаемых ведём явно, whitelist), стадий нет. Подсвечиваем упомянутые таблицы и колонки, показываем результат и пометку.

**Недетерминированность**: `random()`, `now()`, `nextval()` вызываются в пробах заново и дают другие значения. Стадии с volatile-функциями помечаются, значения в них берутся из эталонного выполнения, а не из проб.

### 5.7 Модель данных Trace

```ts
type Lineage = Record<string, string | null>; // алиас → ctid, null = нет пары
type RowKey = string;                          // стабильный ключ из lineage, нужен для layoutId

interface Column { name: string; type: string; source?: { alias: string; column: string } }
interface Row { key: RowKey; lineage: Lineage; values: unknown[] }
interface Relation { columns: Column[]; rows: Row[] }

interface StageBase {
  id: string;
  sourceRange?: { from: number; to: number }; // кусок SQL для связи с редактором
  caption: string;                            // «WHERE: осталось 6 из 10»
  output: Relation;                            // состояние после стадии
}

type Stage = StageBase & (
  | { kind: 'scan'; alias: string; table: string }
  | { kind: 'join'; joinType: 'inner' | 'left' | 'right' | 'full' | 'cross';
      leftKeys: RowKey[]; rightKeys: RowKey[];
      pairs: Array<[RowKey | null, RowKey | null]>; onColumns: string[] }
  | { kind: 'filter'; clause: 'where' | 'having';
      verdicts: Record<RowKey, true | false | null> }
  | { kind: 'group'; keys: string[]; groups: Array<{ key: RowKey; members: RowKey[] }> }
  | { kind: 'window'; partitions: Array<{ members: RowKey[] }>; computed: string[] }
  | { kind: 'project'; kept: string[]; removed: string[]; computed: string[]; renamed: Record<string, string> }
  | { kind: 'distinct'; stacks: Array<{ winner: RowKey; members: RowKey[] }> }
  | { kind: 'sort'; order: RowKey[]; sortKeys: string[] }
  | { kind: 'limit'; kept: RowKey[]; cut: RowKey[] }
  | { kind: 'setop'; op: 'union' | 'union all' | 'intersect' | 'except'; branches: [Trace, Trace] }
  | { kind: 'materialize'; name: string; inner: Trace }
  | { kind: 'recursion'; name: string; iterations: Relation[] }
  | { kind: 'dml'; op: 'insert' | 'update' | 'delete' | 'merge';
      inserted: RowKey[]; deleted: RowKey[];
      updated: Array<{ key: RowKey; before: unknown[]; after: unknown[] }>;
      cascades: Array<{ table: string; deleted: RowKey[]; updated: RowKey[] }> }
  | { kind: 'ddl'; diff: SchemaDiff }
  | { kind: 'error'; sqlstate: string; message: string; detail?: string;
      constraint?: string; focus?: { table?: string; column?: string; position?: number } }
);

interface Trace {
  sql: string;
  statementType: 'select' | 'insert' | 'update' | 'delete' | 'merge' | 'ddl' | 'tcl' | 'other';
  mode: 'full' | 'final-only';
  touched: { tables: string[]; columns: string[] };  // для фокуса на доске
  stages: Stage[];
  result: Relation | null;                             // эталон от прямого выполнения
  notices: string[];
  timingMs: number;
}
```

### 5.8 Базовая доска

- `BoardModel` = схема (схемы, таблицы, колонки, ограничения, FK, индексы) + первые N строк каждой таблицы. Строится из каталога после загрузки урока и после каждого «Применить».
- React Flow: `nodes` = таблицы (`TableNode`, мемоизирован, ре-рендер только при изменении своей таблицы), группы-схемы как `group`-ноды, `edges` = FK.
- Настройки производительности: `onlyRenderVisibleElements`, `nodesDraggable=false`, `elementsSelectable=false` в MVP, отключённые анимации рёбер.
- API доски для остальных модулей (через стор, без прямых вызовов): `focus(tables)`, `highlightColumns(cols)`, `dim(on)`, `fitView()`. Это CSS-классы и движение камеры, без пересборки нод.

### 5.9 Движок оверлея

- `OverlayLayer` лежит поверх React Flow внутри того же контейнера. Он подписан на viewport (`useStore(s => s.transform)`) и выставляет тот же transform на свой корневой div. Поэтому координаты сцены = координаты доски, и pan/zoom работают вместе.
- Стартовая позиция призрака = позиция и размеры соответствующей ноды на доске (берём из `getInternalNode`).
- **Состояние сцены** = список «призрачных таблиц» (позиция, колонки, строки по `RowKey`) + декорации (линии пар, сканер, ножницы, бейджи).
- **Аниматоры**: на каждый `stage.kind` одна чистая функция `(prevScene, stage) → { nextScene, timeline }`, где `timeline` = последовательность фаз (например, для join: «сближение → линии → слияние → уход непарных»). Плеер умеет ставить на паузу и шагать по фазам.
- Строки рендерятся как `motion.div` с `layoutId = tableId + RowKey`. Перестановка (ORDER BY) и перенос между таблицами (JOIN, GROUP) анимируются автоматически через FLIP.
- Скраб назад = мгновенная пересборка сцены до нужной стадии без анимации (сцены детерминированы, так что это дёшево).
- `prefers-reduced-motion`: фазы сменяются без движения, только смена состояний и подписи.

### 5.12 Состояния интерфейса и сбои

- **Загрузка**: оболочка и теория рендерятся сразу; доска показывает скелетон «Поднимаем Postgres...», редактор доступен, запросы встают в очередь.
- **Пустые состояния**: урок без таблиц (глава DDL) → доска с подсказкой «Создай первую таблицу: `create table ...`»; пустой результат → «0 строк» плюс подсказка, на какой стадии строки пропали (берём из трассы).
- **Падение worker'а** (WASM crash, нехватка памяти): автоматический перезапуск и восстановление из снапшота + журнала; тост «Песочница перезапущена, твои изменения восстановлены».
- **Ошибка рендера сцены**: ErrorBoundary вокруг оверлея; сцена закрывается, доска и редактор продолжают работать, в dev-сборке стек в консоль.
- **Ленивая загрузка**: каждый MDX-урок и тяжёлые модули (PGlite, парсер, CodeMirror) грузятся через dynamic import; оболочка не ждёт их.
- **Камера по уроку**: позиция и зум доски запоминаются для каждого урока (localStorage).

### 5.13 Ограничения PGlite (что учитываем)

- Одно соединение и один пользователь: конкурентные транзакции только как срежиссированные сцены (глава 11).
- `CREATE INDEX CONCURRENTLY`, репликация, внешние подключения, `COPY ... FROM` файла сервера не показать вживую: уроки по ним только теоретические.
- Расширения: только контрибы PGlite (`@electric-sql/pglite/contrib/*`): есть `pg_trgm`, `pgcrypto`, `uuid_ossp`, `hstore`, `ltree`, `citext`, `unaccent`, `tablefunc` и др.
- Роли и `GRANT`/`REVOKE` работают внутри одного кластера, но проверка прав для другого пользователя требует `SET ROLE` (проверить в фазе 0).
- Версия Postgres в песочнице показывается в интерфейсе («PostgreSQL 18.3 в браузере»).

### 5.14 Ошибки на человеческом языке

Словарь для ~40 частых SQLSTATE. Каждая запись = объяснение + что подсветить на доске. Примеры:
- `42P01 undefined_table`: «Таблицы X нет. Есть: ...». Список доступных таблиц мигает на доске.
- `42703 undefined_column`: «В таблице X нет колонки Y». Колонки таблицы подсвечиваются, ближайшее по написанию имя предлагается («может, `title`?»).
- `42803 grouping_error`: «Колонка должна быть в GROUP BY или внутри агрегата». Колонка подсвечивается красным в стопке группы.
- `42702 ambiguous_column`: «Колонка `name` есть и в `book`, и в `author`. Укажи, из какой: `b.name`». Обе колонки мигают.
- `23505 unique_violation`, `23503 foreign_key_violation`, `23502 not_null_violation`, `23514 check_violation`: строка отскакивает, нарушенное ограничение подсвечено.
- `22012 division_by_zero`, `22P02 invalid_text_representation`, `42601 syntax_error` (с подсказкой по частым опечаткам: запятая перед FROM, `==`, двойные кавычки вместо одинарных).

Оригинальный текст ошибки Postgres всегда показывается рядом: ученик должен привыкать к настоящим сообщениям.

### 6.1 Стиль объяснения (гайд для авторов, выносится в `docs/content-style.md`)

Взято из курса как эталон тона, тексты пишем свои:

- **Числа-якоря**: «Вернулось 9 строк. Запомни это число» и потом сравнение с другим запросом.

### 6.2 Датасеты

Главный датасет **`bookstore`** (используется в большинстве уроков, растёт вместе с курсом):

- `author (author_id PK, name, country, born_year)`: 6 строк, один автор без книг.
- `book_category (category_id PK, name, parent_id → book_category)`: 5 строк, одна категория без книг, иерархия для рекурсивного CTE.
- `book (book_id PK, title, author_id → author NULL, category_id → book_category NULL, price numeric NULL, pages, published_at date, tags text[], meta jsonb)`: 10-12 строк, одна книга без автора и категории, одна без цены, две с одинаковой ценой (ничьи для rank).
- `customer (customer_id PK, name, email UNIQUE, city NULL, created_at timestamptz)`: 6 строк, один без заказов, один без города, два однофамильца.
- `orders (order_id PK, customer_id → customer, status order_status enum, created_at timestamptz)`: 8 строк.
- `order_item (order_id → orders, book_id → book, qty, price, PK(order_id, book_id))`: 15 строк, связь многие-ко-многим.
- `employee (employee_id PK, name, manager_id → employee NULL, salary, hired_at)`: 8 строк, дерево из трёх уровней для SELF JOIN и рекурсии.
- `review (review_id PK, book_id → book, customer_id → customer, rating 1..5, body text)`: 10 строк для агрегатов и полнотекстового поиска.

Дополнительные датасеты:
- **`events`**: временной ряд (сессии и платежи по дням) для оконных функций, дат, gaps-and-islands.
- **`big_bookstore`**: тот же bookstore, но `book` и `orders` на 100k строк через `generate_series` для индексов и EXPLAIN. Доска показывает таблицы в сжатом виде.
- **`empty`**: пустая БД для глав про DDL, где пользователь сам создаёт таблицы.

Все «особые» строки описаны в `docs/datasets.md`. Это список крайних случаев, на которые ссылаются уроки.

## 7. Задачи-головоломки (после глав, фаза 12)

Задача решается, только если тема понята полностью.

- **Формат задачи**: условие + датасет + эталонное решение + 2-3 скрытых датасета-мутанта с крайними случаями (NULL, дубли, ничьи, пустые группы, пользователи без заказов).
- **Проверка**: запрос пользователя и эталон выполняются на видимом и скрытых датасетах, сравнение мультимножеств (с порядком, если в условии есть сортировка). Захардкодить ответ под видимые данные не получится.
- **Лестница подсказок**: 1) какая тема нужна; 2) визуальная подсказка: доска подсвечивает «ловушечные» строки скрытого датасета; 3) скелет запроса.
- **Разбор после решения или сдачи**: проигрывается частая неправильная версия запроса на скрытом датасете, и видно, на какой стадии она ломается. Например, LEFT JOIN + фильтр в WHERE превращается в INNER, и строки пропадают прямо на глазах. Это главная фишка задач.
- **Примеры задач**: NOT IN с NULL; LEFT JOIN с условием в WHERE; раздутая сумма из-за размножения строк; top-N в группе с ничьими; gaps-and-islands; накопительный итог со сбросом; глубина иерархии через рекурсию; дедупликация с сохранением последней версии (DISTINCT ON); count(*) vs count(col) после LEFT JOIN; медиана и перцентили; бакетизация дат с часовыми поясами; «покупатели, купившие все книги категории» (реляционное деление).
- Цель первого пакета: 30-40 задач, по 2-4 на главу.

## 8. Тестирование

- **Unit (vitest, Node + PGlite)**: трассировщик на каждый вид стадии. Фикстура = датасет + запрос + ожидаемые стадии (виды, число строк, пары join, состав групп).
- **Golden-сверка**: для всех запросов из всех уроков финальная стадия трассы совпадает с прямым выполнением. Это та же сверка, что в рантайме, но на CI.
- **Фаззинг трассировщика (фаза 7+)**: генератор случайных запросов по датасету bookstore (комбинации JOIN/WHERE/GROUP BY/ORDER BY/LIMIT) → трасса должна либо совпасть с эталоном, либо честно уйти в `final-only`. Ловит баги в пробах.
- **Тесты контента**: `pnpm test:content` (см. 6.6).
- **Статика**: `tsc --noEmit` и линтер (Biome: линт + формат одним инструментом) на каждом коммите в CI (GitHub Actions). Пайплайн CI заводится в фазе 1.
- **Сценарии «две сессии»** (глава 11): каждый сценарий прогоняется на настоящем Postgres в Docker в CI (две реальные сессии), чтобы срежиссированный ход совпадал с реальностью.
- **E2E (Playwright)**: открыть урок → набрать запрос → проверить чипы стадий, счётчики, результат. Скриншот-снапшоты конечных состояний ключевых сцен (JOIN, GROUP BY, ORDER BY).
- **Производительность**: Playwright-сценарий «30 таблиц + pan/zoom во время анимации», замер кадров через Performance API; порог 55+ fps на M1.

## 9. Производительность: бюджеты

- Реакция на ввод: парсинг < 5 мс, трасса (все пробы) < 150 мс на учебном датасете, первый кадр сцены < 300 мс после паузы ввода.
- Загрузка: PGlite (~3 МБ gzip) грузится лениво после первого рендера оболочки; теория видна сразу, доска показывает скелетон, пока поднимается БД. Целевое время готовности доски < 2 с на холодную.
- Оверлей: до 200 анимируемых строк одновременно. Больше → сжатый режим: строки рисуются блоками-полосками с общим счётчиком (например, «10 000 строк → WHERE → 1 200»), и анимируются блоки.
- Базовая доска: никаких анимаций; `TableNode` мемоизирован; при показе сцены меняется только класс `dimmed` на контейнере.

## 12. Риски

- **libpg-query не заводится в браузере или отстаёт по версии PG.** Обход: пробы склейкой исходного текста по позициям; крайний вариант `pgsql-ast-parser` (pure JS, хуже покрытие). Проверяется в фазе 0.
- **Пробы дают неверный lineage на экзотике.** Защищены сверкой и whitelist поддерживаемых узлов; при сомнении режим «только итог».
- **Тяжёлые запросы вешают песочницу.** Worker + сторож + восстановление из снапшота и журнала.
- **Перф оверлея на больших стадиях.** Сжатый режим от 200 строк, только transform/opacity.
- **Объём контента (~93 урока).** Вертикальный срез, гайд стиля, тесты контента. Уроки пишутся по одному, как в пайплайне курса.
- **Изоляция транзакций не показать вживую в PGlite.** Срежиссированные сцены, валидированные на настоящем Postgres в CI.
- **Авторское право.** Тексты курса не копируем. Перед публичным релизом вычитка на оригинальность.
