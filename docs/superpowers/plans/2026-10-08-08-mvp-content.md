# Ф8 «Контент MVP и релиз MVP»: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Довести продукт до локального релиза MVP. Нужны гайд по текстам, MDX-компоненты теории (SQL-блок с кнопками «На доску» и «Копировать», сцена по шагам, выноски, мост «текст ↔ доска»), раннер `pnpm test:content` и прогресс по урокам. Дальше 13 MVP-уроков, e2e полного пути, перф-тест на 30 таблицах, проверка пяти критериев успеха спеки и ретро.

**Architecture:** Уроки пишутся в MDX. Fenced-блоки ```` ```sql ```` несут мету (`run expect=rows:9`). Ф1 уже сделала `rehypeCodeMeta`, он подсвечивает код shiki и кладёт на `<pre>` атрибуты `data-lang`, `data-meta` и `data-code`. Ф8 подменяет `pre` компонентом `SqlBlock`: тот разбирает мету через `parseSqlMeta` и шлёт запрос в редактор через `useEditorStore.insertQuery`. Дальше живой превью Ф4 сам строит трассу, и сцена проигрывается. Остальные компоненты (`TlDr`, `Callout`, `DontDoThis`, `Cheatsheet`, `Scene`/`Step`, `T`/`C`) передаются в MDX через проп `components`. Мост `T`/`C` работает только через `useBoardStore`. Тест контента читает `.mdx` как текст и вытаскивает sql-блоки регулярным выражением. Потом гоняет их на датасете урока через node-клиент PGlite (`withDataset`, `inPreview`) и сверяет ожидания. Для `run`-блоков он ещё требует трассу `full`.

**Tech Stack:** React 19, TypeScript strict, MDX 3 (`@mdx-js/rollup`), shiki, zustand 5, react-router 8, shadcn/ui, lucide-react, sonner, Vitest 5 (проекты `dom` и `content`), Playwright 1.64, PGlite 0.5.8 (PostgreSQL 18.3).

**Spec:** `docs/superpowers/specs/2026-10-08-visual-sql-design.md` (разделы 1 «Критерии успеха», 3.3, 3.9, 4, 5.10, 5.11, 6.1, 6.3, 6.5, 6.6, 8, 9, 10). Контракты: `docs/superpowers/plans/2026-10-08-00-contracts.md` (разделы 4, 7, 8, 12, 13). Факты Ф0: `docs/spikes.md`.

## Review Focus

1. **Мета `expect=rows:0` и опечатки в мете.** Ноль не должен теряться как «ложное» значение, а `expect=row:9` должен бросать ошибку, а не молча отключать проверку. Тест: `src/features/lessons/mdx/sql-meta.test.ts`, «rows:0 сохраняется» и «опечатка бросает ошибку» (задача 2).
2. **Извлечение блоков из MDX.** Три обратные кавычки внутри строки SQL (не с начала строки) не обрывают блок. Кириллица и номер строки верные, блоки других языков пропускаются. Тест: `tests/content/blocks.test.ts`, «extractSqlBlocks» (задача 8).
3. **Изоляция примеров.** Превью-блок (`BEGIN ... ROLLBACK`) не оставляет следов для следующих блоков, `apply`-блок коммитит. Тест: `tests/content/blocks.test.ts`, «превью не оставляет следов, apply коммитит» (задача 8).
4. **Ложный зелёный.** Блок с `expectError`, который неожиданно выполнился, и блок без ожидания валят тест с понятным текстом и номером строки. Тест: `tests/content/blocks.test.ts`, «expectError, а запрос выполнился» и «блок без ожидания» (задача 8).
5. **«Пройден» при двух условиях в любом порядке.** Урок дочитан до конца и хотя бы один пример запущен. Одного дочитывания мало, одного запуска тоже. Тест: `src/features/lessons/useLessonProgress.test.tsx`, два сценария порядка (задача 10).

## SQL-примеры

Пример пишется обычным fenced-блоком с языком `sql` и метой после языка:

````mdx
```sql run expect=rows:9
select b.title, a.name
from book b
join author a on a.author_id = b.author_id;
```
````

Мета:
- `run`: кнопка «▶ На доску». Ставь почти всегда.
- `expect=rows:N`: сколько строк вернёт последний оператор блока. Проверяет `pnpm test:content`.
- `expectError=SQLSTATE`: блок обязан упасть с этим кодом (`42703`, `42803`...). Для примеров ошибок.
- `trace=final-only`: визуализатор честно показывает только итог. Над блоком обязателен комментарий с причиной: `{/* final-only: подзапрос во FROM появится в Ф10 */}`.
- `apply`: пример меняет данные. Вместо «На доску» будет кнопка «Применить», в тестах блок коммитится. В уроках про чтение данных не используется.
- `noexec`: не выполнять (псевдокод, синтаксис в шпаргалке). Не сочетается с другими ключами.

Правила:
- У каждого блока есть `expect`, `expectError` или `noexec`. Опечатка в мете роняет тест, и это хорошо.
- В `run`-блоке один оператор. Ключевые слова в нижнем регистре, `;` в конце.
- Блоки выполняются сверху вниз на одной базе. Превью-блоки не оставляют следов, `apply`-блоки оставляют.
- Сортируй результат (`order by`), если в тексте важен порядок строк. Без `order by` порядок не обещан, и такой пример годится только для ловушки про порядок.
- Внутри `<Scene>`, `<Callout>` и других компонентов блок пишется без отступа, с пустой строкой до и после.

## Компоненты

- `<TlDr>Суть урока одной строкой.</TlDr>`
- `<Callout kind="analogy">`: аналогия из жизни. Одна главная аналогия на урок, своя, бытовая, без натяжек. Аналогия объясняет механику, а не украшает текст.
- `<Callout kind="trap">`: ловушка, на которой спотыкаются. Внутри обязательно пример, который её показывает.
- `<Callout kind="tip">`: как делают в продакшене.
- `<Callout kind="note">`: важное отступление, без которого можно жить.
- `<DontDoThis href="https://wiki.postgresql.org/wiki/Don't_Do_This#...">`: пересказ своими словами, почему так не надо, и что делать вместо этого.
- `<T id="public.book">book</T>`: таблица в тексте. Наведение подсвечивает её на доске, клик приводит к ней камеру.
- `<C id="public.book.author_id">book.author_id</C>`: колонка в тексте. Наведение подсвечивает колонку и колонку, на которую она ссылается по внешнему ключу.
- `<Scene>` из нескольких `<Step caption="...">`: срежиссированная последовательность запросов. В каждом шаге ровно один sql-блок. Кнопки «Назад» и «Дальше» отправляют запрос шага на доску.
- `<Cheatsheet>`: шпаргалка. Внутри списки и блоки `noexec`.

Других компонентов в MDX нет. Новый компонент = правка контрактов и гайда.

## Приёмы

- **Числа-якоря.** «Вернулось 9 строк. Запомни это число». Следующий пример сравнивает с ним: «а теперь 11: две книги без автора вернулись».
- **Чего нет в выдаче и почему.** После примера, где строки пропали, перечисли их: «❌ Простой Python: у книги нет автора, пары не нашлось».
- **Что видно на доске.** После каждого `run`-примера одна-две фразы о том, что произойдёт на доске: «строки без пары краснеют и уходят».
- **Ошибка как урок.** Типичная ошибка новичка показывается блоком `expectError`. Рядом текст: что написал Postgres и как это читать.
- **Проверь себя.** Вопрос, ответ на который получается запуском: «Сколько строк вернёт этот запрос, если поменять `>` на `>=`? Проверь на доске».

```ts
export interface SqlMeta {
  run: boolean;
  apply: boolean;
  noexec: boolean;
  expectRows?: number;
  expectError?: string;
  trace?: 'full' | 'final-only';
}

const ROWS = /^rows:(\d+)$/;
const SQLSTATE = /^[0-9A-Z]{5}$/;

// Разбирает мету fenced-блока: «run expect=rows:9 trace=final-only».
// Опечатка в мете = ошибка автора урока, поэтому всё незнакомое бросает исключение
export function parseSqlMeta(meta: string): SqlMeta {
  const out: SqlMeta = { run: false, apply: false, noexec: false };
  for (const token of meta.split(/\s+/)) {
    if (token === '') continue;
    const eq = token.indexOf('=');
    const key = eq === -1 ? token : token.slice(0, eq);
    const value = eq === -1 ? null : token.slice(eq + 1);

    if ((key === 'run' || key === 'apply' || key === 'noexec') && value === null) {
      out[key] = true;
      continue;
    }
    if (key === 'expect' && value !== null) {
      const rows = ROWS.exec(value)?.[1];
      if (rows === undefined) throw new Error(`Мета «${token}»: ожидается expect=rows:N`);
      out.expectRows = Number(rows);
      continue;
    }
    if (key === 'expectError' && value !== null && SQLSTATE.test(value)) {
      out.expectError = value;
      continue;
    }
    if (key === 'trace' && (value === 'full' || value === 'final-only')) {
      out.trace = value;
      continue;
    }
    throw new Error(`Неизвестная мета «${token}»`);
  }

  if (out.expectRows !== undefined && out.expectError !== undefined) {
    throw new Error('Мета: expect и expectError в одном блоке не бывают');
  }
  if (out.noexec && (out.run || out.apply || out.expectRows !== undefined || out.expectError !== undefined)) {
    throw new Error('Мета: noexec не сочетается с run, apply и ожиданиями');
  }
  return out;
}
```

import { Check, Copy, Play, Zap } from 'lucide-react';
import { type ComponentProps, useState } from 'react';
import { useParams } from 'react-router';
import { toast } from 'sonner';
import { Button } from '@/components/ui/button';
import { useSandbox } from '@/features/db/SandboxProvider';
import { DbException } from '@/features/db/types';
import { useEditorStore } from '@/stores/editor';
import { useLessonStore } from '@/stores/lesson';
import { parseSqlMeta } from './sql-meta';

type PreProps = ComponentProps<'pre'> & { 'data-lang'?: string; 'data-meta'?: string; 'data-code'?: string };

// «▶ На доску»: запрос уходит в редактор, дальше живой превью сам строит трассу и проигрывает сцену
export function sendToBoard(sql: string, lessonId: string | undefined): void {
  useEditorStore.getState().insertQuery(sql);
  if (lessonId) useLessonStore.getState().markRanExample(lessonId);
}

// Подменяет <pre> в MDX: SQL-блоки получают кнопки, остальные рендерятся как есть
export function SqlBlock(props: PreProps) {
  const { lessonId } = useParams();
  const { sandbox } = useSandbox();
  const [copied, setCopied] = useState(false);

  if (props['data-lang'] !== 'sql') return <pre {...props} />;
  const sql = props['data-code'] ?? '';
  const meta = parseSqlMeta(props['data-meta'] ?? '');

  const copy = () => {
    navigator.clipboard.writeText(sql).then(
      () => {
        setCopied(true);
        setTimeout(() => setCopied(false), 1500);
      },
      () => toast.error('Не удалось скопировать: браузер не дал доступ к буферу обмена'),
    );
  };

  // Пример меняет данные: показываем запрос в редакторе и сразу применяем с COMMIT
  const apply = async () => {
    sendToBoard(sql, lessonId);
    if (!sandbox) return;
    try {
      await sandbox.apply(sql);
    } catch (e) {
      toast.error(e instanceof DbException ? `Не применилось: ${e.db.message}` : 'Не применилось');
    }
  };

  return (
    <div className="my-4" data-testid="sql-block">
      <pre {...props} />
      <div className="not-prose mt-1 flex flex-wrap items-center gap-2">
        {meta.apply ? (
          <Button size="sm" variant="secondary" onClick={() => void apply()}>
            <Zap aria-hidden />
            Применить
          </Button>
        ) : meta.run ? (
          <Button size="sm" variant="secondary" onClick={() => sendToBoard(sql, lessonId)}>
            <Play aria-hidden />
            На доску
          </Button>
        ) : null}
        <Button size="sm" variant="ghost" onClick={copy}>
          {copied ? <Check aria-hidden /> : <Copy aria-hidden />}
          {copied ? 'Скопировано' : 'Копировать'}
        </Button>
      </div>
    </div>
  );
}

**Files:**

**Interfaces:**
- Consumes: `useBoardStore` (`schema`, `highlightedColumns`, `highlightColumns`, `focus`, `setSchema`) из Ф3; типы `SchemaSnapshot`, `TableInfo`, `ColumnInfo` из `@/features/db/introspect`.
- Produces:
  - `export function T(props: { id: string; children: ReactNode }): JSX.Element`: наведение или фокус клавиатурой подсвечивает все колонки таблицы `id`, уход возвращает прежнюю подсветку, клик вызывает `focus([id])` (камера летит к таблице).

```tsx
import { type ReactNode, useRef } from 'react';
import { useBoardStore } from '@/stores/board';

// 'public.book.author_id' → 'public.book'
const tableOf = (columnId: string) => columnId.split('.').slice(0, 2).join('.');

function columnsOfTable(tableId: string): string[] {
  const table = useBoardStore.getState().schema?.tables.find((t) => t.id === tableId);
  return table ? table.columns.map((c) => `${tableId}.${c.name}`) : [];
}

// Колонка плюс колонка, на которую она ссылается по FK: book.author_id тянет за собой author.author_id
function columnWithFk(columnId: string): string[] {
  const tableId = tableOf(columnId);
  const name = columnId.slice(tableId.length + 1);
  const fk = useBoardStore.getState().schema?.fks.find((f) => f.from.tableId === tableId && f.from.columns.includes(name));
  const target = fk?.to.columns[fk.from.columns.indexOf(name)];
  return fk && target ? [columnId, `${fk.to.tableId}.${target}`] : [columnId];
}

function Term({ tableId, highlight, children }: { tableId: string; highlight: () => string[]; children: ReactNode }) {
  // Подсветка до наведения: вернём её, когда курсор или фокус уйдут
  const previous = useRef<string[] | null>(null);

  const enter = () => {
    const board = useBoardStore.getState();
    if (previous.current === null) previous.current = board.highlightedColumns;
    board.highlightColumns(highlight());
  };
  const leave = () => {
    if (previous.current === null) return;
    useBoardStore.getState().highlightColumns(previous.current);
    previous.current = null;
  };

  return (
    <button
      type="button"
      className="cursor-help font-mono text-[0.9em] underline decoration-dotted underline-offset-4"
      onMouseEnter={enter}
      onMouseLeave={leave}
      onFocus={enter}
      onBlur={leave}
      onClick={() => useBoardStore.getState().focus([tableId])}
    >
      {children}
    </button>
  );
}

export function T({ id, children }: { id: string; children: ReactNode }) {
  return (
    <Term tableId={id} highlight={() => columnsOfTable(id)}>
      {children}
    </Term>
  );
}

export function C({ id, children }: { id: string; children: ReactNode }) {
  return (
    <Term tableId={tableOf(id)} highlight={() => columnWithFk(id)}>
      {children}
    </Term>
  );
}

```tsx
import { Children, isValidElement, type ReactNode, useState } from 'react';
import { useParams } from 'react-router';
import { Button } from '@/components/ui/button';
import { sendToBoard } from './SqlBlock';

// Исходник первого SQL-блока в поддереве: rehypeCodeMeta кладёт его в data-code на <pre>
export function sqlOf(node: ReactNode): string | null {
  for (const child of Children.toArray(node)) {
    if (!isValidElement<{ 'data-code'?: unknown; children?: ReactNode }>(child)) continue;
    const code = child.props['data-code'];
    if (typeof code === 'string') return code;
    const nested = sqlOf(child.props.children);
    if (nested !== null) return nested;
  }
  return null;
}

export function Step({ caption, children }: { caption: string; children?: ReactNode }) {
  return (
    <div>
      <p className="font-medium">{caption}</p>
      {children}
    </div>
  );
}

// Срежиссированная последовательность запросов: один шаг на экране, переход шлёт запрос шага на доску
export function Scene({ children }: { children: ReactNode }) {
  const { lessonId } = useParams();
  const [index, setIndex] = useState(0);
  // MDX кладёт между шагами текстовые переводы строк, их отбрасываем
  const steps = Children.toArray(children).filter(isValidElement);

  const go = (next: number) => {
    setIndex(next);
    const sql = sqlOf(steps[next]);
    if (sql !== null) sendToBoard(sql, lessonId);
  };

  return (
    <section aria-label="Сцена" className="my-6 rounded-lg border px-4 py-2">
      <div className="not-prose flex items-center justify-between gap-2 py-2">
        <span className="text-sm text-muted-foreground">
          Шаг {index + 1} из {steps.length}
        </span>
        <div className="flex gap-2">
          <Button size="sm" variant="outline" disabled={index === 0} onClick={() => go(index - 1)}>
            Назад
          </Button>
          <Button size="sm" disabled={index >= steps.length - 1} onClick={() => go(index + 1)}>
            Дальше
          </Button>
        </div>
      </div>
      {steps[index]}
    </section>
  );
}
```

```ts
import { introspect, type SchemaSnapshot } from '@/features/db/introspect';
import { type DbClient, DbException, type QueryResult } from '@/features/db/types';
import { parseSqlMeta, type SqlMeta } from '@/features/lessons/mdx/sql-meta';
import { initParser, parseSql } from '@/features/sql/parser';
import { traceStatement } from '@/features/tracer/trace';
import { inPreview } from '../helpers/db';

export interface SqlBlockSource {
  line: number;
  rawMeta: string;
  meta: SqlMeta;
  sql: string;
}

// Забор ```sql с начала строки (до трёх пробелов отступа, как в CommonMark), закрывающий тоже с начала строки.
// Три обратные кавычки посреди строки SQL блок не закрывают
const SQL_FENCE = /^ {0,3}```sql(?:[ \t]+([^\n]*))?\n([\s\S]*?)\n {0,3}```[ \t]*$/gm;

export function extractSqlBlocks(mdx: string): SqlBlockSource[] {
  return [...mdx.matchAll(SQL_FENCE)].map((m) => {
    const line = mdx.slice(0, m.index).split('\n').length;
    const rawMeta = (m[1] ?? '').trim();
    try {
      return { line, rawMeta, meta: parseSqlMeta(rawMeta), sql: m[2] ?? '' };
    } catch (e) {
      throw new Error(`строка ${line}: ${(e as Error).message}`);
    }
  });
}

type Outcome = { ok: true; results: QueryResult[] } | { ok: false; code: string; message: string };

async function run(db: DbClient, sql: string): Promise<Outcome> {
  try {
    return { ok: true, results: await db.exec(sql) };
  } catch (e) {
    if (e instanceof DbException) return { ok: false, code: e.db.code, message: e.db.message };
    throw e;
  }
}

// Число строк последнего оператора; у оператора без колонок результата (INSERT без RETURNING, DDL) это rowCount
function rowsOf(results: QueryResult[]): number {
  const last = results.at(-1);
  if (!last) return 0;
  return last.fields.length > 0 ? last.rows.length : (last.rowCount ?? 0);
}

// Выполняет блоки урока сверху вниз на одном клиенте. Возвращает проблемы, пустой список = всё сошлось
export async function checkBlocks(
  blocks: SqlBlockSource[],
  db: DbClient,
  opts: { trace: boolean } = { trace: true },
): Promise<string[]> {
  const problems: string[] = [];
  let schema: SchemaSnapshot | null = null;
  if (opts.trace) await initParser();

  for (const { line, meta, sql } of blocks) {
    const at = `строка ${line}`;
    if (meta.noexec) continue;
    if (meta.expectRows === undefined && meta.expectError === undefined) {
      problems.push(`${at}: у блока нет ожидания (expect=rows:N или expectError=SQLSTATE)`);
      continue;
    }

    // Трасса до выполнения: apply-блок ещё не закоммичен, данные те же, что увидит пользователь
    if (opts.trace && meta.run && meta.expectError === undefined && meta.trace !== 'final-only') {
      const parsed = parseSql(sql);
      if (!parsed.ok) {
        problems.push(`${at}: парсер не принял блок: ${parsed.error.message}`);
      } else if (parsed.statements.length !== 1) {
        problems.push(`${at}: в run-блоке должен быть один оператор, а их ${parsed.statements.length}`);
      } else {
        const [stmt] = parsed.statements;
        schema ??= await introspect(db);
        const snapshot = schema;
        const trace = stmt ? await inPreview(db, () => traceStatement(stmt, db, { schema: snapshot })) : null;
        if (trace && trace.mode !== 'full') {
          problems.push(
            `${at}: трасса final-only (${trace.fallbackReason ?? 'причина не указана'}); почини трассировщик или пометь блок trace=final-only с причиной`,
          );
        }
      }
    }

    const outcome = meta.apply ? await run(db, sql) : await inPreview(db, () => run(db, sql));
    if (meta.apply && outcome.ok) schema = null;

    if (meta.expectError !== undefined) {
      if (outcome.ok) problems.push(`${at}: ожидалась ошибка ${meta.expectError}, а запрос выполнился`);
      else if (outcome.code !== meta.expectError) {
        problems.push(`${at}: ожидалась ошибка ${meta.expectError}, получена ${outcome.code}: ${outcome.message}`);
      }
      continue;
    }
    if (!outcome.ok) {
      problems.push(`${at}: неожиданная ошибка ${outcome.code}: ${outcome.message}`);
      continue;
    }
    const rows = rowsOf(outcome.results);
    if (rows !== meta.expectRows) problems.push(`${at}: ожидалось ${meta.expectRows} строк, получено ${rows}`);
  }
  return problems;
}

```ts
import { useEffect } from 'react';
import { useEditorStore } from '@/stores/editor';
import { useLessonStore } from '@/stores/lesson';
import type { LessonMeta } from './types';

// Прогресс урока: вернуть последний запрос, запоминать правки, отметить «пройден».
// Пройден = урок дочитан до метки end и запущен хотя бы один пример, порядок любой
export function useLessonProgress(meta: LessonMeta, end: Element | null): void {
  useEffect(() => {
    const saved = useLessonStore.getState().byId[meta.id]?.lastQuery;
    useEditorStore.getState().insertQuery(saved ?? meta.initialQuery ?? '');
    return useEditorStore.subscribe((state, prev) => {
      if (state.text !== prev.text) useLessonStore.getState().setLastQuery(meta.id, state.text);
    });
  }, [meta]);

  useEffect(() => {
    if (!end) return;
    let reachedEnd = false;
    const tryComplete = () => {
      const p = useLessonStore.getState().byId[meta.id];
      if (reachedEnd && p?.ranExample && !p.completed) useLessonStore.getState().markCompleted(meta.id);
    };
    const observer = new IntersectionObserver((entries) => {
      if (!entries.some((e) => e.isIntersecting)) return;
      reachedEnd = true;
      tryComplete();
    });
    observer.observe(end);
    const unsubscribe = useLessonStore.subscribe(tryComplete);
    return () => {
      observer.disconnect();
      unsubscribe();
    };
  }, [meta.id, end]);
}
```

## Колонка

Колонка это одно свойство, одинаковое для всех строк таблицы. У <T id="public.book">book</T> есть колонки <C id="public.book.title">title</C>, <C id="public.book.price">price</C>, <C id="public.book.pages">pages</C> и другие.

Выберем три колонки:

```sql run expect=rows:11
select title, price, pages from book;
```

Строк по-прежнему 11, колонок 3. Каждая строка прошла целиком, а на выходе из каждой осталась только запрошенная часть. Это и есть «получить колонку».

## Ячейка

Ячейка это значение на пересечении строки и колонки. Одна строка и одна колонка, значит одна ячейка:

```sql run expect=rows:1
select title from book where book_id = 7;
```

Одна ячейка: «Остров погибших кораблей». Так добираются до самого маленького кусочка данных.

## У каждой колонки свой тип

Тип говорит, что за значения живут в колонке и что с ними можно делать. Сравнить `price` с числом можно, а `title` с числом нельзя:

```sql run expect=rows:1
select title, price, pages, published_at, tags from book where book_id = 1;
```

Одна строка «Тихого Дона». Смотри на типы: `price` это numeric (цена с копейками), `pages` это int, `published_at` это date, `tags` это text[], массив строк. Типы нарисованы прямо у колонок на доске.

А теперь попытаемся сравнить текст с числом:

```sql run expectError=42883
select title from book where title = 5;
```

Postgres отвечает `operator does not exist: text = integer`. Так он говорит: «не могу сравнить строку с числом». Типы не совпали, сравнения не существует. Приводить типы руками научимся в главе 5.

## Пустая ячейка это NULL

Если значения нет, в ячейке стоит не ноль и не пустая строка, а NULL. «Не знаем», «не указано», «нет значения».

```sql run expect=rows:1
select title, price from book where price is null;
```

Одна строка: «Остров погибших кораблей». На доске пустая ячейка рисуется серой плашкой `NULL`. Это особое значение, про него будет отдельный урок про трёхзначную логику (4.5).

## Ловушки

<Callout kind="trap">

## Ты пишешь не в том порядке, в каком Postgres думает

Вот обычный запрос:

```sql run expect=rows:11
select * from book;
```

SQL выглядит так: сначала `select`, потом `from`, потом `where`. А выполняется наоборот. Postgres сначала находит таблицу, потом фильтрует строки, потом собирает выдачу. Полный порядок такой:

1. `FROM` и `JOIN`: какие таблицы и какие строки берём.
2. `WHERE`: какие строки проходят.
3. `GROUP BY`: строки сбиваются в группы (глава 7).
4. `HAVING`: какие группы проходят.
5. `SELECT`: какие колонки и выражения попадают в выдачу.
6. `ORDER BY`: в каком порядке строки стоят.
7. `LIMIT`: сколько строк отдаём.

Это логический порядок. Postgres внутри может хитрить и что-то переставлять ради скорости, но результат всегда такой, будто шаги прошли именно так. Наша доска показывает шаги как раз в логическом порядке.

<Callout kind="analogy">
Запрос это конвейер в пиццерии, и клаузы это станции. `FROM` привозит продукты. `WHERE` выбрасывает просроченное. `SELECT` собирает пиццу. `ORDER BY` раскладывает по коробкам в нужном порядке. `LIMIT` решает, сколько коробок отдать курьеру. Ты в меню перечисляешь блюда (`select`) раньше склада (`from`), но пиццу всё равно собирают после того, как продукты приехали.
</Callout>

## Почему это важно: алиас из SELECT невидим в WHERE

Раз `WHERE` выполняется раньше `SELECT`, алиаса, который ты придумал в `select`, в `where` ещё не существует. Попытаемся:

```sql run expectError=42703

```

Postgres: `column "sale" does not exist`. В момент `WHERE` колонки `sale` нет, она появится на шаге `SELECT`. Фильтруй по исходной колонке: `where price > 2000`.

```sql run expect=rows:3

```

Три строки, отсортированные по скидочной цене: 1791, 2160, 2880. Почему так вышло с числами: 1990 и 2400 и 3200, умноженные на 0.9.

## Пустая ячейка

NULL это не ноль, не пустая строка и не «нет строки». Это значение «неизвестно»: данные просто отсутствуют.

```sql run expect=rows:1

## Сравнение с NULL всегда «не знаю»

Условие в `WHERE` хочет получить TRUE или FALSE. С NULL любое сравнение даёт третье, `NULL`, «не знаю». А фильтр пропускает только TRUE.

Классическая ловушка новичка:

```sql run expect=rows:0

## COALESCE: подставить значение вместо NULL

<Callout kind="analogy">

</Callout>

## Почему OFFSET плохо на больших таблицах

OFFSET 1000000 заставляет Postgres посчитать и выкинуть миллион строк, и только потом отдать результат. Чем глубже страница, тем больше работы. Это называется offset-пагинация, и на выручку приходит keyset: запомнить значение ключа последней строки страницы и спрашивать «дальше него».

У нас «Простой Python» на 3-м месте с ценой 1990. Следующая страница без offset. Первая попытка, как её пишут новички:

```sql run expectError=42601

```

```sql run expect=rows:3
select title, price from book where price < 1990 order by price desc limit 3;

<TlDr>INNER JOIN склеивает две таблицы по условию ON: в выдачу попадают только строки, нашедшие пару в обеих таблицах.</TlDr>

## Что есть в данных

Две таблицы. В <T id="public.book">book</T> 11 книг, в <T id="public.author">author</T> 6 авторов. Колонка <C id="public.book.author_id">book.author_id</C> смотрит на <C id="public.author.author_id">author.author_id</C>: на доске между ними ребро. Особые строки: у «Простого Python» и «Изучаем Python» автора нет (NULL), у Бориса Пастернака нет книг.

## Зачем соединять таблицы

Почему бы не хранить имя автора прямо в таблице книг? Тогда имя повторялось бы в каждой его книге, и поправить опечатку пришлось бы в десятке мест. Поэтому данные разделяют: книги отдельно, авторы отдельно, а связь через `author_id`. Это и делает реляционную базу реляционной.

Соединить таблицы в одном запросе умеет JOIN.

## Первое соединение

Вот два шага: сначала посмотрим на авторов, потом соединим:

```sql run expect=rows:6
select * from author;
```

```sql run expect=rows:9
select b.title, a.name
from book b
join author a on a.author_id = b.author_id;
```

Вернулось 9 строк. Запомни это число. На доске две таблицы съезжаются навстречу, между колонками `author_id` протягиваются линии для каждой совпавшей пары, потом пары сливаются в одну широкую строку: слева книга, справа автор. 9 пар совпало.

Откуда 9: у 9 из 11 книг автор указан и нашёлся. Каждая строка выдачи это «книга + её автор».

<Callout kind="analogy">
Список гостей вечеринки, где каждый отметил, с кем пришёл. INNER JOIN это сводный список пар: в него попадают только те, кого отметили с обеих сторон. Кто не отмечен ни у кого, за стол не садится.
</Callout>

## Алиасы таблиц: b и a

В запросе таблицы получили короткие имена: `book b`, `author a`. Это алиасы таблиц. Без них пришлось бы писать `book.title`, `author.name`, и так в каждом упоминании. С алиасами: `b.title`, `a.name`.

Алиас обязателен, когда таблица соединяется сама с собой (урок 6.6), и просто удобен во всех остальных случаях.

## Что случилось с 11 книгами

Две книги без автора в выдачу не попали. У них `author_id` NULL, и пары в таблице авторов не нашлись. INNER JOIN не терпит строк без пары: они краснеют и уходят вниз.

Ты уже знаешь этот приём из урока про NULL: нет пары, нет строки. В разделе «чего нет» перечислим всех пропавших.

## Размножение строк

Бывает наоборот: строк больше, чем в исходных таблицах. У Михаила Шолохова две книги:

```sql run expect=rows:2
select a.name, b.title
from author a
join book b on b.author_id = a.author_id
where a.name = 'Михаил Шолохов';
```

2 строки: «Тихий Дон» и «Судьба человека». Автор один, но его строка склеилась с двумя строками книг, и в выдаче он дважды. На доске видно, как строка автора «клонируется» на каждую пару. JOIN не складывает, а именно склеивает пары: сколько пар, столько строк.

## USING: соединение по одинаковым колонкам

Если колонки называются одинаково, условие пишут короче через USING:

```sql run expect=rows:9
select b.title, a.name
from book b
join author a using (author_id);
```

Те же 9 строк. USING (author_id) значит «соедини по колонке author_id из обеих таблиц». Звёздочка покажет разницу:

```sql run expect=rows:9
select * from book b join author a using (author_id);
```

9 строк, и колонка `author_id` в выдаче одна, а не две: USING сливает колонки соединения. При ON-условии колонок было бы две.

## Условие посложнее

В ON можно писать не только равенство ключей:

```sql run expect=rows:6
select b.title, a.name
from book b
join author a on b.author_id = a.author_id and a.country = 'Россия';
```

6 строк: только книги российских авторов. Французский «Путешествие к центру Земли» и бразильский «Python. К вершинам мастерства» ушли.

## Ловушки

<Callout kind="trap">
Забыл условие ON: Postgres откажется выполнять запрос, это не «соедини как-нибудь»:

```sql run expectError=42601
select b.title, a.name from book b join author a;
```

Синтаксическая ошибка: JOIN без условия запрещён. Хочешь «все со всеми»: это CROSS JOIN, урок 6.5.
</Callout>

<Callout kind="trap">
Колонка `author_id` есть в обеих таблицах. Напишешь её без алиаса, и Postgres спросит, из какой именно:

```sql run expectError=42702
select author_id from book b join author a on b.author_id = a.author_id;
```

`column reference "author_id" is ambiguous`, код `42702`. Уточняй: `b.author_id` или `a.author_id`.
</Callout>

<Callout kind="tip">
Указывай алиас у каждой колонки в запросах с JOIN. Даже там, где неоднозначности сейчас нет: новая колонка в таблице завтра сделает твой запрос двусмысленным.
</Callout>

## Отправная точка: INNER

Сначала якорь из прошлого урока:

```sql run expect=rows:9
select b.title, a.name
from book b
join author a on a.author_id = b.author_id;
```

9 строк. Запомни: «Простой Python» и «Изучаем Python» сюда не попали, потому что пары в таблице авторов у них нет. INNER JOIN строки без пары выбрасывает.

## LEFT: все строки слева

Поменяем одно слово:

```sql run expect=rows:11
select b.title, a.name
from book b
left join author a on a.author_id = b.author_id;
```

11 строк. Было 9, стало 11: обе книги без автора вернулись. На доске строки без пары не краснеют и не уходят: они едут в итог, а правая половина заполняется серыми NULL-плашками. У «Простого Python» в колонке `name` стоит NULL.

Вот и ответ на вопрос «почему INNER теряет книги, а LEFT нет»: INNER требует пару, LEFT разрешает её отсутствие.

Левая таблица это та, что стоит слева от слова JOIN в тексте запроса, здесь `book`. LEFT JOIN сохраняет все строки левой таблицы, правую достраивает NULL при отсутствии пары. Правые строки без пары (как Пастернак) всё равно уходят.

## RIGHT: все строки справа

RIGHT JOIN зеркально: сохраняет правую таблицу, NULL достраивает слева.

```sql run expect=rows:10
select b.title, a.name
from book b
right join author a on a.author_id = b.author_id;
```

10 строк: 9 пар плюс Борис Пастернак с NULL в колонке `title`. Книги без автора ушли: слева их никто не обязан спасать.

Тот же результат даёт LEFT JOIN, если поменять таблицы местами:

```sql run expect=rows:10
select a.name, b.title
from author a
left join book b on b.author_id = a.author_id;
```

10 строк. RIGHT JOIN почти всегда можно переписать как LEFT, поменяв стороны, и многие так делают: читать `left join` привычнее. Проверь себя: в выдаче этого запроса Пастернак, а «Простого Python» нет.

<Callout kind="analogy">
Танцевальный вечер, где пары не обязаны сложиться. INNER JOIN: танцуют только сложившиеся пары. LEFT JOIN: каждый из левого списка выходит на паркет, а если партнёра нет, танцует с пустым местом. RIGHT JOIN то же, только список другой.
</Callout>

## Ловушка: WHERE превращает LEFT в INNER

Самая частая ошибка с LEFT JOIN: фильтровать правую таблицу в WHERE:

```sql run expect=rows:9
select b.title, a.name
from book b
left join author a on a.author_id = b.author_id
where a.name is not null;
```

Снова 9 строк! WHERE выполнился после соединения и выбросил строки, где `name` оказался NULL, то есть те самые спасённые книги. LEFT остался только на бумаге: по факту это INNER JOIN. На доске видно, как строки сначала получают NULL-половины, а потом падают на фильтре.

Правильное место для такого фильтра: условие ON (тогда левые строки сохранятся), и это целый урок 6.9.

select count(*) from book;
```

Одна строка, одно значение: 11. На доске все 11 строк сжимаются в одну, а счётчик пробегает значения: 1, 2, 3... до 11. Выдача агрегатного запроса без GROUP BY всегда одна строка.

<Callout kind="analogy">
Стопка монет на столе. `count` говорит, сколько монет. `sum` складывает номиналы. `min` и `max` находят самую маленькую и большую по достоинству. Всё это вопросы про стопку целиком, а не про одну монету.
</Callout>

## count(*) против count(колонка)

Два похожих счётчика с разной привычкой к NULL:

```sql run expect=rows:1
select count(price) from book;
```

10, а не 11. `count(price)` считает только не-NULL значения. Книга без цены не посчиталась: NULL невидим для агрегатов, как и для сравнений из урока 4.5.

```sql run expect=rows:1
select count(*) from customer;
```

```sql run expect=rows:1
select count(city) from customer;
```

6 и 5. `count(*)` считает строки, NULL в ячейках не мешает. `count(city)` считает заполненные города, Мария Ивановна без города не влезла.

Правило: `count(*)` для числа строк, `count(колонка)` для числа заполненных значений.

## sum, avg, min, max

Остальная пятёрка на ценах книг:

```sql run expect=rows:1
select min(price), max(price) from book;
```

Минимум 350.00, максимум 3200.00. NULL-цена не участвует: минимума «нет значения» не бывает.

```sql run expect=rows:1
select avg(price) from book;
```

Среднее 1138.00: Postgres сложил 10 цен (11380.00) и разделил на 10, а не на 11. Книга без цены в среднем не участвует, знаменатель честно 10.

Количество экземпляров в заказах:

```sql run expect=rows:1
select sum(qty) from order_item;
```

19. `sum` тоже игнорирует NULL: если бы в какой-то строке `qty` был NULL, она не испортила бы сумму, а просто не попала бы в неё.

## Пустое множество: NULL или ноль

Что вернут агрегаты, если строк нет вообще? Проверим на невозможном условии:

```sql run expect=rows:1
select sum(price) from book where price > 99999;
```

Одна строка, в ней NULL. Складывать нечего, и `sum` честно говорит «не знаем». Не ноль!

```sql run expect=rows:1
select count(price) from book where price > 99999;
```

Ноль. `count` считает штуки, пусто значит 0. А `avg` и `min` на пустом множестве дадут NULL, как `sum`. Запомни: сумма пустоты это NULL, и это не придирка. Ноль означал бы «складывали и получилось ничего», а тут складывать было нечего.

## Агрегаты можно смешивать

Агрегатных выражений может быть несколько, как обычных колонок, и алиасы из урока 4.1 работают. Дальше в сцене `min` и `max` стоят рядом в одном запросе, а можно и все пять сразу: `select count(*), min(price), max(price), sum(price), avg(price) from book`.

```

</Step>

## Агрегат по частям

Урок 7.1 научил сворачивать всю таблицу в одно число. А если нужно «по каждой стране отдельно»? Для этого и есть GROUP BY:

## Что можно, а что нельзя в выдаче

Правило жёсткое: в списке SELECT могут стоять только колонки из GROUP BY и агрегаты. Почему, видно на доске: в стопке «Россия» 4 разных имени, какое из них писать в выдачу? Postgres не выбирает, он отказывается:

```sql run expectError=42803

```

`column "author.name" must appear in the GROUP BY clause`, код `42803`. Колонка `name` не в GROUP BY и не в агрегате, её место в стопке неоднозначно. Лечится двумя путями: добавить `name` в `group by` или завернуть в агрегат, например `string_agg(name, ', ')`.

<TlDr>WHERE фильтрует строки до группировки, HAVING фильтрует уже готовые группы. «Статусы, где больше одного заказа» это HAVING.</TlDr>

## Что есть в данных

В <T id="public.orders">orders</T> 8 заказов: 4 paid, 2 new, 1 shipped, 1 cancelled. Заказы с 2024-04-01: 5 штук, из них 2 paid, 2 new, 1 cancelled. В <T id="public.review">review</T> 10 отзывов о 7 книгах.

## WHERE не видит агрегатов

Хочется оставить статусы, где заказов больше одного:

```sql run expectError=42803
select status, count(*) from orders where count(*) > 1 group by status;
```

Postgres отвечает `aggregate functions are not allowed in WHERE`, код `42803`. И он прав: вспомни урок 4.2, WHERE выполняется до GROUP BY. В момент WHERE стопок ещё нет, «число заказов в группе» ещё не посчитано. Фильтровать нечем.

## HAVING фильтрует группы

Для условий по агрегатам существует HAVING. Он выполняется после GROUP BY, когда стопки уже собраны:

```sql run expect=rows:4
select status, count(*) from orders group by status;
```

```sql run expect=rows:2
select status, count(*) from orders group by status having count(*) > 1;
```

Первый запрос: 4 группы, это якорь. Второй: 2 группы, paid и new. Shipped и cancelled по одному заказу и не прошли. На доске фильтр по группам выглядит как WHERE из урока 4.3, только сканер бежит не по строкам таблицы, а по стопкам: прошедшие мигают зелёным, остальные уходят.

<Callout kind="analogy">
Конкурс самодеятельности. WHERE это охрана на входе: решает, кто вообще попадёт на сцену. HAVING это жюри: смотрит уже выступившие номера и отсеивает слабые. Одни и те же люди, но вопросы задаются в разное время и про разное.
</Callout>

## WHERE и HAVING вместе

Оба фильтра в одном запросе идут по конвейеру урока 4.2: сначала WHERE, потом GROUP BY, потом HAVING:

```sql run expect=rows:3
select status, count(*) from orders
where created_at >= '2024-04-01'
group by status;
```

```sql run expect=rows:2
select status, count(*) from orders
where created_at >= '2024-04-01'
group by status
having count(*) > 1;
```

Первый: только заказы с апреля, 3 группы (paid 2, new 2, cancelled 1). Второй: из них отфильтрованы группы больше одного заказа, остались paid и new. Сравни с HAVING без WHERE: туда входили все 8 заказов, и paid там было 4. Числа разные, потому что на входе разные строки.

## Условие не по агрегату

HAVING может фильтровать и по обычным колонкам группы:

```sql run expect=rows:3
select status, count(*) from orders group by status having status <> 'cancelled';
```

4 минус 1 = 3 строки. Работает, но так не пишут: по колонкам группы фильтрует WHERE, и это дешевле: зачем собирать стопку, чтобы её выбросить. HAVING оставь для агрегатов.

В HAVING, как в SELECT, живут колонки из GROUP BY и агрегаты:

```sql run expectError=42803
select status, count(*) from orders group by status having customer_id = 1;
```

`42803`: `customer_id` не в GROUP BY и не в агрегате. Внутри стопки 2 заказа разных покупателей, какой из них «равен 1»?

## Дорогие категории

Средняя цена по категориям из урока 7.2, оставим только дороги выше 1000:

```sql run expect=rows:2
select category_id, avg(price) from book group by category_id having avg(price) > 1000;
```

2 строки: Python-книги в среднем 2800.00 и NULL-категория («Простой Python» за 1990). Классика и фантастика не прошли фильтр.

## Ловушки

<Callout kind="trap">
WHERE по дате меняет состав групп, а HAVING только прячет готовые. Запросы «где статус встречается больше N раз с прошлого квартала» и «где статус встречается больше N раз» дают разные ответы, и разница именно в WHERE. Прежде чем фильтровать, спроси себя: про строки это условие или про группы?
</Callout>

<Callout kind="tip">
Правило выбора простое. Условие по колонкам строк и без агрегатов: WHERE. Условие по `count`, `avg`, `sum`: HAVING. Если условие написали не там, Postgres скажет `42803`, прислушайся.
</Callout>

<Cheatsheet>
- WHERE: строки, до GROUP BY, агрегаты запрещены (`42803`).
- HAVING: группы, после GROUP BY, агрегаты разрешены.
- Конвейер: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
- Условие по агрегату в WHERE не напишешь: для него существует HAVING.
</Cheatsheet>
