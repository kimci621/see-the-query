# Ф12 «Задачи-головоломки»: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: используй superpowers:subagent-driven-development (рекомендуемый) или superpowers:executing-plans, чтобы выполнять план задача за задачей. Шаги размечены чекбоксами (`- [ ]`).

**Goal:** движок задач-головоломок: условие, проверка решения на видимом и скрытых датасетах-мутантах, три уровня подсказок, разбор с проигрыванием типичной неправильной версии (трасса со стадией, где она сломалась), UI `/t/:taskId`. 33 задачи T1-T33 из трекера ✅ по DoD.

**Architecture:** задача - это папка `content/tasks/<id>/`: условие (`task.mdx`), эталон (`reference.sql`), типичная неправильная версия (`wrong.sql`), мутанты (`mutants/*.sql` - патчи поверх bookstore, применяются в свежей песочнице). Проверка: решение пользователя прогоняется на видимом датасете и на каждом мутанте; сравнение с эталоном по мультимножеству канонических строк (или с порядком, если задача про порядок). Подсказки и разбор не показывают данные мутантов: подсветка ловушечных строк - на ВИДИМОМ датасете. Разбор: `wrong.sql` прогоняется через трассировщик (Ф5-Ф11) на мутанте, где он падает, сцена останавливается на стадии расхождения с эталоном.

**Tech Stack:** без новых пакетов: TS strict, PGlite, существующие `sandbox`/`tracer`/`overlay`, MDX-пайплайн Ф8, react-router (маршрут уже в контрактах).

**Spec:** спека раздел 7 (задачи-головоломки), 5.2 (`features/tasks`), 6.2 (датасеты), 8 (тесты). Контракты: разделы 4-8, 13.

## Глобальные ограничения

- Ф12 начинается, когда Ф0-Ф11 ✅ (правило трекера «После основных этапов»).
- Скрытые датасеты не покидают проверку: ни подсказки, ни UI не показывают строки мутантов, только факт «на скрытом датасете решение дало не тот ответ».
- Мутанты детерминированы: фиксированный SQL-патч, без рандома. Порядок мутантов фиксирован (м1, м2...).
- Каждая задача: падающий тест ДО контента (раннер задач), эталон проходит на всех мутантах, неправильная версия падает хотя бы на одном.
- Решение подогнать под видимые данные нельзя: мутант создаёт ситуацию, где подгонка даёт неверный ответ. Это и есть приёмочный тест задачи.
- Комментарии на русском, тексты без длинных тире.
- `pnpm format` + `pnpm check` зелёный перед коммитом; коммит с ЯВНЫМИ путями; ``. Трекер: ⬜ → 🔄 → ✅ с датой в коммите.

## Review Focus

1. **Утечка мутантов в подсказки.** Подсказка уровня 2 показывает ловушечные строки ВИДИМОГО датасета. Тест: рендер подсказок не содержит данных мутанта (греп по уникальным значениям мутанта в выводе).
2. **Подгонка решения.** Решение, хардкоженное под bookstore (например, `where name <> 'Борис Пастернак'`), обязано падать на мутанте, который меняет имена. Тест движка: анти-тест «хардкод» на T1.
3. **«Неправильная версия» ломается не там.** Разбор обязан показать СТАДИЮ расхождения с эталоном (сверка трасс), не просто «ответ не совпал». Тест: для T2 стадия - агрегат после LEFT JOIN.
4. **Порядок строк.** Задачи про порядок (T27, T13) проверяются с порядком; остальные - мультимножеством канонических строк. Смешение - баг. Тест движка: перестановка строк проходит мультимножественную проверку, падает порядковую.
5. **Изоляция песочниц.** Каждый мутант - свежая песочница (снапшот bookstore + патч), утечка состояния между прогонами недопустима. Тест: два мутанта подряд, состояние не смешивается.

## Проверка движка: контракт `engine.ts`

```ts
export interface TaskCheckResult {
  visible: boolean;                    // на видимом bookstore
  mutants: Array<{ id: string; passed: boolean }>;
  passed: boolean;                     // visible и все мутанты
  actual: string[][] | null;           // канон строк юзера на первом упавшем
  expected: string[][] | null;         // канон эталона там же
}
export async function checkTask(task: Task, solutionSql: string, signal?: AbortSignal): Promise<TaskCheckResult>;
```

Канон строки: значения ячеек через `verify.rowCanon` (Ф5), приведение `numeric`-строк к числу, `Date` к ISO - как в `verify.ts`. `check: 'ordered'` сравнивает последовательности, `'set'` - отсортированные, `'plan'` - текст плана `EXPLAIN (COSTS OFF)` эталона и юзера совпадает с точностью до имён (задачи T31, T32).

```sql
select a.name
from author a
where exists (select 1 from book b where b.author_id = a.author_id)

order by a.name

select a.name
from author a
where a.author_id in (select author_id from book group by author_id having min(price) > 1000)

```

## Задачи T1-T33

Каждая задача - по образцу T1 (задача 1): папка `content/tasks/<id>/` с `task.mdx` (условие + 3 подсказки), `reference.sql`, `wrong.sql`, `mutants/`. Шаги в каждой: трекер Txx ⬜→🔄 → файлы → `pnpm test:tasks` зелёный (эталон проходит, wrong падает) → сцены глазами → Txx →✅ → коммит `feat(tasks): задача Txx <название>`. Условие и ловушка взяты из трекера; ниже - эталон (суть), неправильная версия (ловушка) и мутанты (что именно мутируем). Полные тексты условий пишутся по гайду контента, разговорно, без длинных тире.

Числа-якоря по bookstore (арбитр - раннер): Пастернак без книг; «Остров» (id 7) без цены и без заказов; книги 2 и 10 - python; у «Путешествия» и «Детей Гранта» цена 610 (ничья); Николай/Лебедева зарплата 70000 (ничья); Морозов (190000) больше руководителя Орлова (180000); заказ 1 мая по Москве/UTC; два «Ивана Петровых» с разными email.

- **T2 Книги и число заказов, включая незаказанные.** Эталон: `left join order_item` + `count(i.order_id)`; «Остров» - 0. Wrong: `count(*)` (даёт 1). Мутанты: книга в 5 заказах (размножение); книга без заказов с NULL-ценой. Стадия поломки - `group`.
- **T3 Покупатели города и заказы за год, включая без заказов.** Эталон: условие по заказу в ON (или `and (o.order_id is null or ...)`). Wrong: фильтр в WHERE. Мутанты: покупатель города с заказом вне года; покупатель города без заказов.
- **T4 Выручка и средний рейтинг по категориям одной выборкой.** Эталон: агрегаты в двух CTE, join по book. Wrong: два join в одном запросе (размножение строк, сумма раздута). Мутанты: книга в 3 заказах и с 2 отзывами (множитель 6).
- **T5 Сотрудники, зарабатывающие больше своего менеджера.** Эталон: self join `e.salary > m.salary`; ответ Морозов. Wrong: `where salary > (select avg(salary) ...)` (средняя по компании). Мутанты: двое больше руководителя; руководитель без подчинённых.
- **T6 Сотрудники без подчинённых.** Эталон: `not exists`. Wrong: `not in (select manager_id from employee)` - 0 строк из-за NULL у директора. Мутанты: второй сотрудник с NULL-руководителем (два корня); убрать всех подчинённых у одного.
- **T7 Цепочка начальников до директора.** Эталон: рекурсивный CTE с накоплением пути. Wrong: join по одному уровню. Мутанты: 5-й уровень; сотрудник - сам себе руководитель в скрытом датасете? нет (цикл): сотрудник двумя путями.
- **T8 Путь категории «A > B > C» и глубина.** Эталон: рекурсия с `parent.name || ' > ' ||`. Wrong: join без рекурсии. Мутанты: 4-й уровень вложенности категорий; категория без родителя.
- **T9 Покупатели, купившие все книги категории.** Эталон: двойное отрицание (`not exists (book where not exists (order_item where ...))`) или `group by having count(distinct) = (select count ...)`. Wrong: `in (select customer_id ...)` (купил хотя бы одну). Мутанты: категория из 1 книги (in случайно прав); покупатель купил все, кроме одной.
- **T10 Пары книг вместе, без зеркальных дублей.** Эталон: self join `order_item` с `a.book_id < b.book_id`. Wrong: `a <> b` (зеркальные дубли). Мутанты: тройка книг в одном заказе (3 пары); пара в двух заказах (2 вхождения).
- **T11 Самая дорогая книга в категории с учётом ничьих.** Эталон: `rank() = 1`; в фантастике ничья 610/610 - 2 строки. Wrong: `row_number() = 1` (теряет одну). Мутанты: тройная ничья; NULL-цена самая «дорогая» (nulls last).
- **T12 Топ-2 покупателя по выручке в городе, без города - отдельной группой.** Эталон: `row_number over (partition by coalesce(city, '<без города>'))`. Wrong: partition by city (NULL - одна группа со строками или теряется). Мутанты: город с 4 покупателями (граница топ-2); двое без города с равной выручкой.
- **T13 Последний заказ покупателя при одинаковом времени.** Эталон: `distinct on (customer_id) ... order by customer_id, created_at desc, order_id desc`. Wrong: без тай-брейка. Мутанты: два заказа в одну секунду (заказ 1 мая Москвы/UTC уже есть); отмена после оплаты в ту же секунду.
- **T14 Удалить дубли клиентов по email без учёта регистра, оставив самого раннего.** Эталон: `delete ... using` с `(created_at, customer_id)` сравнением или `row_number() over (partition by lower(email))`. Wrong: distinct on наоборот/по id. Мутанты: тройной дубль; дубль с равным created_at (тай-брейк по id).
- **T15 Выручка по дням с нулями.** Эталон: `generate_series` + `left join` (count/sum дают 0/NULL - coalesce). Wrong: group by по фактическим дням (нет нулей). Мутанты: 3 дня подряд без продаж; день с возвратом.
- **T16 Серии дней подряд с покупками.** Эталон: gaps-and-islands: `created_at::date - row_number() over (order by ...)`. Wrong: lag сравнение с фикс. шагом (пропущенный день ломает серию). Мутанты: две серии с разрывом 1; одинокий день.
- **T17 Накопительная выручка со сбросом в начале месяца.** Эталон: `sum over (partition by date_trunc('month', ...))`. Wrong: без партиции (копится через месяц). Мутанты: границы двух месяцев; возврат в середине месяца.
- **T18 Рост выручки месяц к месяцу в %.** Эталон: `lag` + `100 * (x - lag) / nullif(lag, 0)` (NULL первого месяца, деление на ноль). Wrong: без nullif. Мутанты: месяц с нулевой выручкой; один месяц всего.
- **T19 Медиана цены по категориям.** Эталон: `percentile_cont(0.5) within group (order by price)`; NULL-цены игнорируются агрегатом. Wrong: avg. Мутанты: чётное число книг (среднее двух соседей); все цены NULL в категории.
- **T20 Средний рейтинг по категории, книги без отзывов не портят среднее.** Эталон: `left join` + `avg(rating)` (NULL игнорируется). Wrong: `coalesce(rating, 0)` (утягивает вниз) - на bookstore категории без отзывов дают NULL vs 0. Мутанты: категория с одним NULL-отзывом... отзывов без рейтинга не бывает: категория, где половина книг без отзывов.
- **T21 Число заказов по каждому статусу, включая статусы без заказов.** Эталон: `enum_range('new'::order_status) ... left join`. Wrong: group by status. Мутанты: статус без заказов (уже есть: shipped есть... найти); все заказы одного статуса.
- **T22 Заказы за конкретные сутки по TZ пользователя.** Эталон: `created_at >= timestamptz '... 00:00' and created_at < + interval '1 day'`. Wrong: `between ... '23:59:59'`. Мутанты: заказ в 23:59:59.5; заказ 1 мая 00:10 Москвы (30 апреля UTC).
- **T23 Книги с тегом python и без тега beginner.** Эталон: `tags @> '{python}' and not tags @> '{beginner}'`. Wrong: `not 'beginner' = any(tags)` с NULL-тегами? (массивы not null - мутант с NULL-массивом). Мутанты: книга `{python}`; книга `{python, beginner}`; NULL-массив.
- **T24 Покупатели с уведомлениями и без языка в settings.** Эталон: `settings ? 'notify'` + `not settings ? 'lang'`; ответ Мария. Wrong: `->> 'lang' is null` (пропускает и отсутствующий, и null - на bookstore одинаково; мутант различает). Мутанты: `{"notify": true, "lang": null}` (язык есть, значение null).
- **T25 Загрузить прайс через UPSERT, обновляя только изменившиеся цены.** Эталон: `on conflict (book_id) do update set price = excluded.price where book.price is distinct from excluded.price returning ...`. Wrong: без where (все «обновлены»). Мутанты: цена не изменилась; новая книга в прайсе.
- **T26 Клиенты старой выгрузки, которых нет в новой.** Эталон: `not exists` с `is not distinct from` по строке. Wrong: EXCEPT (NULL-ы равны, строка с NULL-городом «находится»). Мутанты: клиент с NULL-городом в обеих; клиент только в новой.
- **T27 Третья страница по 3 книги при одинаковых ценах, стабильно.** Эталон: keyset `order by price, title limit 3 offset 6` (порядок полный - title тай-брейк) или `row_number`. Wrong: `order by price limit 3 offset 6` (нестабильно при ничьей 350). Мутанты: 4 книги с ценой 350 (граница страницы).
- **T28 Число книг по корзинам цен, включая пустые.** Эталон: `left join (values ('дёшево', 0, 500), ...) v on ...`. Wrong: group by case (нет пустых корзин). Мутанты: пустая корзина в середине диапазона; книга на границе (500).
- **T29 Суммы по группам и общий итог с подписями.** Эталон: `rollup` + `grouping()` + `coalesce(name, 'ИТОГО')`. Wrong: union с тоталом (или grouping без меток). Мутанты: одна группа (rollup даёт 2 строки); NULL-ключ в данных (спутать с итогом).

Wrong: два update без условия (CHECK `bonus >= 0` падает - 23514, или уходит в минус при отключённом check). Мутанты: недостаточно бонуса у источника.

Wrong: `select *` (heap access). Мутанты: таблица с «дырявым» visibility map после update (_ios не берётся - rel: показать, что ответ всё равно правильный, план другой).

## Риски и что делать

- **Мутанты не ловят подгонку.** Анти-тест хардкода в движке (греп литералов видимых данных в решении юзера - предупреждение, не провал) + ревью каждой задачи: wrong обязан падать минимум на одном мутанте (раннер).
